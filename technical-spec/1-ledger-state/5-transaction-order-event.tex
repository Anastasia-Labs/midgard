\section{Transaction Order event}
\label{h:transaction-order-event}

A forced transaction set is a finite map from transaction order ID to the compact transaction order source value:
\begin{align*}
    \T{ForcedTransactionSet} &\coloneq \T{Map(TxOrderId, ForcedInclusionTx)} \\
      &\coloneq \Bigl\{
        (k_i: \T{TxOrderId}, v_i: \T{ForcedInclusionTx}) \mid \forall i \neq j.\; k_i \neq k_j
    \Bigr\}
\end{align*}

Transaction orders are events on L1 as an alternative to the L2 transaction submission to operators.
Similar to a deposit or withdrawal event, a transaction order in a Midgard block acknowledges that a user has created an L1 utxo at the Midgard L1 transaction order address, obligating the operator to include the given L2 transaction.
The transaction order payload does not carry an operator validity classification.
In turn, the operator sets \code{MidgardTxValidity} when including the order in a block.
This invalidity claim itself can then be subject to fraud proofs if the operator had stated incorrectly.
\begingroup
\allowdisplaybreaks{}
\begin{align*}
    \T{TxOrderEvent} &\coloneq \T{(TxOrderId, MidgardTxCompactWithoutValidity)} \\
    \T{TxOrderId} &\coloneq \T{OutputRef} \\
    \T{ForcedInclusionTx} &\coloneq \left\{
    \begin{array}{ll}
        \T{tx\_compact} : & \T{MidgardTxCompactWithoutValidity} \\
        \T{operator\_validity} : & \T{MidgardTxValidity}
    \end{array} \right\}
\end{align*}
\endgroup

The \code{TxOrderId} of a transaction order event corresponds to one of the inputs spent by the user in the L1 transaction that created the transaction order utxo on L1 (more specifically, it's the hash of its serialized output-reference).
This key is needed to identify the L1 transaction order utxo, and ensure that each order is unique.
The forced transaction source root is keyed by this L1 order identity, not by the L2 transaction ID.
This permits multiple L1 orders for the same L2 transaction to be represented and challenged independently.
The L2 transaction ID is derived from \code{tx\_compact.body}; it is not repeated in \code{ForcedInclusionTx}.
The transaction validity interval is also part of the compact body, so transaction-order due checks use that validity range rather than a separate inclusion timestamp.

The effect of a valid included transaction order on a block's utxo set is identical to a valid L2 transaction request.
It removes all of the transaction's inputs from the ledger and adds all of its outputs.
Invalid included transaction orders are represented as forced transaction trace steps whose operator validity classification is challengeable.

In canonical V1, every canonical field preimage is published as an independently
locked fragment. A second transaction references that fragment and may mint a
compact field-receipt NFT only after the receipt policy recomputes the compact
source, field hash, canonical encoding, and compiled field bound on L1. The
receipt datum binds the \code{TxOrderId}, transaction commitment, field index,
and exact fragment output reference. This two-transaction sequence avoids a
circular attempt to place a publishing transaction's own ID in one of its
inline output datums.

The final transaction-order mint references exactly nine compact receipts,
not all nine large field fragments. It verifies the ordered receipt NFT and
datum for every committed field and records both ordered reference lists in
the order datum. When the order is consumed, all fragments and receipts must
also be consumed, the order NFT and all receipt NFTs must be burned, and the
fragment/receipt spending validators independently enforce those burns.
Missing, duplicate, non-canonical, mismatched, oversized, or unreceipted
fragments fail closed.

The canonical V1 validation trace uses the same machine for normal and forced
transactions. A valid forced transaction therefore applies the exact accepted
ledger delta, while an invalid forced transaction commits an exact no-op.
An operator verdict that differs from the L1-computed terminal verdict is a
fault in either direction.

The temporary \code{ValidForcedTransactionUnsupported} implementation gate is
fail-closed scaffolding only. It must be removed and replaced by complete
accepted-effectful and rejected-no-op L1 proof paths before canonical V1
activation.

\Cref{h:transaction-order} describes the lifecycle of a transaction order request in further detail.
