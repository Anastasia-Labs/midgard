\section{Script execution and the proof boundary}
\label{s:phase-two-fraud-proofs}

Midgard's transaction codec and off-chain evaluator can represent native,
Plutus V3, and MidgardV1 scripts. Canonical V1 enables that surface through a
committed deterministic validation trace whose one-step transitions are
independently verified by L1. The trace covers inline and reference source
resolution, redeemer-purpose binding, script-integrity binding, native-script
evaluation, CEK execution, protected-output receive purposes, observers,
minting policies, execution budgets, and the resulting ledger delta.

Every enabled script purpose requires all of the following together:

\begin{enumerate}
    \item a committed execution trace or other L1-verifiable evidence format;
    \item sound challenge and negative tests for every enabled script purpose;
    \item worst-case transaction-size and execution-unit evidence;
    \item the exact canonical V1 protocol/profile identity, deployment manifest,
          validator hashes, and version gate.
\end{enumerate}

The canonical V1 dispute is a stateful computation thread. Opening authenticates
the validation descriptor and transaction source against the challenged
\code{HeaderV1}; the thread datum then binds the challenged header hash,
operator verification key, current bisection interval, both trace roots, the
agreed lower state, and the response deadline. Operator midpoint moves require
the committed operator's signature and challenger moves require the fraud
prover's signature. Each move reproduces the same computation-thread NFT and
the uniquely derived next datum.

At an interval of one transition, L1 authenticates both claimed post-state
memberships and executes the validation-machine instruction from the agreed
pre-state. Only a challenger win may finalize the computation thread into a
fraud-proof token. Failure by the operator to make its required move before
the deadline also selects the challenger. Dispute version 1 fixes a
(300{,}000)-millisecond response window and 32 bisection rounds. The exact
canonical V1 block maturity is seven days ((604{,}800{,}000) milliseconds), while
the response schedule's derived minimum with a two-times reserve is
(39{,}600{,}000) milliseconds. Opening rejects a challenge begun too late to
finish before maturity. The deployment manifest must bind the exact dispute
validator, response schedule, and seven-day maturity; any mismatch is
unsupported.

Unknown or missing source fragments, languages, term tags, builtin tags,
purposes, versions, integrity hashes, cost-model digests, or machine
instructions fail closed. Canonical V1 must remain release-gated until all of the
conditions above have validator-hash-bound evidence.
