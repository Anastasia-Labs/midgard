\section{Transaction request (L2)}
\label{h:transaction-request}

A user's primary method of transacting on the Midgard ledger is to submit an L2 transaction directly to the current operator via a web-based API endpoint.
Operators are expected to serve such APIs in a publicly accessible and employ sufficient security techniques to mitigate denial-of-service.

Users' L2 transactions follow the data structure defined in \cref{h:midgard-transaction-types}.
In particular, users can freely set transaction time-validity intervals according to their preferences.
The original interval-overlap design permits inclusion when the transaction interval overlaps the block event interval.
Current transaction validation instead requires the selected \code{block\_slot} to lie inside the transaction interval, and the node derives that slot from the block end time.
This is a conformance difference, including the POSIX-versus-slot unit issue in \cref{h:deviations-from-cardano-transaction-types}; overlap alone is not sufficient for current admission.

Durable submission does not guarantee validation, inclusion, or confirmation.
A request can be rejected for ledger or execution rules, conflict with another request, outlive its validity interval, remain queued under capacity constraints, or be censored.
The L1 transaction-order mechanism supplies the separate forced-inclusion path while valid block production and the required challenge machinery remain available.
Current point-based validation also does not support the earlier claim that two disjoint transaction intervals can both be accepted solely because one block event interval overlaps each.
