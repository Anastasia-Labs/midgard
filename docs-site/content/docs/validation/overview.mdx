---
title: "Validation Engine Overview"
description: "The two-phase validation pipeline (Phase A structural/native checks, Phase B script/ledger evaluation) the Midgard node uses to admit queued L2 transactions."
---

When a Midgard node receives a queued L2 transaction, this pipeline decides
whether it may enter a block. **Phase A** is stateless and per-transaction: it
decodes the transaction, checks structural invariants, and verifies signatures
and native scripts. **Phase B** is dependency-aware and stateful: it orders
transactions by their input/output dependencies, applies each against a UTxO
state, evaluates Plutus and Midgard scripts locally, and enforces value
preservation. A transaction that fails either phase is rejected with a stable
code; one that passes both is admitted along with the UTxO changes it causes.

The pipeline lives in the `@al-ft/midgard-validation` package, the shared
validation surface a Midgard node runs at admission.

<Callout type="info">
This engine validates the *ledger* semantics of L2 transactions. It is the
off-chain counterpart to the protocol's on-chain rules, see
[Phase Two Validation](/docs/spec/phase-two-validation) in the specification for
how these checks relate to the fraud-proof settlement layer.
</Callout>

## Pipeline

<Mermaid chart={`flowchart TD
  Q[QueuedTx: txId, txCbor, arrivalSeq, createdAt] --> A[Phase A: runPhaseAValidation]
  A -->|decode + structural + signature checks| AR{per-tx valid?}
  AR -->|no| RJ1[RejectedTx: code + detail]
  AR -->|yes| PV[PhaseAValidatedTx: ledgerTx + graph + derived]
  PV --> B[Phase B: runPhaseBValidationWithPatch]
  B -->|dependency graph, conflict buckets| BO[ordered evaluation]
  BO -->|UTxO lookup, script eval, value preservation| BR{ledger valid?}
  BR -->|no| RJ2[RejectedTx + cascade to dependents]
  BR -->|yes| ACC[accepted + UTxOStatePatch]
`} />

## Package exports

The package exposes a public surface through `package.json` subpath exports and
re-exports everything from `src/index.ts`. The most important entry points:

| Export | Module | Purpose |
| --- | --- | --- |
| `./phase-a` | `phase-a.ts` | `runPhaseAValidation`, stateless per-tx validation. |
| `./phase-b` | `phase-b.ts` | `runPhaseBValidationWithPatch`, dependency-aware ledger validation. |
| `./ledger` | `ledger.ts` | `LedgerEntry` / `ProcessedTx` UTxO row model. |
| `./ledger-tx` | `ledger-tx/` | Semantic `MidgardLedgerTx` types and canonical CBOR codec. |
| `./local-script-eval` | `local-script-eval.ts` | Local UPLC evaluation via the Harmonic Labs machine. |
| `./script-context` | `script-context.ts` | Builds Plutus V3 / Midgard V1 script contexts. |
| `./script-source` | `script-source.ts` | Resolves inline and reference script sources. |
| `./midgard-redeemers` | `midgard-redeemers.ts` | Redeemer decoding and script-purpose data. |
| `./plutus-data` | `plutus-data.ts` | Plutus data to canonical CBOR hex conversion. |
| `./tx-out-ref` | `tx-out-ref.ts` | Transaction-input reference helpers. |
| `./types` | `types.ts` | Shared config, result, and `RejectCodes`. |

## Rejection codes

Both phases emit a canonical `RejectedTx` record, `{ txId, code, detail }`, using
the stable `RejectCodes` map in `types.ts`. The pipeline persists these codes for
observability and replay, so they change only when the corresponding rejection
semantics change. Codes range from
`E_CBOR_DESERIALIZATION` and `E_EMPTY_INPUTS` (Phase A) to `E_DOUBLE_SPEND`,
`E_DEPENDENCY_CYCLE`, and `E_VALUE_NOT_PRESERVED` (Phase B).
