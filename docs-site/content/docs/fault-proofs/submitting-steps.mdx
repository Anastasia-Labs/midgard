title: "Submitting Proof Workflows"
description: "Durable fraud-proof execution, retired manual routes, and the computation-thread lifecycle."
---

A supported fraud-proof workflow authenticates evidence, opens a computation
thread, advances its category-specific state machine, and reconciles each L1
submission. A successful thread can produce the permanent fraud-proof record
used for [structural correction](/docs/fault-proofs/removing-blocks).

## Runtime entry points

`workflow-readiness` reports the selected adapter's readiness. An adapter still
requires an admitted concrete runner; category presence does not prove a
particular deployment is ready.

`run-workflow` and `resume-workflow` require the same identity and infrastructure
inputs:

```text
midgard-fault-proofs run-workflow \
  --fraud-category <catalogue-category> \
  --deployment-fingerprint <32-byte-hex> \
  --header-hash <28-byte-hex> \
  --workflow-journal-dir <directory> \
  --workflow-runtime-config <infrastructure-config.json>
```

Use `resume-workflow` with the same persisted identity and journal after an
interruption. The runtime configuration must supply the accepted deployment,
public retained-DA/L1 authority, funding and signer infrastructure. Follow the
[challenger runbook](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/challenger-runbook.md)
for the full versioned configuration and readiness checks.

## Retired manual routes

The generic `submit-step-01` through `submit-step-04`, invalid-range,
zero-input, and non-existent-input file submitters are rejected by
`legacy-submission-boundary.ts`. `submit-init` is also rejected without a
category and for the categories listed in that boundary. The stable error is
`RF-043_LEGACY_SUBMISSION_RETIRED`, raised before provider or wallet access.

A name in CLI help or a historical JSON artifact is not evidence that the route
can submit. Other low-level routes, including transition-trace and validation
dispute operations, have their own authenticated inputs and category-specific
steps. Use their current help/schema together with the installed runner.

## Thread and proof lifecycle

The computation-thread token identifies a proof in progress. Successful
completion burns it and mints the permanent fraud-proof token; exceptional
cancellation burns the thread without creating successful proof evidence.
Validation disputes can require alternating signed moves, source verification,
one-step resolution, or timeout transitions rather than a fixed four-step
sequence.

A submitted hash is not confirmation. After an error or interruption, reconcile
the persisted intent, transaction status, and current thread UTxO before
retrying. A transport failure can occur after submission; blindly rebuilding
the same step is not a recovery procedure.

Once a successful fraud-proof record exists, correction must still complete
before the target leaves the removable queue state. Current deployment
acceptance is tracked by [Project Status](/docs/getting-started/status).
