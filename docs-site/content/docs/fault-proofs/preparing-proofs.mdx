---
title: "Preparing Fraud Proofs"
description: "Turn a Midgard block's transactions into the proof artifacts the submit steps consume, using the prepare-* commands."
---

The five `prepare-*` commands are the front of the fault-proof pipeline. They take
a Midgard block, find the transaction(s) that violate a ledger rule, build the
membership proofs against the block's transactions Merkle-Patricia Trie, and emit
the JSON artifacts that the `submit-*` commands later feed on-chain. They touch no
wallet and no L1 provider. They operate purely on transaction data.

Both commands take their input from **exactly one** source: a live node
(`--midgard-node-url`), a saved transactions file (`--transactions-file`), or, for double-spend only, a built-in `--sample-double-spend` fixture. Supplying zero
or more than one source is an error.

## `prepare-double-spend`

Finds two transactions in one block that spend the same input, then produces
per-transaction inclusion proofs and input CBOR lists. Source:
`demo/midgard-fault-proofs/src/prepare-double-spend.ts`.

```sh
midgard-fault-proofs prepare-double-spend \
  (--midgard-node-url <url> | --transactions-file <path> | --sample-double-spend) \
  --header-hash <hex> \
  [--expected-transactions-root <hex>] \
  [--tx1-id <hex> --tx2-id <hex>] \
  [--output-dir <path>] \
  [--allow-incompatible-output]
```

- `--header-hash` (required), the 28-byte block header hash the block is fetched
  or matched by.
- `--tx1-id` / `--tx2-id` (optional, must be given together), pin the exact
  double-spending pair. When omitted, `resolveDoubleSpendPair` scans the block for the
  first input spent by two distinct transactions.
- `--expected-transactions-root`: a 32-byte root to cross-check against the root
  the tool recomputes from the block's native transactions.
- `--output-dir`: when set, the artifacts are written to disk (see below);
  otherwise the full result is printed to stdout as JSON.

### What it computes

`decodeTransactionMaterial` decodes each transaction's canonical CBOR into a
native Midgard tx, recomputes and checks its node tx id, and extracts its spend
inputs. `buildTrieView` builds the block's transactions trie and produces a
membership proof for each of the two chosen transactions. The result records the
shared `doubleSpentInput`, each transaction's `doubleSpentInputIndex`, and a
`compatibility` block flagging whether the material can be used by the
`submit-step` commands.

<Callout type="warn" title="Compatibility gate">
  If `--expected-transactions-root` is supplied and does not match the root the
  tool recomputes, `compatibility.canUseSubmitStepCommands` is `false`. When
  writing files, the tool then **refuses** to emit submit-step material unless
  you pass `--allow-incompatible-output` (which writes them for diagnostics
  only).
</Callout>

### Files written with `--output-dir`

From `writePreparedFiles`:

| File                 | Consumed by                                                                                                                         |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `tx1-inclusion.json` | `submit-step-01` `--tx-inclusion`                                                                                                   |
| `tx2-inclusion.json` | `submit-step-02` `--tx-inclusion`                                                                                                   |
| `tx1-inputs.json`    | `submit-step-03` `--tx1-inputs`                                                                                                     |
| `tx2-inputs.json`    | `submit-step-04` `--tx2-inputs`                                                                                                     |
| `plan.json`          | Human-readable summary: header hash, double-spent input, both node tx ids, both input indices, compatibility, commitment encodings. |

With `--sample-double-spend` and `--output-dir`, an extra
`block-transactions.json` is written from `makeSampleDoubleSpendTransactions`, a
three-transaction fixture where `tx1` and `tx2` share input `1111…#7`. This is the
quickest way to see the artifact shape without a running node.

## `prepare-invalid-range`

Finds a transaction whose validity range violates the block's declared validity
window. Source: `demo/midgard-fault-proofs/src/prepare-invalid-range.ts`.

```sh
midgard-fault-proofs prepare-invalid-range \
  (--midgard-node-url <url> | --transactions-file <path>) \
  --header-hash <hex> \
  --block-valid-from <posixMs> \
  --block-valid-to <posixMs> \
  [--expected-transactions-root <hex>] \
  [--tx-id <hex>] \
  [--output-dir <path>] \
  [--allow-incompatible-output]
```

- `--block-valid-from` / `--block-valid-to` (both required), the block's declared
  validity window in POSIX milliseconds. `--block-valid-from` must be `<=`
  `--block-valid-to`.
- `--tx-id` (optional), pin a specific transaction. When omitted, the tool selects the
  first violating transaction in the block.

For each transaction, `normalizeNativeTxValidityRange` normalizes its validity
interval and `invalidRangeViolationReason` decides whether it falls outside the
block window. The selected transaction is emitted with its
`normalizedValidityRange` and a machine-readable `violationReason`.

### Files written with `--output-dir`

| File                | Consumed by                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `tx-inclusion.json` | `submit-invalid-range-step-01` `--tx-inclusion`                                                                                   |
| `plan.json`         | Summary: header hash, block validity window, node tx id, normalized range, violation reason, compatibility, commitment encodings. |

The same compatibility gate and `--allow-incompatible-output` override apply.

## `prepare-non-existent-input`

Targets a transaction that spends an input which does not exist: the input is
absent from the previous ledger state and is not produced by any transaction in
the same block. Source: `demo/midgard-fault-proofs/src/prepare-non-existent-input.ts`.

```sh
midgard-fault-proofs prepare-non-existent-input \
  (--midgard-node-url <url> | --transactions-file <path>) \
  --header-hash <hex> \
  [--bad-tx-id <hex>] \
  [--bad-input-index <n>] \
  [--prev-utxos-root <hex>] \
  [--prev-block-payload-file <path>] \
  [--expected-transactions-root <hex>] \
  [--output-dir <path>]
```

- `--bad-tx-id`: the transaction that spends the non-existent input. Optional only
  when the block holds a single transaction; for a multi-transaction block the tool
  errors rather than guessing.
- `--bad-input-index` (optional, defaults to `0`), which of that transaction's
  inputs is claimed non-existent.
- `--prev-utxos-root` (optional, defaults to the empty-trie root), the previous
  ledger's UTxO root that the ledger non-membership proof is built against.
- `--prev-block-payload-file` (optional), a saved previous-block payload used to
  reconstruct the prior ledger entries.
- `--expected-transactions-root`: a 32-byte root to cross-check against the root
  the tool recomputes from the block's native transactions.

The tool builds one membership proof and two non-membership proofs: the offending
transaction's inclusion in the block's transactions trie, the missing input's
absence from the previous ledger state, and its absence from the outputs created
within the block itself.

### Files written with `--output-dir`

| File                            | Consumed by                                                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `ne-tx-inclusion.json`          | `submit-non-existent-input-step-01` `--tx-inclusion`                                                              |
| `ne-inputs-preimage.json`       | `submit-non-existent-input-step-02` `--inputs-preimage`                                                           |
| `ne-ledger-non-membership.json` | `submit-non-existent-input-step-03` `--ledger-non-membership-proof`                                               |
| `ne-txs-non-membership.json`    | `submit-non-existent-input-step-04` `--txs-non-membership-proof`                                                  |
| `ne-plan.json`                  | Summary: header hash, bad tx id and input index, the missing input, and the transactions and previous-UTxO roots. |

Unlike double-spend and invalid-range preparation, there is no compatibility
override: on a root mismatch the command fails instead of writing
diagnostics-only material.

## `prepare-no-reference-input`

The reference-input mirror of `prepare-non-existent-input`: it targets a
transaction that *reads* a reference input which is absent from the previous
ledger state and is not produced by any transaction in the same block. Source:
`demo/midgard-fault-proofs/src/prepare-no-reference-input.ts`.

```sh
midgard-fault-proofs prepare-no-reference-input \
  (--midgard-node-url <url> | --transactions-file <path>) \
  --header-hash <hex> \
  [--bad-tx-id <hex>] \
  [--bad-reference-input-index <n>] \
  [--prev-utxos-root <hex>] \
  [--prev-block-payload-file <path>] \
  [--expected-transactions-root <hex>] \
  [--output-dir <path>]
```

The flags carry the same meaning as the non-existent-input ones, with
`--bad-reference-input-index` (optional, defaults to `0`) selecting which of the
transaction's **reference** inputs is claimed missing. A transaction that reads
no reference inputs at all is rejected as out of bounds.

The proof shape is identical too, one membership proof and two non-membership
proofs, because the missing reference input is keyed exactly like a spend input:
by the node's `TransactionInput` CBOR in the ledger trie, and by the raw 32-byte
producing tx id in the block's transactions trie.

### Files written with `--output-dir`

| File                                    | Consumed by                                                                                                                 |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `nri-tx-inclusion.json`                 | `submit-no-reference-input-step-01` `--tx-inclusion`                                                                        |
| `nri-reference-inputs-preimage.json`    | `submit-no-reference-input-step-02` `--reference-inputs-preimage`                                                           |
| `nri-ledger-non-membership.json`        | `submit-no-reference-input-step-03` `--ledger-non-membership-proof`                                                         |
| `nri-txs-non-membership.json`           | `submit-no-reference-input-step-04` `--txs-non-membership-proof`                                                            |
| `nri-plan.json`                         | Summary: header hash, bad tx id and reference-input index, the missing reference input, and the transactions and previous-UTxO roots. |

As with non-existent-input, there is no compatibility override: a root mismatch
fails the command.

## `prepare-zero-input`

Finds a transaction whose native body commits an empty spend-input list and
produces the transaction inclusion proof consumed by the two zero-input proof
steps. Source: `demo/midgard-fault-proofs/src/prepare-zero-input.ts`.

```sh
midgard-fault-proofs prepare-zero-input \
  (--midgard-node-url <url> | --transactions-file <path>) \
  --header-hash <hex> \
  --expected-transactions-root <hex> \
  [--tx-id <hex>] \
  [--output-dir <path>]
```

- `--tx-id` optionally pins the exact zero-input transaction. Without it, the
  first violating transaction is selected. A pinned transaction that has one or
  more spend inputs is rejected.
- `--expected-transactions-root` is required. It is the 32-byte **counted,
  domain-separated**
  transactions root committed by the state-queue block header. It is not the raw
  PHAS root carried in the membership proof.

The output exposes both commitments explicitly:

- `transactionsPhasRoot` is the raw MPF root opened by
  `tx-inclusion.json` and passed to step 01.
- `committedTransactionsRoot` is
  `commit_counted_root(TransactionsRootDomain, transactionsPhasRoot, txCount)`
  and must equal the selected header's `transactions_root`.

The root check is mandatory and strict. A missing expected root, raw PHAS root,
stale counted root, or root from a different block aborts preparation before any
submit-step files are written.

### Files written with `--output-dir`

| File                | Consumed by                                                                                                                                         |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tx-inclusion.json` | `submit-zero-input-step-01` `--tx-inclusion`                                                                                                        |
| `plan.json`         | Summary: header hash, zero-input tx id, spend-inputs hash, raw transactions PHAS root, counted header commitment, and required expected-root check. |

`prepare-*` only builds inputs, it never touches L1. The next stage takes these
files and drives them through the on-chain computation thread.
