Proof preparation must bind exact transaction and ledger evidence to an
authenticated L1 header. Operator REST data, local transaction lists, or sample
fixtures do not become authoritative because a caller labels them trusted.

## Current CLI boundary

The executable retains names such as `prepare-double-spend`,
`prepare-invalid-range`, `prepare-non-existent-input`, `prepare-input-no-idx`,
and `prepare-zero-input`, but their old `--midgard-node-url`,
`--transactions-file`, and `--sample-double-spend` routes are diagnostic inputs
and are rejected before proof construction. They are not working preparation
recipes. `--allow-incompatible-output` does not bypass this boundary.

The separate module files retain historical artifact builders; source presence
is not an authenticated executable route. Current usage comments mention
`executeCanonicalPrepareCommandV1`, but that name is not an exported callable
implementation in this checkout. Use the installed workflow surfaces described
in the [challenger runbook](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/challenger-runbook.md).

## Retained-DA transition preparation

`prepare-transition-trace` has a dedicated path before the generic preparation
rejection gate. It reads a retained DA envelope and authenticates its bytes by
reconstructing the caller-pinned header hash:

```text
midgard-fault-proofs prepare-transition-trace \
  --da-payload-envelope <retained-envelope.cbor-or-json> \
  --header-hash <authenticated-28-byte-header-hash> \
  --output-dir <artifact-directory>
```

Obtain the envelope through the public retained-DA transport and authenticate
the selected header through L1. This command does not independently establish
L1 provenance for a hash supplied by the caller.

It writes `plan.json` and `proof-<index>-<kind>.cbor` files for buildable
header-derived detections. Despite the `.cbor` suffix, those proof files contain
hexadecimal CBOR text. `plan.json` contains detections, buildability, and reasons
that additional evidence is required. An empty proof list does not establish
that every ledger transition is valid.

Retained DA alone cannot supply all inputs for omitted/out-of-window L1 event
proofs, accepted-transaction transition mismatches, or arbitrary one-step ledger
mutation proofs. The preparer reports these as guidance requiring authenticated
L1 event references, validation evidence, or predecessor-ledger witnesses.

## From evidence to a workflow

A durable runner must authenticate its deployment, evidence, funding, and
reference scripts before submitting any stage. See
[Submitting proof steps](/docs/fault-proofs/submitting-steps) and the
[catalogue status](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/catalogue-status.md)
for installation and acceptance boundaries.
