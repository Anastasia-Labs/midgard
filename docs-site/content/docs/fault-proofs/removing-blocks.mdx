---
title: "Removing Fraudulent Blocks"
description: "Removing a proven-fraudulent block from the state queue, who may do it, when it is allowed, and how to inspect a deployment before starting a proof."
---

After a computation thread succeeds and mints a `fraud_proof` token, a separate
correction workflow must remove the offending block and apply the required
slashing/reward transitions. Minting the proof does not perform removal.

## When removal is allowed

Removal requires a `fraud_proof` token for the target block. The token sits in the permanent, unspendable fraud-proof record and is
authenticated as a reference input; it is not spent from the watcher's wallet. The block must still be **in the state queue**: a block that
has already merged into confirmed state cannot be removed this way, which is why the
challenge window exists.

Correction removes successors through separate confirmed transactions,
refetching queue topology after each, then removes the target. Slashing can
occur during descendant pruning; the protocol prevents applying the same
operator slash repeatedly.

## Commands

- **`remove-fraudulent-block`**: removes a proven-fraudulent block from the state queue
  and slashes the operator's bond. Requires the
  [computation thread](/docs/onchain/fraud-proof-machines) to have concluded and the
  `fraud_proof` token to exist.
- **`inspect-contracts`**: resolves a blueprint and deployment against the fraud-proof
  catalogue and reports policy IDs, addresses, step hashes, and init-readiness.
  Read-only. Run it before initializing a thread, not only when removing.

<Callout type="error" title="Terminal on-chain action">
  Removal is the terminal, state-changing outcome of the fraud-proof process,
  and it settles on Cardano L1. It removes an on-chain header and slashes a
  bond. It does not delete any local node state.
</Callout>

<Callout type="warn" title="Removal races other state-queue mutations">
  Removing a header mutates the state queue, which operators' commitment and
  merge transactions also mutate. Removal does not coordinate with any Midgard
  node. For a non-tail target, the command requires `--await-confirmation`: each
  successor removal is confirmed and the state-queue topology refetched before
  the next one. A removal that loses a race to a competing commit or merge
  fails; a bare CLI run must be re-run, while the watcher's workflow
  orchestrator retries it from the fresh L1 view until it is confirmed.
</Callout>
