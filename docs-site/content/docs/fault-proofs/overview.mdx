Midgard is an **optimistic rollup**: block producers post compact block headers to
Cardano L1, and those blocks are assumed valid unless someone proves otherwise.
The mechanism that makes "otherwise" enforceable is the **fraud proof**, an on-chain
procedure that demonstrates a committed block violated Midgard's ledger rules, letting
the block be removed and its operator's bond slashed. A block can be challenged while it
is queued, before it merges into confirmed state.

The `@al-ft/midgard-fault-proofs` package exposes low-level proof commands and
durable workflow execution through `midgard-fault-proofs`. The independent
watcher uses its workflow layer for supported installed categories.

The protocol concept is a **fraud proof**. The package, its binary, and its commands say
**fault proof**. Both names refer to the same thing: the tooling and watcher design
adopted `fault proof`, while the deployed contracts and the protocol specification say
`fraud proof`.

<Callout type="info" title="Where this fits">
  This tooling is the challenge side of the optimistic model. The watchers that
  detect fraud are documented under [Watchers &amp; Data
  Availability](/docs/watchers/concept); the on-chain validators these commands
  drive are the fraud-proof machines described in [On-chain: Fraud-Proof
  Machines](/docs/onchain/fraud-proof-machines). For the protocol-level design,
  see [Protocol Spec](/docs/fault-proofs/protocol-spec).
</Callout>

## How the CLI dispatches commands

`src/bin.ts` is the entrypoint. It reads `process.argv`, takes the first token as
the **command**, and parses the rest as `--flag value` pairs into a single
`ParsedArgs` record (an unknown flag throws `Unknown argument: <arg>`). `main()`
then validates the command against a fixed allow-list and calls the matching
module function, writing the result to stdout as JSON. Passing `--help` or `-h`
prints the usage block and exits.

The current command inventory lives in the `usage` template and dispatch
branches in `bin.ts`. Help includes retired names so they can fail with a
specific explanation; it is not a list of executable authenticated workflows.
For example, `submit-input-no-idx-fold` is retired, and several older file-based
step/init routes fail through `legacy-submission-boundary.ts`.

The main operational groups are:

| Group                   | Surface                                                 | Boundary                                                              |
| ----------------------- | ------------------------------------------------------- | --------------------------------------------------------------------- |
| Readiness and recovery  | `workflow-readiness`, `run-workflow`, `resume-workflow` | Requires an admitted runner and deployment-bound infrastructure.      |
| Retained-DA preparation | `prepare-transition-trace`                              | Reconstructs a pinned header and records which evidence is buildable. |
| Deployment inspection   | `inspect-contracts`                                     | Reads the blueprint and deployment; does not submit.                  |
| Category steps          | Supported `submit-*` routes                             | Each has its own evidence, thread, and reference-script requirements. |
| Correction              | `remove-fraudulent-block`, `remove-unattested-block`    | Distinct proof-backed and attestation-timeout state transitions.      |

The older REST/file/sample preparation routes are rejected by the executable.
See [Preparing evidence](/docs/fault-proofs/preparing-proofs) and
[Submitting workflows](/docs/fault-proofs/submitting-steps) before using a
historical command example.

## Category and workflow authority

`--fraud-category` is parsed from the SDK's
`FRAUD_PROOF_CATALOGUE_CATEGORY_ORDER`, rather than a separate CLI allowlist.
A parsed category, an installed watcher runner, and deployment acceptance are
separate checks. Use the maintained
[catalogue status](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/catalogue-status.md)
for that distinction and the
[challenger runbook](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/challenger-runbook.md)
for workflow operation.

`workflow-readiness`, `run-workflow`, and `resume-workflow` expose the durable
workflow lifecycle. The low-level step commands remain useful for individual
proof stages; they are not an exhaustive inventory of installed workflows.
Category-specific state machines and their token lifecycles are described by
the [Protocol Spec](/docs/fault-proofs/protocol-spec) and the current catalogue.

## Providers, wallets, and networks

Supported low-level submit/remove commands use the L1 wiring in `src/runtime.ts`
(whereas workflow commands load their versioned infrastructure configuration):

- **Provider**: `--provider Blockfrost` (default) or `--provider Kupmios`.
  Blockfrost needs `--blockfrost-api-url` / `--blockfrost-key` (or the
  `L1_BLOCKFROST_API_URL` / `L1_BLOCKFROST_KEY` env vars); Kupmios needs
  `--kupo-url` / `--ogmios-url`.
- **Network**: `--network Mainnet|Preview|Preprod` (parsed by `parseNetwork`).
- **Prover wallet**: one of `--wallet-seed-phrase`, `--wallet-seed-phrase-env`,
  `--wallet-private-key`, or `--wallet-private-key-env`. With none supplied,
  `resolveProverSigner` falls back to the `USER_WALLET` seed-phrase env var.
- **Contracts**: supported low-level submission and inspection routes require
  `--blueprint <path>` and `--deployment-info <path>`. Workflow and retained-DA
  preparation commands have different inputs; use their current schemas.

<Callout type="warn" title="Manual tooling">
  These commands submit real L1 transactions and sign with a real wallet. They
  include low-level building blocks as well as workflow commands. Run
  `inspect-contracts` first to confirm your blueprint and deployment agree
  before initializing a thread.
</Callout>
