An operator runs the off-chain machinery that keeps a Midgard L2 deployment
progressing: it serves the HTTP API, validates and enqueues L2 transactions,
maintains PostgreSQL-backed views and LevelDB Merkle Patricia Forestry (MPF)
state, and runs the background fibers that commit block headers to L1, confirm
those commitments, and merge matured blocks into confirmed state.

## What operating a deployment involves

`demo/midgard-node` is the demo off-chain runtime that ties the protocol
together. A running node is responsible for:

- serving the HTTP API used by wallets, tests, and local tooling,
- validating and enqueuing submitted Midgard-native transactions,
- maintaining PostgreSQL-backed views of mempool, latest-ledger, immutable
  history, and auxiliary indexes,
- maintaining LevelDB-backed Merkle Patricia Forestry state for ledger and
  transaction roots,
- running background fibers that monitor mempool state, commit blocks, confirm
  block commitments, merge confirmed state, fetch deposit and withdrawal UTxOs,
  and sweep old retention data.

Operating a deployment is therefore more than "start the server": it includes a
one-time deployment flow (preparing a hub-oracle nonce, publishing reference
scripts, initializing protocol state), ongoing operator lifecycle actions
(registering and activating an operator), and recovery procedures for
interrupted flows.

## The production-grade L2 posture

Midgard is intended to be a production-grade L2. Interpret operational decisions,
configuration, recovery, benchmarking, and state resets through that lens. The
repository codifies a strict decision standard.

<Callout type="warn" title="Priority order when tradeoffs are required">
When operational tradeoffs are unavoidable, prioritize in this exact order:

1. **Correctness**
2. **Safety**
3. **Liveness**
4. **Performance**
5. **Convenience**

A change that improves benchmarks but weakens a production guarantee must never
become the default. Keep strict behavior as the default and isolate any
non-production behavior behind clearly named controls.
</Callout>

Operators should prefer options that maximize protocol correctness and state
integrity, safety under adversarial conditions, determinism and
reproducibility, operational reliability and failure recovery, auditability and
clear observability, and explicit, auditable migrations and configuration.

### Three rules that constrain operations

These rules are load-bearing for anyone running a node against real or
persistent Cardano state. Each has its own reference in the
[compatibility rules](/docs/operators/node/compatibility-rules) page.
