Deposits and withdrawals are the bridge between Cardano L1 and the Midgard L2
ledger, implementing the [User-Event Protocol](/docs/spec/user-event-protocol).

<Mermaid
  chart={`

  U([User]) -->|L1 deposit submission| D[L1 deposit UTxO]
  D -->|visible and inclusion time due| P[Local projected output]
  P -->|deposit block confirmed| L[Spendable L2 ledger]
  D -->|deposit event settled and absorbed| R[(L1 reserve)]
  L -->|signed withdrawal order| W[L1 withdrawal order]
  W -->|valid event settled| A[Payout accumulator]
  R -->|fund| A
  A -->|conclude payout| U
`}

## Actors

<ActorCard actor="user" name="Depositor">
  Locks funds at the L1 deposit validator and later redeems them via a
  withdrawal order. The HTTP deposit builder needs no depositor signing key: it
  returns an unsigned transaction for external signing. The CLI submission
  command instead uses the user wallet selected explicitly for that command.
</ActorCard>

<ActorCard actor="operator">
  Reconciles visible L1 deposits and projects due events into the local ledger
  and processes withdrawal payouts from the reserve.
</ActorCard>

## Deposits

<InvariantBox>
  The reserve is on Cardano L1. Absorption requires a settled deposit event and
  its authenticated settlement proof. Local projection is provisional: the
  output remains hidden from spendable queries until confirmation assigns its
  block header, and recovery can invalidate the matching assignment.
</InvariantBox>

| Command                               | Effect                                                                                                                  |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `submit-deposit`                      | Builds and submits the L1 deposit transaction. Funds move to the deposit validator.                                     |
| `project-deposits-once`               | Projects due deposits into the local mempool ledger; their spendability also requires confirmed-header assignment.      |
| `reconcile deposit-projected`         | Inspects visibility/projection; `--repair` fetches visible deposits and projects due events.                            |
| `absorb-confirmed-deposit-to-reserve` | Moves a settled deposit's funds into the L1 protocol reserve using its settlement proof.                                |
| `reconcile-deposit-submission`        | Checks a persisted deposit submission against provider evidence before retry; unresolved observations remain ambiguous. |

Submission, due-time projection, confirmed-header assignment and settlement are
separate milestones. Inspect inclusion time and the projected header when a
deposit appears stuck. The acceptance flow waits for the deposit block to merge
before spending it. Within one block, deposits execute after L2 transactions,
so a transaction cannot spend that block's newly introduced deposit.

## Withdrawals

<RiskCallout level="high" title="Irreversible payout">
  Reserve payouts settle on L1 and cannot be reversed. Verify the withdrawal
  order and reserve balance before submitting a payout.
</RiskCallout>

| Command                  | Effect                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------- |
| `submit-withdrawal`      | Builds and submits the L1 withdrawal order. Starts the withdrawal, does not pay it out. |
| `fetch-withdrawals-once` | Reads pending L1 withdrawal orders and records them locally, so they can be classified. |
| `withdrawal-status`      | Reports the order's classification and payout progress. Read-only.                      |

A withdrawal order is classified before it is paid. An order can be found invalid, for
example `NonExistentWithdrawalUtxo` or `IncorrectWithdrawalOwner`. Payment happens
separately, through [reserve and payout](/docs/operators/node/reserve-payout).

Deposit fetching/projection and withdrawal fetching also run continuously in
the [background fibers](/docs/operators/node/background-fibers). Their relevant
one-shot commands can inspect or advance the same stages.
