The end-to-end (E2E) acceptance flow verifies that a change has not broken the real
Midgard operator path: it drives a full deployment through deposit, L2 transfers,
block commit, data-availability attestation, and merge, then checks health, database
state, balances, and logs.

<Callout type="warn" title="Advanced acceptance path">
  This is the operator acceptance overview, not a user quickstart. A clean
  public-testnet acceptance gate is still a [project
  blocker](/docs/getting-started/status), so treat a green run as the current
  baseline evidence, not completion of the full acceptance contract.
</Callout>

## The step wrappers

Three `midgard-node-tools` commands structure the run so every step produces a
durable, machine-readable summary:

- **`e2e-run-step`**: wraps a one-shot command, capturing a raw log and a JSON step
  summary. Flags: `--id`, `--cwd`, `--raw-log`, `--summary-out`, `--timeout-ms`,
  then `--` followed by the wrapped command.
- **`e2e-start-service`**: starts a long-running service (the node or the DA committee
  node) and waits on its readiness URL. Flags include `--service`, `--ready-url`,
  `--health-url`, `--pid-file`, `--ready-timeout-ms`, `--poll-interval-ms`.
- **`e2e-finalize-summary`**: aggregates the step summaries, transaction hashes, and
  the node log into `logs/$RUN_ID/summary.json` and `summary.md` with a verdict.

## Prerequisites

The current consensus profile has no accepted release-evidence digest. Both the
committee and public retained-DA reader enforce release readiness at startup, so
this acceptance sequence is currently blocked at that prerequisite. Verify the
compiled profile before submitting deployment transactions; do not bypass the
assertion to manufacture acceptance evidence.

## Choose a run mode

Pick a mode before any state-changing command:

| Mode                              | When                                                                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **Fresh deployment**              | Starting a new acceptance identity on purpose (fresh one-shot, fresh reference scripts, fresh `init`, matching local state reset). |
| **Attach / resume**               | A complete deployment already exists; run or continue it. Do **not** run `init`; start via `listen` / Docker.                      |
| **Continue interrupted pre-init** | A fresh deployment failed before `init`; resume only within the same documented identity.                                          |
| **Diagnose post-init**            | `init` or a later step may have succeeded; reconcile chain/DB/run-state before acting.                                             |
| **Fresh redeploy recovery**       | Required only by the [state-reset rules](/docs/operators/node/compatibility-rules).                                                |

<Callout type="warn" title="Do not fresh-redeploy on every failure">
  Provider, wallet, DA, projection, scheduler, and merge failures are gates to
  fix or wait through, not redeploy triggers. Never combine clean local
  databases with an old on-chain manifest or an old hub-oracle one-shot outref.
</Callout>

## The fresh-run sequence

<Mermaid

  B --> C["patch .env, reset local state"]
  C --> D["publish node-runtime reference scripts"]

  E --> F["register + activate operator"]
  F --> G["start DA committee, independent retained reader, producer preflight"]

  J --> K["poll /tx-status until committed"]

  Q --> N["e2e-finalize-summary"]`}

Each state-changing step is wrapped in `e2e-run-step`. From
`demo/midgard-node`, protocol init uses:

```bash
TOOLS_CLI=../midgard-node-tools/dist/index.js
RUN_ID="e2e-run-$(date -u +%Y%m%dT%H%M%SZ)"
E2E_STEP_DIR="logs/$RUN_ID/steps"
mkdir -p "$E2E_STEP_DIR"

node "$TOOLS_CLI" e2e-run-step \
  --id init-protocol \
  --cwd "$(pwd)" \
  --raw-log "logs/$RUN_ID/init.log" \
  --summary-out "$E2E_STEP_DIR/init.json" \
  --timeout-ms 1200000 \
  -- \
  node dist/index.js init \
  --contract-deployment-info-output deploymentInfo/contract-deployment-info.json
```

Configure the DA writer and the separate SELECT-only public retained-DA process
using the [DA committee guide](/docs/watchers/da-committee-node). Acceptance
requires PostgreSQL-backed storage, a distinct public-reader identity and
credentials, and a manifest-bound public retrieval probe. The public libp2p
listener has no HTTP readiness endpoint.

The committee service (from `demo/da-committee-node`) must also be ready on
its configured `/readyz` before L2 activity. This abbreviated command assumes
those role-specific environments and manifests are already prepared:

```bash
DA_NODE_DIR="$(cd ../da-committee-node && pwd)"
node "$TOOLS_CLI" e2e-start-service \
  --service da-committee-node \
  --cwd "$DA_NODE_DIR" \
  --ready-url http://127.0.0.1:8787/readyz \
  --health-url http://127.0.0.1:8787/healthz \
  --pid-file "$DA_NODE_DIR/run/e2e-watcher.pid" \
  --ready-timeout-ms 180000 \
  -- pnpm start
```

<Callout type="info" title="Key rules baked into the flow">
  Keep `RUN_GENESIS_ON_STARTUP=false` and run protocol init explicitly. Use a
  fresh, funded operator-wallet UTxO for the hub-oracle one-shot. Host DB-backed
  commands need `POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=5433`; `/tx-status` takes
  `tx_hash`. Do not use `attest-state-queue-once` as the acceptance path; the DA
  committee must sign, submit, and apply the attestation. Every command used in
  this flow is documented in the [CLI
  reference](/docs/operators/node/cli-reference).
</Callout>

## What a green run proves

The baseline sequence exercises a deposit, two L2 transfers, DA attestation,
automatic merge, and final balances. Wait for the deposit block to settle before
spending its output: deposits execute after transactions within a block.

The finalizer's full acceptance contract additionally requires independent
state-correction, exact economics, withdrawal/reserve/payout, both forced
classification directions, crash/rollback, and availability-capability evidence.
Missing adapters or evidence keep those gates blocked. Baseline success alone
cannot produce full release acceptance; see [fault-proof workflows](/docs/fault-proofs/overview)
and [release status](/docs/getting-started/status).

## Artifacts

Use a unique run directory such as `logs/$RUN_ID/` and retain:

- `steps/*.json`: one structured summary per `e2e-run-step` (with `observedTxHashes`).
- per-step raw logs at their explicit `--raw-log` paths and the complete node log
  for the acceptance window.
- `deployment-run-state.json`: the run-state used across nonce and reference-script
  publication.
- `summary.json` and `summary.md`: the finalized dashboard from
  `e2e-finalize-summary`.

## Pass criteria

`e2e-finalize-summary` must report `functionalVerdict`, `cleanRunVerdict`, and
`verdict` as `success`, with `nextSafeAction: none_run_complete`. The full
state-correction and recovery gates above must pass, alongside:

- one consumed deposit and two accepted L2 admissions;
- `/healthz` healthy and `/readyz` ready with no readiness reasons;
- both L2 transaction statuses are `committed`, with balances reflecting the transfers;
- `pending_block_finalizations` finalized; `mempool`, `processed_mempool`, `blocks`,
  and unfinished local mutation jobs all zero after merges;
- `immutable` and `confirmed_ledger` contain the merged results;
- `stateQueue.headers` is empty after the final merge;
- the final log scan shows no unexplained error, failure, abandon, or crash entries.

## Common failure modes

Classify a blocker and take the safe next action rather than resubmitting blindly:

| Blocker                              | Safe next action                                                                                               |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| Local Kupmios unhealthy              | Run `l1-provider-preflight --json`; fix local Kupo/Ogmios/Cardano-node. Do not switch to a remote provider.    |
| Fresh one-shot mismatch              | Stop. Attach/resume if already initialized; otherwise restart fresh with a new one-shot and matching manifest. |
| Operator registered but not active   | Reconcile operator lifecycle; use activate-only recovery only when chain state proves registration exists.     |
| Deposit not projected                | Check `deposits_utxos.inclusion_time`; wait until due, then run `project-deposits-once`.                       |
| DA node not ready before L2 activity | Stop before transfers. Fix DA wallet/config/provider and restart the DA node.                                  |
| DA payload conflict or root mismatch | Stop. Do not merge. Diagnose payload construction and the endpoint set.                                        |
| DA signatures below threshold        | Start enough DA signer instances or fix peer propagation. Do not lower the threshold.                          |
| Merge skipped by state-queue lease   | Inspect `/stateQueueMutationLease` and unfinished mutation jobs; wait or repair the real stuck job.            |

Before repeating a submitted milestone, use the relevant `reconcile` command
with `--json` and resolve ambiguous transaction observations. Use `--repair`
only when that result explicitly supports it. Acceptance requires automatic
merge; `reconcile merge-complete --repair` cannot establish that evidence.
