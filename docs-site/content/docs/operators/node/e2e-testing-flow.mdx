The end-to-end (E2E) acceptance flow verifies that a change has not broken the real
Midgard operator path. One command, `e2e-stack` in `midgard-node-tools`, deploys
or resumes a Cardano Preprod deployment with local providers, starts the node, DA
committee, public retained DA and watcher, and runs wallet journeys: deposit,
L2 transfer, automatic merge and finality, withdrawal and automatic payout.

<Callout type="warn" title="Advanced acceptance path">
  This is the operator acceptance overview, not a user quickstart. A clean
  public-testnet acceptance gate is still a [project
  blocker](/docs/getting-started/status): a green run proves the functional
  path, not the full release-readiness contract.
</Callout>

## Prerequisites

<Steps>
  <Step>
    **Toolchain**: the workspace dependencies installed with `pnpm` (see [Local
    Dev](/docs/getting-started/local-dev)), Node 22.16 or newer, the pinned
    Aiken compiler, Docker Compose 2.21 or newer, Go, Rust/Cargo and Linux
    `flock`. The command builds the contracts, runtimes and images itself.
  </Step>
  <Step>
    **L1 backend**: a local Cardano node, see [Running the L1
    Backend](/docs/getting-started/l1-backend). Every role reads and submits
    through its socket.
  </Step>
  <Step>
    **Configuration**: a stack configuration JSON copied from
    `demo/midgard-node-tools/config/preprod-stack.example.json`, naming (never
    holding) the wallet, DA and transport secrets in the node `.env`. The full
    specification is `demo/midgard-node-tools/docs/PREPROD_STACK.md`.
  </Step>
  <Step>
    **Local feedback gate**: for transaction-preparation changes, run the lower
    layers first.
  </Step>
</Steps>

```bash
cd demo
pnpm run test:tx-prep:sdk
pnpm run test:tx-prep:node
pnpm run test:tx-prep:emulator
```

## Run it

From the repository root, check the configuration offline, then run:

```bash
pnpm --dir demo/midgard-node-tools run e2e-stack --config /absolute/path/stack.json --check
pnpm --dir demo/midgard-node-tools run e2e-stack --config /absolute/path/stack.json
```

`--check` starts nothing and spends nothing. `--setup-only` stops after setup
and readiness, leaving the services running. The same command, with the same
configuration, attaches to a complete deployment or resumes an interrupted one:
every confirmed step is reconciled against Cardano and the saved records, never
repeated. A fresh deployment needs fresh local storage; run it from a separate
linked worktree rather than deleting volumes.

## What the run does

<Mermaid
  chart={`flowchart TD
  A["prerequisites: builds"] --> B["providers: Cardano node, Postgres"]
  B --> C["storage and wallet checks"]
  C --> D["hub-oracle one-shot nonce"]
  D --> E["node-runtime reference scripts"]
  E --> F["db:migrate + init, verified manifest"]
  F --> G["register + activate operator"]
  G --> H["generate DA, retained DA and watcher services"]
  H --> I["DA committee ready, producer DA preflight, node + watcher ready"]
  I --> J["per cycle: deposit absorbed, exact L2 credit"]
  J --> K["transfer committed, payload read over public DA, finalized"]
  K --> L["withdrawal, automatic payout to the exact destination"]`}
/>

The node merges through its automatic merge worker; no manual `/commit`,
`/merge` or repair command is used. Every command the run executes is saved
with its raw log and structured summary, and every transaction intent is saved
before it is first submitted.

## Pass criteria

A run passes when the command exits 0 and:

- `journey-summary.json` in the run directory reports `wallet-journey-complete`
  with the configured number of cycles, and every step in `stack-journal.json`
  is complete;
- each cycle shows the exact L2 credit and debit including fees, a committed
  transfer whose payload was retrieved over public libp2p DA, confirmed-ledger
  finality, and the exact L1 payout destination and value; and
- the node's `/readyz` has no reasons, automatic settlement is healthy, the
  watcher is live and ready, and every DA committee member is ready.

## What a green run does not prove

The release-readiness gates (every launch-scope fault-proof family, exact slash
and reward economics, the reserve and payout sequence, both forced-classification
directions, and the crash/rollback matrix) need evidence this run does not
produce. See [fault-proof workflows](/docs/fault-proofs/overview) and
[release status](/docs/getting-started/status).

## When the run stops

The run stops with a message rather than guessing. It never repeats an
ambiguous submission, never builds a second hub-oracle nonce, and refuses a
changed deployment identity or mismatched local storage. Read the message, fix
the cause (funding, configuration, a provider, or simply waiting for Cardano),
and rerun the same command. Do not wipe the run directory, volumes or local
databases, and do not run deployment or wallet commands by hand around it.
