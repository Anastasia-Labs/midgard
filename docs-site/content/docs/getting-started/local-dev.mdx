This page lists the toolchain and the commands used to work on Midgard.

## Getting the code

All instructions in this documentation assume a local checkout of the Midgard
monorepo:

```sh
git clone https://github.com/Anastasia-Labs/midgard.git
cd midgard
```

Have these installed before you start:

- **Git** and a **POSIX shell**.
- **Node.js 22.16 or later** and **pnpm** (the workspace pins `pnpm@9.15.4`, see
  below), for the TypeScript packages.
- **Docker with the Compose v2 plugin**, for the
  [L1 backend](/docs/getting-started/l1-backend) and the node images.
- **[Aiken](https://aiken-lang.org/)**, only if you build the on-chain code.
- **Nix**, only if you use the development shell or build the LaTeX spec.

## Toolchain

The TypeScript workspace under `demo/` uses `pnpm`:

- **Package manager:** `pnpm@9.15.4` (pinned via `packageManager` in
  `demo/package.json`).
- **Node.js:** `>=22.16.0` (declared in the `engines` field of `demo/package.json`).

<Callout type="info" title="On-chain toolchain">
  The on-chain Aiken code is built separately with the Aiken compiler. Install
  [Aiken](https://aiken-lang.org/) to build `onchain/aiken`.
</Callout>

## Demo workspace commands

Run these from the `demo/` directory:

```sh
pnpm run build        # build all workspace packages
pnpm run typecheck    # typecheck all workspace packages
pnpm run test         # typecheck, then run all package tests
pnpm run lint         # eslint with --max-warnings=0
pnpm run format-check # prettier --check
```

`build` and `typecheck` run workspace packages with bounded concurrency.
`test` first type-checks, then runs the explicit package lanes in
`demo/scripts/run-test-lanes-v1.mjs`; it is not a recursive test of every
workspace member. Use `pnpm run test:serial` for the recursive workspace pass,
or run a package's own `test` command for a targeted change. Node and tools
suites also require their documented PostgreSQL test setup.

Exact flags, heap limits, and formatting exclusions live in `demo/package.json`.

### Targeted transaction-preparation tests

`demo/package.json` also defines focused test scripts:

| Script                  | Command                                                                            |
| ----------------------- | ---------------------------------------------------------------------------------- |
| `test:tx-prep:sdk`      | `pnpm --filter @al-ft/lucid-midgard test && pnpm --filter @al-ft/midgard-sdk test` |
| `test:tx-prep:node`     | Runs node transaction-preparation checks and node-tools e2e reliability checks.    |
| `test:tx-prep:emulator` | Runs `midgard-node` emulator tests and a fault-proofs submit-init emulator test.   |
| `test:tx-prep:local`    | Runs the `sdk`, `node`, and `emulator` groups in sequence.                         |

## Per-package builds

From the repository root, install the workspace once, then select a package:

```sh
pnpm --dir demo install --frozen-lockfile
pnpm --dir demo/midgard-sdk build
pnpm --dir demo/midgard-node build
```

## Building the on-chain code

Use the compiler/toolchain pinned by `onchain/aiken/aiken.toml` and the repository
CI configuration.

For demo, preprod, or e2e deployments, build the Aiken contracts from `onchain/aiken`
with the `testnet` environment **before** building node images:

```sh
cd onchain/aiken && aiken build --env testnet
```

Use another Aiken environment only when the task explicitly targets it.

## Development shell

From `demo`, its `Makefile` provides a Nix development shell:

```sh
make shell   # runs: nix develop
```

## Building the technical specification

From the repository root, build the LaTeX spec with:

```sh
make spec
```

Then open `technical-spec/midgard.pdf`.

## Git hooks

From the repository root, install the project's hooks once per clone:

```sh
bash .githooks/install
```

See [`CONTRIBUTING.md`](https://github.com/Anastasia-Labs/midgard/blob/main/CONTRIBUTING.md)
for the full contribution workflow and review expectations.

L1 transaction validity bounds are protocol-dependent. Use the SDK builders and
the transaction-finalization rules referenced by the node runbooks; arbitrary
wall-clock offsets are not a substitute for the deployed rule.
