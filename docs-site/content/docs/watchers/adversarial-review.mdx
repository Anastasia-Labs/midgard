  of the design-only watcher plan: planning documents, not shipped code. The
  working implementation is
  [`demo/da-committee-node`](/docs/watchers/da-committee-node) (package/bin name
  `midgard-watcher`).
</Callout>

## Verdict

**No-go as a production-ready plan in its first draft.**

The watcher docs identify many of the right launch gates, but several were not concrete, testable,
or aligned tightly enough with the current Midgard repo. The Midgard readiness doc is already
explicit that public testnet is no-go because fraud-proof / proof-data availability, deterministic
deployment identity, finality/rollback, CI, and acceptance gates remain blockers.

The reviewer's single strongest correction:

<Callout type="error" title="Move the hard problems into Milestone 0/1">
  Move proof coverage, DA / header binding, transition-trace design, consensus
  feature gates, and finality / provider policy into the earliest milestones.
  Building a broad verifier before those are frozen risks producing a watcher
  that can detect real faults it cannot prove or stop.
</Callout>

## Findings

Each finding below records the reviewer's concern and the disposition (how the plan was changed to
absorb it).

### 1. Critical: State-transition proofs were not a first-class launch gate

The first plan verified only the final `utxos_root`; it did not require a committed transition
trace, step index, exact-once coverage, or per-step challenge path. Local transaction faults are
insufficient because an operator can commit individually valid transactions with a wrong post-state
root. **Disposition:** add a milestone before verifier/proof work for `transition_trace_root`,
`transition_trace_index_root`, step schema, exact-once and ordering challenges, and Aiken/TypeScript
conformance/budget tests.

### 2. Critical: DA was under-specified for independent challengers

The first DA task defined a payload but not deterministic state-queue header reconstruction from
public payload bytes, non-circular header/payload binding, certificate contents, or a rule that
missing DA blocks append/merge or are directly slashable. The spec's DA section remains aspirational
Leios/Mithril design. **Disposition:** make DA security mode, retention, permissionless retrieval,
`challenge_window + finality + proof_margin`, and missing-DA challenge semantics launch blockers.

### 3. Critical: Consensus feature gating was missing

Excluding features from the security claim is not enough if the deployed protocol still admits
unprovable features. Current validation accepts or evaluates mint, Plutus/MidgardV1 scripts,
observers, redeemers, protected receives, budgets, and value preservation. **Disposition:** add a
manifest-enforced feature matrix, every enabled ledger feature must have end-to-end proof support
or be rejected/disabled in consensus.

### 4. Critical: L1 finality and provider consistency were not strong enough

The first plan accepted an ambiguous "at least one provider, with a path to
multiple" policy. **Disposition:** require an explicit source discriminator.
`local_node` uses the watcher's own full node and chain-sync stream as the sole
consensus authority, with rollback propagation and same-node query/index
alignment. `external_providers` requires at least two operationally independent
providers to agree on network and compatible chain point. Both modes require
explicit finality, fail-closed mismatch handling, and rollback quarantine.

### 5. High: Spec, implementation, and proof roots required one conformance rule

The original review found inconsistent transition order and root representations.
The current spec and node now agree on withdrawals, forced transaction orders,
normal L2 transactions, then deposits, and reject same-block spending of a
deposit. Aiken proof binding is still incomplete. **Disposition:** keep generated
TypeScript/Aiken/live-block golden vectors and clean-redeploy criteria as a
release gate so order or root schemas cannot drift again.

### 6. High: Double-spend E2E can pass without proving acceptedness

Phase A rejects non-`TxIsValid`, but the current native compact verifier checks the validity code is
well formed without necessarily asserting it equals `TxIsValid`. **Disposition:** require `TxIsValid`
assertions in all accepted-transaction proof helpers plus mutation tests with invalid validity codes.

### 7. High: Acceptance gate was too narrow

Requiring only one proof-covered invalid block proves a demo path, not production coverage.
**Disposition:** require E2E emulator tests for every claimed proof family, gated preprod tests for
all launch-scope families, negative tests proving valid blocks cannot be challenged, and artifacts
from public DA / proof bundles.

### 8. High: Fraudulent-header removal concurrency was under-specified

The first plan covered tail/non-tail tests but not live state-queue races, refetch-after-each-
confirmation, successor pruning order, or per-removed-block slashing under concurrent commits/merges.
**Disposition:** add adversarial removal-orchestration tests against changing topology, stale UTxOs,
concurrent append/merge attempts, and active/retired/already-slashed operators.

### 9. High: Protocol economics and timing were not production-planned

Current parameters still include TODOs, a very short `maturity_duration`, and zero slash/reward
values in testnet settings. **Disposition:** add a quantitative proof-deadline model, worst-case
proof steps, L1 confirmation depth, retries, fee congestion, DA fetch, and rollback margin must fit
inside maturity with measurable slack.

### 10. Medium: Manifest trust and provenance were incomplete

The manifest task listed many fields but not a full script parameterization graph, DA mode, feature
gates, release commit, signer trust root, threshold/rotation policy, or manifest signing authority.
**Disposition:** treat manifest generation, signing, verification, and key custody as a dedicated
release-security milestone.

## How this maps to the shipped node

Several of these findings are already partly answered by the working DA committee node and the
libp2p transport migration:

- Finding 2 (DA binding) and the `payload_hash` vs `header_hash` separation are addressed by the
  [DA transport migration](/docs/watchers/da-transport-migration), which requires committee nodes to
  reconstruct the state-queue header from payload bytes and match it against L1 before signing.
- Finding 1 (transition trace) surfaces in the committee node's optional `transition_proof_data`
  derivation, described in [DA committee node](/docs/watchers/da-committee-node).
- Finding 4 (finality/providers) appears in the runtime's `MultiStateQueueProvider` and
  `finalityDepth` scanning, described in [libp2p runtime](/docs/watchers/libp2p-runtime).

For the fault-proof coverage matrix that findings 1, 3, 6, and 7 depend on, see
[fault proofs](/docs/fault-proofs/overview) and [offchain data architecture](/docs/spec/offchain-data-architecture).
