## What Midgard is

Midgard is an optimistic rollup on Cardano. Operators build L2 blocks off-chain, publish full
block data to a public data-availability (DA) layer, and commit fixed-size block headers to
Cardano L1 through Midgard's state-queue contracts. Each committed block waits for a protocol
`maturity_duration` before it can be merged into the confirmed L2 state. During that waiting
period, anyone can verify the block. If the block is invalid, a challenger submits a fraud proof
on L1, prevents the block from merging, removes the fraudulent header from the queue, and slashes
the operator bond.

The important design point is that Cardano L1 does **not** re-execute every Midgard block during
normal operation. L1 only enforces the commit, queue, merge, settlement, and proof protocols.
Independent off-chain watchers provide the continuous verification that makes the optimistic
design safe.

The key L1 protocol objects the watcher must track include:

- `hub_oracle`: deployment registry for protocol script hashes and addresses.
- `operator_directory`: registered, active, and retired operators plus their bonds.
- `scheduler`: assigns operator shifts.
- `state_queue`: FIFO queue of committed block headers and the current confirmed state.
- `settlement`: post-merge records for deposits, withdrawals, and forced transaction orders.
- `reserve` and `payout`: custody and payout lifecycle for deposits and valid withdrawals.
- `fraud_proof_catalogue`: fixed mapping from proof-category IDs to the first validator in each
  proof procedure.
- `computation_thread` and `fraud_proof`: the multi-step proof state machine and permanent proof
  token.
- User-event scripts, deposit, withdrawal order, transaction order, and witness staking scripts.

## What a watcher is

A Midgard watcher is an independent verifier and challenger. It follows Cardano L1, follows
Midgard's state queue, retrieves the full block data from DA, locally evaluates every committed
block under the Midgard ledger rules, and submits the corresponding fraud proof if the committed
header is wrong.

A watcher is **not** an operator. It does not produce blocks, run a public mempool, or serve
user transaction submission. It is also **not** merely an indexer, because it must be able to act
before the maturity window closes. The minimum useful watcher does four things:

1. Reconstruct public Midgard state from L1 plus DA.
2. Re-execute committed blocks deterministically.
3. Select the precise proof family for any violation.
4. Submit and monitor proof transactions until the bad block or bad claim is neutralized.

## Security role

The watcher enforces the optimistic-rollup assumption that invalid blocks are detected before they
merge. It protects properties such as:

- Invalid L2 state transitions do not become confirmed.
- Deposits, withdrawal orders, and forced L2 transaction orders cannot be censored while block
  production continues.
- Operators cannot fabricate deposits, withdrawals, or transaction orders that do not exist on L1.
- Operators cannot include user events outside their assigned event interval.
- Operators cannot include invalid L2 transactions as valid, nor mark valid forced transactions
  and withdrawals invalid without a provable reason.
- Operators cannot double-spend, spend missing inputs, use withdrawn reference inputs, violate
  validity ranges, underpay fees, omit required signatures/scripts, or otherwise violate the L2
  transaction rules.
- Settlement resolution claims can be disproved if a confirmed deposit, withdrawal, or forced
  transaction order remains unprocessed.
- Data-availability failures are detected and, once the corresponding proof path is deployed,
  challenged.

Economically, the watcher is what makes operator bonds meaningful: the bond deters fraud only if a
watcher can reliably convert an invalid block into a successful proof and claim the
`fraud_prover_reward`.

## Watcher inputs and local state

A production watcher needs one explicit Cardano L1 source mode with finality
and rollback policy: either `local_node`, where its own full node and chain-sync
stream are the sole consensus authority and every Ogmios/Kupo/db-sync query
surface must match that node, or `external_providers`, where at least two
operationally independent providers must agree on network and compatible chain
point. It also needs a verified Midgard deployment manifest, the authenticated
hub-oracle view and all protocol UTxOs, DA material for every committed block
under challenge, a local rule bundle keyed by protocol version, and a funded
prover wallet for proof-init, proof-step, token-mint, and header-removal
transactions.

<Callout type="warn" title="Distrust operator-local data">
  The watcher should not depend on an operator's local Postgres tables, MPF
  stores, or admin endpoints for security-critical data. Those are useful
  diagnostics, not trusted inputs. Every local table should be reproducible from
  L1 plus DA; if it cannot be reproduced, treat it as a cache, not authority.
</Callout>

## Block verification pipeline

<Callout type="info" title="Canonical block application order">
  The current specification and node apply withdrawals, forced transaction
  orders, normal L2 transactions, then deposits. Same-block spending of a
  deposit is therefore invalid. A watcher must still load this rule from the
  deployed protocol version and reject any unversioned order change. See
  [offchain data architecture](/docs/spec/offchain-data-architecture).
</Callout>

The watcher runs each committed queue block through an ordered pipeline:

1. **Deployment and chain following**, verify local durable state belongs to the current
   deployment fingerprint (fail closed on mismatch); track all protocol UTxOs with finality and
   rollback handling.
2. **State queue tracking**, parse each linked-list node datum, distinguish confirmed-state root,
   queued headers, appends, merges, and fraudulent-header removals, and verify per-header invariants
   (`prev_header_hash`, `prev_utxos_root`, `start_time`/`end_time`, adjacent event intervals,
   scheduled operator, bond hold, DA attestation).
3. **Data availability fetch and root checking**, fetch each queued block's DA payload and recompute
   `transactions_root`, `deposits_root`, `withdrawals_root`, and `utxos_root`. Unavailable, malformed,
   or root-inconsistent data is a DA or commitment fault.
4. **L1 user-event indexing**, index deposits, withdrawal orders, and transaction orders directly
   from L1, authenticate each event, and enforce the inclusion window `(previous_end_time,
block_end_time]`. This is the core censorship-resistance rule.
5. **L2 transaction validation**, reuse the `midgard-validation` split of Phase A (stateless
   per-transaction checks) and Phase B (stateful validation against the reconstructed UTxO state).
6. **Deposits, withdrawals, and forced transactions**, independently classify each withdrawal
   (for example `NonExistentWithdrawalUtxo`, `SpentWithdrawalUtxo`, `IncorrectWithdrawalOwner`,
   `WithdrawalIsValid`) and confirm forced transactions are included with correct priority.
7. **Block application order**, apply the block transition exactly as the deployed protocol version
   defines it, loaded as a versioned rule bundle rather than hard-coded.
8. **Settlement, reserve, and payout watching**, track each settlement event until processed and
   submit the settlement disproof path if an operator attaches a false resolution claim.

## Fraud-proof flow

The watcher treats proof submission as a state machine with durable recovery: detect a concrete
violation and choose a proof family; build a proof bundle; submit computation-thread `Init`; advance
each proof step; on the final step mint the permanent fraud-proof token and burn the computation
thread through `Success`; submit `RemoveFraudulentBlockHeader` and slash the operator; prune
descendants; and verify the queue no longer contains the fraudulent block. For settlement claims, the
analogous path is `Disprove Resolution Claim` plus operator slashing.

Current [fault-proof tooling](/docs/fault-proofs/overview) covers the computation-thread
machinery and a set of Aiken proof families, but production proof coverage is not
complete; see [Project Status](/docs/getting-started/status).

The suggested service boundaries split the watcher around trust and determinism: `chain`,
`contracts`, `da`, `ledger`, `proof-data`, `detectors`, `proofs`, `submitter`, `db`, and `api`. The
`ledger` and `proofs` packages should be testable without a live Cardano node.

## Watcher block decision

For each queued block, the watcher should produce exactly one decision:

| Decision              | Meaning                                                                                                                                       |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| `verified`            | All roots and rules match; safe to let the block mature. The only healthy state.                                                              |
| `pending_da`          | Block cannot yet be evaluated because DA is temporarily unavailable, with a deadline before maturity. Close to maturity this is an emergency. |
| `unprovable_gap`      | A violation may exist but the deployed proof set cannot prove it. A production launch blocker for security claims.                            |
| `fault_detected`      | A concrete proof-covered violation exists and proof submission is in progress.                                                                |
| `fault_proven`        | A fraud-proof token exists for the target block or settlement claim.                                                                          |
| `removed_or_resolved` | The bad block or claim has been removed and slashing completed or observed.                                                                   |
