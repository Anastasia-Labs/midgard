`demo/midgard-watcher` is the independent verifier and challenger. It follows
Cardano L1, retrieves retained DA, reconstructs L2 commitments, and supervises
supported proof workflows. The [DA committee](/docs/watchers/da-committee-node)
is a separate service responsible for retention, retrieval, and attestation.

Cardano validates the L1 protocol transactions; it does not re-execute every
L2 block. A watcher therefore needs authenticated L1 observations and public
DA, enough intermediate evidence to prove a supported fault, and time to
complete the challenge before the applicable deadline.

## Runtime

The package exposes `start` and `replay`. `start` runs the watcher until
shutdown; `replay` catches up durable state through the same runtime and then
closes it. Replay can drive proof workflows and is not an offline command.

Use the
[package README](https://github.com/Anastasia-Labs/midgard/blob/main/demo/midgard-watcher/README.md)
for build commands and configuration schemas, and the
[challenger runbook](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/challenger-runbook.md)
for proof workflow operation.

## Trust and recovery

- The executable requires `acceptance` mode, `Preprod` (or `Custom` for an
  isolated devnet) and the `local_node` L1 source: the watcher reads L1 only
  through its own ChainSync follower on the Cardano node's socket, with the
  node transport. Its finality depth equals the deployment profile's
  confirmation depth.
- Operator-local databases, MPF stores, and admin endpoints do not replace
  authenticated L1 and DA evidence.
- A rollback rewinds the follower's facts to the intersection and every
  projection recomputes. A rollback deeper than k leaves the watcher up and
  unready, with the `/readyz` reason `rollback_beyond_k`.
- Verification binds the deployed transaction format, source roots, event
  placement, transition trace, and validation material. Deposits follow
  transactions in phase order, so same-block deposit spending is invalid.

The accepted rationale and implementation anchors live in
[Watcher verification boundaries](https://github.com/Anastasia-Labs/midgard/blob/main/docs/midgard/decisions/watcher-verification-boundaries.md).

## Acceptance

Runtime readiness means startup checks passed for that configured process. It
does not establish public launch readiness or complete proof coverage.
An installed runner, a deployed proof validator, publicly retrievable evidence,
and an accepted end-to-end result are separate requirements.

Use the
[catalogue status](https://github.com/Anastasia-Labs/midgard/blob/main/docs/fault-proofs/catalogue-status.md)
for current installation and coverage, and [Project Status](/docs/getting-started/status)
for release gates. Acceptance must cover valid-block non-challengeability,
restart/rollback, changing queue topology, retention, deadline margins,
deployment provenance, key custody, and configured economics.
