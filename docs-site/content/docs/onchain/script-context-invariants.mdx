Exactly which properties of Aiken's `cardano/transaction.Transaction` a Midgard
validator may treat as guaranteed. The list is intentionally strict: only
ledger/runtime guarantees, or invariants enforced by Aiken's opaque on-chain
types, are included. Source:
[`docs/script-context-invariants.md`](https://github.com/Anastasia-Labs/midgard/blob/main/docs/script-context-invariants.md).

<Callout type="warn" title="Rule of thumb">
  If a property is not listed here, contracts and off-chain code must not treat
  it as guaranteed without an additional source. Where a rule applies to `TxOut`
  values but not to `transaction.mint`, that distinction is called out
  explicitly.
</Callout>

## Scope

1. Aiken's `Transaction` is not a byte-for-byte copy of the full transaction
   body. On-chain scripts cannot see bootstrap inputs, bootstrap outputs, or
   transaction metadata.
2. `transaction.redeemers` only contains **script** witnesses. Pubkey witnesses
   never appear there.
3. `transaction.inputs` in script context are **ledger-ordered**, not
   builder-ordered. Off-chain code must not assume they follow the order of
   `.collectFrom(...)` or similar builder calls.

## Ordering invariants

### Inputs

- `transaction.inputs` is ordered lexicographically by `OutputReference`
  (`tx id`, then output index).
- That list order is the reference order used when reasoning about `Spend`
  purposes.

### Outputs

- `transaction.outputs` preserves transaction-body order.
- Output order is not lexicographically re-sorted by the ledger for script
  context.

### Withdrawals

- `transaction.withdrawals` is ordered by ascending `Credential`.
- For this ordering, script credentials compare **lower** than
  verification-key credentials.

### Redeemers

- `transaction.redeemers` is ordered by ascending `ScriptPurpose`.
- For the subset used by this repository, the effective purpose ordering is
  `Spend`, then `Mint`, then `Withdraw`.
- Within `Spend`, entries are ordered lexicographically by the
  `OutputReference` / `TxOutRef` of the spent script input.
- Within `Mint`, ordering is lexicographic by policy ID / currency symbol.
- Within `Withdraw`, ordering follows the ledger-ordered withdrawal credential
  list.
- Because `transaction.redeemers` only contains script witnesses, pubkey-spent
  inputs do not create `Spend(...)` entries there.

### Governance-specific ordered fields

- `transaction.votes` is ordered by ascending `Voter`, then ascending
  `GovernanceActionId`.
- `Publish { at, .. }` refers to the 0-based index in
  `transaction.certificates`.
- `Propose { at, .. }` refers to the 0-based index in
  `transaction.proposal_procedures`.

## `Value` invariants

These apply to any Aiken `Value` in script context, including `Output.value` and
`transaction.mint`.

1. A `Value` is a normalized nested map: `PolicyId -> AssetName -> Int`.
2. The outer policy map is ordered lexicographically by policy ID.
3. Each inner asset-name map is ordered lexicographically by asset name.
4. Duplicate policy IDs cannot appear.
5. Duplicate asset names under one policy cannot appear.
6. Zero-quantity entries are not allowed in a `Value`.
7. Ada is represented as policy ID `""` and asset name `""`.
8. Because `""` sorts before any non-empty bytestring, Ada is the first asset
   entry whenever a `Value` contains lovelace.

## `TxOut`-specific value invariants

These apply to `transaction.outputs[*].value` and to resolved input values seen
through `transaction.inputs[*].output.value`.

1. Output values cannot contain negative quantities.
2. Any asset present in an output value has strictly positive quantity.
3. All output values carry lovelace, so Ada is the first entry in an output
   `Value`.
4. Contracts may rely on "Ada first" only because outputs carry lovelace, Ada
   uses the empty policy ID and empty asset name, and Aiken `Value` ordering is
   lexicographic.

## Important non-guarantees

<Callout type="error" title="Do not assume these">
  1. Do not generalize output-value positivity rules to `transaction.mint`. Mint
     values may contain negative quantities, which represent burns.
  2. Do not assume every spent input has a redeemer entry. Only Plutus
     script-spent inputs do.
  3. Do not assume redeemer positions are stable under reordering of inputs,
     mint policies, or withdrawals. Witness indices are a function of ledger
     ordering, not builder call order.
  4. Do not assume output order is sorted. It is preserved body order.
</Callout>

## Practical summary

For this repository, the load-bearing facts are:

1. `transaction.inputs` are lexicographically ordered by `TxOutRef`.
2. `transaction.outputs` preserve tx-body order.
3. `Value` is lexicographically ordered by policy ID, then asset name.
4. Zero-quantity entries are absent from `Value`.
5. Token quantities in `TxOut` values are non-negative and non-zero.
6. `TxOut` values always contain Ada as the first entry (Ada's policy ID `""`
   always sorts first).
7. `transaction.redeemers` must be read in ledger order, with the
   repository-relevant subset `Spend < Mint < Withdraw < ...`.

Many Midgard validators exploit these facts through explicit **index redeemers**
(for example `settlement_input_index`, `hub_ref_input_index`,
`mint_redeemer_index`): the off-chain builder supplies the position and the
validator re-checks the referenced entry against the invariants above.
