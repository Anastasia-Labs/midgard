---
title: "Native Transaction Model"
description: "The Midgard native transaction format lucid-midgard produces, and how strict canonical CBOR and hashing keep it deterministic."
---

`lucid-midgard` builds the **implemented** Midgard native transaction format, not
a close approximation. The codec itself lives in `@al-ft/midgard-core`
(`src/codec/native.ts`); this page describes the format the builder produces.

## Implemented format

The current implementation is native v1, defined by these protocol constants
(exported from `midgard-core`):

- `MIDGARD_NATIVE_TX_VERSION = 1`
- `MIDGARD_POSIX_TIME_NONE = -1`
- `MIDGARD_NATIVE_NETWORK_ID_NONE = 255`

A full transaction is a four-element tuple:

```text
[version, body_canonical, witness_set_canonical, validity]
```

The canonical body carries six field preimages and the scalar body fields. The
canonical witness set carries three preimages: address, script, and redeemer
witnesses. There is no datum witness bucket.

The separately derived compact wire form is
`[version, body_compact, witness_set_hash, validity]`: its body is a record of
field commitments and scalars, not a single body hash. `MidgardNativeTxFull` is
the in-memory canonical transaction paired with this derived compact form.

## Hashing and the transaction id

Native commitments use Blake2b-256. The transaction id is derived as:

```text
blake2b256(ASCII("MidgardNativeTxBodyV1") ++ CBOR(version) ++ CBOR(body_compact))
```

Use `computeMidgardNativeTxId(nativeTx)` rather than reproducing this derivation.
Address signatures verify against that id. It differs from the separate,
domain-separated commitment to the complete canonical transaction bytes.

## Strict canonical CBOR

The builder produces canonical RFC 8949 CBOR compatible with the node codec. It
must not emit indefinite-length values, `undefined`, duplicate map keys, or
trailing bytes. Any helper that accepts user-supplied CBOR applies strict decode
and re-encode rules.

## Field preimages

Each of the nine field preimages has its own canonical V1 schema and bounds.
An empty field is not universally encoded as a bare CBOR empty list: use the
shared field codecs. The no-script integrity value is
`EMPTY_NULL_ROOT = blake2b256(cbor(null))`.

## Outputs

Outputs are serialized as byte strings inside the native outputs preimage. They
are Babbage/Conway map-form transaction outputs with a Shelley payment
credential. **Output order is authored order and is preserved**, outputs are
never re-sorted for context construction.

### Protected outputs

`pay.ToProtectedAddress(...)` sets bit `0x08` on the first address byte before
the output enters the native output preimage. Validation clears that bit for
ordinary address decoding, but Phase B uses the marker to require either a
matching vkey witness (protected pubkey outputs) or a MidgardV1 receive execution
(protected script outputs). Local output derivation and chaining keep this byte
representation exactly, rather than rebuilding outputs from decoded display
fields.

## Script integrity

`scriptIntegrityHash` is **not** a legacy Cardano `script_data_hash`. For
transactions requiring non-native scripts it is:

```text
blake2b256(cbor([
  redeemerTxWitsHash,
  scriptLanguageViews
]))
```

`scriptLanguageViews` is a canonical CBOR map from stable numeric language tags
to frozen ordered integer cost-model arrays. The initial tags are `2` for
`PlutusV3` and `128` for `MidgardV1`. The map contains only languages actually
required by the transaction after Phase B resolves inline and reference script
sources. Native-only and no-script transactions use `EMPTY_NULL_ROOT`. See
[Scripts, Redeemers, and Indexing](/docs/sdk/lucid-midgard/scripts-redeemers) for
the full derivation.

## Cardano bridge

Node ingress accepts the canonical Midgard proof-submission envelope and rejects
Cardano transaction bytes. `cardanoTxBytesToMidgardNativeTxFull` is a separate
core diagnostic conversion helper; `lucid-midgard` build, import, and submission
paths do not invoke it.
