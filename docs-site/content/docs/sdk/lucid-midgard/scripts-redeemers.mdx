description: "Attaching scripts, choosing script purposes, how redeemer indexes are derived from validator ordering, and how the script integrity hash is computed."
---

Scripts are the highest-risk part of building a Midgard transaction. A redeemer points
at its script by **position**, and those positions are derived from validator ordering,
not from the order you called the builder. Get the derivation wrong and the transaction
fails validation; optional local preflight can detect it before submission.

`lucid-midgard` derives every index for you. This page explains the rules it applies, so
you can reason about a transaction that does not validate.

## Script purposes

Phase B discovers script executions for four purposes:

| Purpose   | Triggered by                                      |
| --------- | ------------------------------------------------- |
| `spend`   | A script payment credential on a spent output.    |
| `mint`    | A policy id in the native mint map.               |
| `observe` | A required observer hash in the transaction body. |
| `receive` | A protected script output.                        |

`receive` is Midgard-specific. It requires a MidgardV1 script context, and a PlutusV3
`receive` is rejected locally before submission because Cardano's context cannot express
it. See [Value Accounting](/docs/validation/value-accounting).

Redeemer tags follow Cardano's, plus one: `spend`, `mint`, `observe` (the reward tag),
and `receive`, which is tag `6`.

## Index derivation

Each redeemer index is the position of its target in a **sorted** list:

- **Spend**: position of the spent out-ref in the lexicographically sorted spend-input
  list.
- **Mint**: position of the policy id in the sorted policy id list.
- **Observe**: position of the observer hash in the sorted observer list.
- **Receive**: position of the protected receiving script hash in the sorted, unique
  receiving-hash list.

<Callout type="warn" title="Outputs are the exception">
  Outputs are never sorted for context construction. They stay in authored
  order. Every other derived index uses validator ordering, which is why
  balancing can reorder inputs without invalidating your redeemers, but
  reordering outputs changes the transaction.
</Callout>

## Datums

Midgard supports inline PlutusData datums only. Datum hashes are rejected.
Although `attach.Datum` exists on the fluent surface, completion rejects datum
witnesses because the native wire format has no datum witness bucket.

## Script integrity hash

`scriptIntegrityHash` is **not** a Cardano `script_data_hash`. It commits to the
redeemer witness hash and the language views actually required:

```text
scriptIntegrityHash = blake2b256(cbor([
  redeemerTxWitsHash,
  scriptLanguageViews
]))
```

`scriptLanguageViews` is a canonical CBOR map from a stable numeric language tag to that
language's frozen, ordered cost-model array. The tags are `2` for `PlutusV3` and `128`
for `MidgardV1`. The value carries the cost model only; Phase B dispatches on the tag.

The map contains **only** the non-native languages the transaction actually requires,
after Phase B resolves inline and reference script sources. Native-only and no-script
transactions use `EMPTY_NULL_ROOT`, which is `blake2b256(cbor(null))`.

Phase A checks presence only: if redeemers or non-native inline witnesses exist, the
hash must be non-empty. It cannot verify the language views, because reference scripts
may need Phase B state to resolve. Phase B rebuilds the views, recomputes the hash, and
rejects on mismatch. A missing language view and an extraneous one are both mismatches.

<Callout type="error" title="Cost models are protocol constants">
  The `PlutusV3` and `MidgardV1` cost-model views are frozen Midgard constants.
  A dependency bump must not change these arrays. Changing them is a protocol
  migration.
</Callout>

## Reference scripts

Reference inputs must preserve their canonical output bytes. Trusted metadata
binds a declared script language and hash to a reference out-ref; declarations
are checked against available script bytes and cannot supply executable code.

Non-native reference execution requires the canonical script envelope and exact
CEK program material. Supply required sidecar material through
`complete({ programMaterial })`; completion verifies its match and fails closed
when material is missing or inconsistent. Metadata alone is insufficient.
Node Phase B still resolves the reference input against its own ledger state.
