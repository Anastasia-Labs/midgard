Chapter 5 specifies the rules a Midgard L2 transaction and block must satisfy. These
rules are intended to be the precise contract that both the off-chain validator and
the on-chain fraud proofs check against.

## Cardano ledger rules

Section 5.1 (`1-cardano-ledger-rules.tex`) is written. It restates the Cardano ledger
rules Midgard inherits, each with its violation code. For example, **No Ada minted**
requires `lovelaces(mint(t)) = 0` and is violated by `ADA-MINTED`. This does not
prohibit minting or burning non-Ada assets.

## Custom Midgard ledger rules

<Callout type="info" title="Canonical V1 is indivisible">
  `technical-spec/5-ledger-rules/2-custom-midgard-ledger-rules.tex` now records
  the canonical rules, while `demo/midgard-core/src/consensus-profile-v1.ts` is
  their machine-readable identity. Protocol version `1` enables mint/burn,
  native/PlutusV3/MidgardV1 scripts, redeemers, reference inputs/scripts,
  observers, script payment credentials, and protected outputs as one fixed V1
  surface. A deployment either binds that complete tuple and its L1-disputable
  proof machinery or refuses to activate; unknown profile identities and
  unsupported encodings fail closed.
</Callout>

What the implementation enforces today is documented under the
[validation engine](/docs/validation/phase-a). Section 5.2 rules are enforced
across canonical construction, admission, DA verification, and the
L1-disputable validation machine:

| Section 5.2 heading         | Status in the implementation                                                                                                                                                                                                                          | Reject code                                       |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Is valid                    | Enforced at canonical V1 admission. `ledgerTx.validity` must be `TxIsValid`.                                                                                                                                                                          | `E_IS_VALID_FALSE_FORBIDDEN`                      |
| No auxiliary data           | Enforced at canonical V1 admission. `auxiliaryDataHash` must equal `EMPTY_NULL_ROOT`.                                                                                                                                                                 | `E_AUX_DATA_FORBIDDEN`                            |
| Certificates empty          | Holds by construction. The native transaction format has no certificate field.                                                                                                                                                                        | Not applicable                                    |
| Only zero withdrawals       | Holds by construction. Native transactions carry required observers, not withdrawals. When a native transaction is converted to a Cardano transaction, each observer becomes a reward-account withdrawal of exactly `0` lovelace (`codec/native.ts`). | Not applicable                                    |
| Mint and burn authorization | Phase B runs each native, PlutusV3, or MidgardV1 non-Ada minting policy and checks `inputs + mint − fee − outputs = 0`; Ada mint remains forbidden.                                                                                                   | script-verdict failure or `E_VALUE_NOT_PRESERVED` |

<Callout type="warn" title="No feature-gate fallback">
  `lucid-midgard` exposes `mintAssets` and `mint` because mint/burn is part of
  canonical V1, not a dormant future profile. These calls construct immutable
  builder state; they are not rejected merely because the mint preimage is
  non-empty. Canonical completion and validation enforce exact profile bounds,
  policy authorization, the zero-Ada rule, and `inputs + mint − fee − outputs =
  0`. Release activation stays closed until the exact deployment-bound proof
  paths cover that fixed surface; an operator or manifest cannot disable mint,
  scripts, or another normative V1 feature to bypass the gate.
</Callout>

Section 5.1 also states rules a fraud proof can demonstrate a block violated,
including the transaction validity range and the requirement that all inputs resolve.

## Data-availability rules

- **Retained block payload matches the L1 header**: the payload the committee retains
  must correspond to the committed header.
- **Normal transaction root projection**: how the transaction root is projected and
  checked.

## In the codebase

The rules are enforced off-chain by the two-phase
[validation engine](/docs/validation/overview) (Phase A structural checks, Phase B script and
ledger evaluation) and, when a block breaks them, adjudicated on L1 by the
[fraud-proof machines](/docs/onchain/fraud-proof-machines). The DA rules are realized
by the [data-availability committee](/docs/watchers/da-committee-node).
