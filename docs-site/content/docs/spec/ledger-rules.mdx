Chapter 5 specifies the rules a Midgard L2 transaction and block must satisfy. These
rules are intended to be the precise contract that both the off-chain validator and
the on-chain fraud proofs check against.

## Cardano ledger rules

Section 5.1 (`1-cardano-ledger-rules.tex`) is written. It restates the Cardano ledger
rules Midgard inherits, each with its violation code. For example, **No Ada minted**
requires `lovelaces(mint(t)) = 0` and is violated by `ADA-MINTED`.

## Custom Midgard ledger rules

<Callout type="info" title="The launch profile is normative">
`technical-spec/5-ledger-rules/2-custom-midgard-ledger-rules.tex` now records the
launch rules, while `demo/midgard-core/src/consensus-profile.ts` is their
machine-readable identity. A future profile may enable additional features only
with corresponding L1-disputable proof coverage.
</Callout>

What the implementation enforces today is documented under the
[validation engine](/docs/validation/phase-a). The closest counterparts to the section
5.2 headings are Phase A's stateless checks:

| Section 5.2 heading | Status in the implementation | Reject code |
| --- | --- | --- |
| Is valid | Enforced by Phase A. `ledgerTx.validity` must be `TxIsValid`. | `E_IS_VALID_FALSE_FORBIDDEN` |
| No auxiliary data | Enforced by Phase A. `auxiliaryDataHash` must equal `EMPTY_NULL_ROOT`. | `E_AUX_DATA_FORBIDDEN` |
| Certificates empty | Holds by construction. The native transaction format has no certificate field. | Not applicable |
| Only zero withdrawals | Holds by construction. Native transactions carry required observers, not withdrawals. When a native transaction is converted to a Cardano transaction, each observer becomes a reward-account withdrawal of exactly `0` lovelace (`codec/native.ts`). | Not applicable |
| No mints | Enforced by Phase A and independently by DA payload verification. The canonical mint preimage must be empty. | `E_MINT_FORBIDDEN` |

<Callout type="warn" title="Mint/burn is retained, not enabled">
`lucid-midgard` retains the `mintAssets` and `mint` methods, and Phase B retains
the profile-independent `inputs − fee + mint − outputs = 0` accounting equation.
Under `midgard-launch-consensus-v1`, the builder methods fail immediately and
Phase A/DA reject any non-empty mint preimage. This preserves the product surface
without claiming the missing mint-authorization and value-preservation fraud
proofs. Enabling mint/burn requires a new consensus profile and those proof
families, as required by
[issue #459](https://github.com/Anastasia-Labs/midgard/issues/459).
</Callout>

Section 5.1 also states rules a fraud proof can demonstrate a block violated,
including the transaction validity range and the requirement that all inputs resolve.

## Data-availability rules

- **Retained block payload matches the L1 header**: the payload the committee retains
  must correspond to the committed header.
- **Normal transaction root projection**: how the transaction root is projected and
  checked.

## In the codebase

The rules are enforced off-chain by the two-phase
[validation engine](/docs/validation/overview) (Phase A structural checks, Phase B script and
ledger evaluation) and, when a block breaks them, adjudicated on L1 by the
[fraud-proof machines](/docs/onchain/fraud-proof-machines). The DA rules are realized
by the [data-availability committee](/docs/watchers/da-committee-node).
