# Regenerating goldens and ledgers

A file that a step writes cannot prove that the step is correct. A golden is
evidence only while it is exactly what its producer emits today, so it is
regenerated by its generator and compared, not edited to agree with itself.

A **channel** is one generator (or measuring verifier) plus the committed files
it writes. Every channel in the tree is declared once, in
[`scripts/channels.json`](scripts/channels.json). Read the table through the
script rather than by hand: it resolves producer packages, Aiken imports and
measured-module closures that a reader would miss.

## Steps

1. **Find the affected channels.**

   ```sh
   node .agents/skills/regenerating-goldens-and-ledgers/scripts/affected-channels.mjs --base origin/main
   node .agents/skills/regenerating-goldens-and-ledgers/scripts/affected-channels.mjs --files <path>...
   ```

   Without `--files` it diffs the working tree against `merge-base(<base>, HEAD)`
   and adds untracked files. For each affected channel it prints the reason, the
   check command, the sync command and the CI step. `--json` gives the same
   report as data.

   | Exit | Meaning                                                                                | Do                                                 |
   | ---- | -------------------------------------------------------------------------------------- | -------------------------------------------------- |
   | 0    | Looked. Either lists channels or says `no generated-artifact channel is affected`.     | Continue.                                          |
   | 1    | Looked and found a changed generator or generated-looking file that no channel claims. | Add it to `channels.json` first (step 6).          |
   | 2    | Could not look: git diff failed, bad ref, unreadable table, bad arguments.             | Fix the cause. Exit 2 never means "nothing to do". |

   Done when the script exits 0 and you have its channel list.

2. **Build the blueprint if a listed channel reads it** (the ledgers and the
   blueprint-bound fixtures). See [The blueprint](#the-blueprint).

3. **Run each listed check, in the order printed.** The order puts producers
   before consumers (lucid fixtures before `native-compact-aiken`, profiles
   before the consensus-profile doc). A channel whose check is `none` or
   `manual` goes on your list of unchecked artifacts, with the reason the script
   printed.

4. **On a red check, decide which side is wrong.** If you changed the producer
   on purpose, the artifact is stale: go to step 5. If you did not mean to change
   what the producer emits, the producer is wrong: fix the source, not the
   artifact.

5. **Sync with the generator, then check again.** Use the printed sync command.
   Re-run the check; it must pass with no further edits. For ledgers, triage the
   drift before re-taking: [references/ledgers.md](references/ledgers.md). [review]

6. **When you add or move a generator, update the table.** Add a channel to
   `scripts/channels.json` (or an `ignored` entry with a reason if its output is
   never committed) and run
   `node .agents/skills/regenerating-goldens-and-ledgers/scripts/affected-channels.mjs --verify-table`.
   It must print `verify-table: ok`.
   [ci: Agent Skills CI/Test scripts shipped inside skills]

Done when every channel the script listed is green on its check, or is on your
unchecked list with its reason, and each regenerated output is staged beside
the source change that caused it.

## Rules

- **Never hand-edit a generated artifact.** That covers whole generated modules,
  rebound constants, `*.generated.json`, the generated block of
  `docs/consensus-profile-v1.md`, `onchain/aiken/env/*.ak`,
  `generated-deployment-profiles.ts` and ledger rows
  [ci: Midgard Node CI/Check native V1 field-access golden vectors] and the
  sibling check steps listed in [references/channels.md](references/channels.md).
  Blind spot: channels whose check has no CI step (`transaction-root-v1`,
  `validation-one-step-cross-language`, three execution ledgers, most fit
  ledgers, the watcher fixture, the benchmark fixtures) accept a hand edit
  silently; only a reader catches those.
- **Commit the source change and the regenerated output together** [review].
  CI catches a split commit only for channels whose check it runs, and only on
  the pull request's final state.
- **`:check` compares, `:sync` writes.** `:check` regenerates into a temporary
  copy and fails on any byte difference, without writing the committed files
  (`demo/midgard-core/scripts/golden-channel.mjs:202-210`). `:sync`
  (and bare `fixtures:<name>` for the midgard-node and lucid-midgard channels)
  overwrites the committed files. A check that exits 0 prints nothing for some
  channels (`fixtures:transition-trace-abi:check`, measured 2026-09-25) [review].
- **A generator's Aiken text is code that must compile.** Generators emit
  `use` lines and type names as string templates, and rebind constants by name
  in hand-written modules. Renaming an Aiken type or module, or deleting a
  rebound constant, breaks the generator even though no TypeScript changed. The
  script treats the modules a generated golden imports as inputs for this
  reason [script: .agents/skills/regenerating-goldens-and-ledgers/scripts/affected-channels.mjs].
  At check time, a rebind whose constant is gone throws
  `missing Aiken constant <name>` from `rebindAikenConstants`.
- **A red CI step hides every golden check after it.** Midgard Node CI stops at
  the first failing step, and "Check canonical V1 profile documentation" runs
  before every golden check. Run the listed checks locally rather than trusting
  a red pull request to have reported them all [review].
- **Generated Aiken is formatted by the pinned fork**
  [ci: Aiken CI/Run normalized Aiken auto-formatter check]. Blind spot:
  `golden-channel.mjs` formats with `MIDGARD_AIKEN_BIN`, else `aiken` on
  `PATH`, and asserts nothing about which compiler that is, so check
  `node onchain/aiken/scripts/pinned-compiler.mjs` first. The long comment at
  `demo/midgard-core/scripts/golden-channel.mjs:122-145` says stock `aiken fmt`
  is the authority. That comment is stale: the workflow pin
  (`.github/workflows/aiken-ci.yml:13-16`) makes the fork the formatter.
- **Every generator is in the table.** A tracked generator, ledger, writer env
  var, fixture package script or generated-looking file that no channel claims
  fails `--verify-table`, which the skill's own test runs on every pull request
  [ci: Agent Skills CI/Test scripts shipped inside skills]. Blind spot:
  discovery works by naming convention (`scripts/generate-*`, `sync-*`,
  `write-*`, `verify-*-exec-ledger-*`, `*.generated.*`, `*-golden.test.ak`,
  `*-generated.ak`, `generated-*`, a "Generated by" or "do not edit" header in
  the first 400 bytes, `MIDGARD_{WRITE,SYNC,REGENERATE}_*`). A generator named
  otherwise, writing a file named otherwise, is invisible to it.

## The blueprint

`onchain/aiken/plutus.json` is a build output of whichever compiler and profile
last ran. It is not tracked and, as of 2026-09-25, not gitignored.

- **Never commit it.** The pre-commit hook refuses a staged `plutus.json`
  (`.githooks/pre-commit:50-58`) [hook: pre-commit]. Blind spot: the hook only
  runs where it is enabled (`make enable-git-hooks`), and
  `MIDGARD_SKIP_HOOKS=1` skips it.
- **Build it fresh, with the pinned fork, before anything that reads it**:
  fit ledgers, the DA deployment fixture, the watcher initialization fixture,
  fault-proof and node suites. `pnpm --dir demo run deployment:build preprod-testing`
  regenerates the profiles, refuses any compiler other than the pinned fork,
  runs `aiken build --env preprod_testing`, and records the blueprint hash in
  the gitignored `plutus.json.deployment.json`
  (`demo/scripts/deployment-profiles.mjs:260-290`)
  [script: demo/scripts/deployment-profiles.mjs]. CI builds the same way in "Build
  testnet Aiken blueprint". Blind spot: nothing checks that the `plutus.json`
  on disk is fresh. A leftover blueprint from another branch or profile makes
  every blueprint-bound check measure the wrong contracts.
- The compiler pin lives in both workflows as `AIKEN_FORK_VERSION` and is read
  by `onchain/aiken/scripts/pinned-compiler.mjs`. Check it with
  `node onchain/aiken/scripts/pinned-compiler.mjs` before building.

## Known failure: Wave 0 (fixed 2026-09-25 in `71e605e46`)

Three generators had drifted from the Aiken they emit, and CI did not say so.

- `11e1cb6ef` (2026-09-03) renamed `CommittedFieldClaimV1` to
  `CommittedFieldClaim` across the SDK, including the string templates in
  `generate-canonical-decodability-v1-goldens.mjs` (a `use` line, so the
  generated module no longer compiled) and a doc comment in
  `generate-committed-field-shape-v1-goldens.mjs`. The Aiken type is still
  `CommittedFieldClaimV1` (`onchain/aiken/lib/midgard/fraud-proofs/canonical-decodability/rule.ak:292`).
- `3e3090aa1` (2026-08-31) deleted `maximum_cardano_compact_cbor` and
  `maximum_cardano_transaction_id` from
  `validators/fraud-proofs/da-hash-preimage/step-02.ak`. The
  ordered-collection generator still rebound them there.
- Each check would have gone red: the regenerated modules no longer matched the
  committed ones, and the rebind would throw `missing Aiken constant`. None
  reported, because
  "Check canonical V1 profile documentation" was red first and every later step
  was skipped (Midgard Node CI run 35676544721, 2026-09-22).
- `71e605e46` fixed the templates and pointed the ordered-collection family at
  `step-01.ak` only, with the constants that module actually declares.

The lesson is the rule above: a renamed Aiken symbol or a deleted rebound
constant is a generator change, and a red earlier step is not evidence that
later checks pass.
