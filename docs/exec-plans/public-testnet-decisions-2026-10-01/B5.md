# B5 — Enable finite devnet housekeeping at the manifest's day value

Recommendation, based on current source inspected on 2026-10-01: set the devnet node's `RETENTION_DAYS` to the verified deployment manifest's `da.transportProfile.retentionDays`, currently 15 days. Make that an explicit stack setting derived from the deployment, rather than relying on the node's default of zero. Keep long-term archives separate. This is a recommendation only; no runtime setting was changed for this report.

The important qualification is that this setting controls a limited group of database records. It does **not** promise that node or committee block payloads remain downloadable for 15 days. Enabling it solves one source of growth, not every storage or catch-up problem.

## What the current problem is

The node defaults to `RETENTION_DAYS=0`, which disables age-based deletion of transaction rejection records, address history, completed deposit records and completed withdrawal records. Those records accumulate as the devnet runs. Setting a finite duration lets normal housekeeping remove eligible old records. The current stack generator copies environment settings into `node.env` but does not explicitly supply `RETENTION_DAYS`, so an omitted value still reaches the node's zero default. See [node config, line 537](../../../demo/midgard-node/src/services/config.make-config.ts#L537), [sweeper, line 172](../../../demo/midgard-node/src/fibers/retention-sweeper.ts#L172), and [stack generation, line 130](../../../demo/midgard-node-tools/src/full-stack/runtime.ts#L130).

Deletion is not simply “erase all deposits after 15 days.” Deposits must be consumed, have an assigned block header and have no pending finalization reference. Withdrawals must be finalized, have an assigned block header and have no pending finalization reference. Those guards should remain. Address history and transaction rejections have direct age cutoffs, so old query results disappear from the operational node. See [deposit deletion, line 432](../../../demo/midgard-node/src/database/deposits.ts#L432), [withdrawal deletion, line 263](../../../demo/midgard-node/src/database/withdrawals.restore-corrected-classification.ts#L263), [address history, line 117](../../../demo/midgard-node/src/database/addressHistory.ts#L117), and [rejections, line 70](../../../demo/midgard-node/src/database/txRejections.ts#L70).

## Days, deadlines and capacity are different

The configuration accepts an integer number of 24-hour days. `15` means 1,296,000,000 milliseconds. It cannot express 22.5 minutes as a fractional day: fractions are rejected, and a nonzero node value below the current 15-day transport floor is rejected. Zero has a special meaning: disable these age-based table deletions. See [day conversion, line 5](../../../demo/midgard-core/src/retention-window.assert-da-challenge-window-within-maturity.ts#L5), [node validation, line 23](../../../demo/midgard-node/src/database/retention-policy.ts#L23), and [transport floor, line 48](../../../demo/midgard-core/src/da-transport.da-libp2p-runtime-manifest.ts#L48).

The protocol's required evidence horizon is calculated separately in milliseconds: block maturity plus a worst-case proof allowance equal to half maturity. In the currently selected `preprod-testing` build, maturity is 900,000 ms, so that horizon is 1,350,000 ms, or 22.5 minutes. Both current short testing profiles use that maturity. The 15-day configured window is therefore much longer than the required horizon. For comparison, a mainnet-profile build with seven-day maturity calculates a 10.5-day required horizon and 4.5 days of configured headroom. These are source-derived examples, not measurements of a running deployment. See [selected profile, line 255](../../../demo/midgard-core/src/generated-deployment-profiles.ts#L255), [testing timings, line 97](../../../demo/midgard-core/src/generated-deployment-profiles.ts#L97), [local testing timings, line 141](../../../demo/midgard-core/src/generated-deployment-profiles.ts#L141), [mainnet timings, line 9](../../../demo/midgard-core/src/generated-deployment-profiles.ts#L9), and [shared calculation, line 48](../../../demo/midgard-core/src/retention-window.assert-da-challenge-window-within-maturity.ts#L48).

Neither a duration nor its calculated headroom proves sufficient disk capacity. Capacity depends on data arriving per day, record and payload sizes, database overhead, and records that remain protected. Size the disk against measured traffic and expose storage growth; no disk requirement was measured here. Also, the example environment file still describes the seven-day/10.5-day case, which is not the currently selected testing profile. See [example comment, line 229](../../../demo/midgard-node/.env.example#L229).

## Why each component has a different retention rule

| Component and data | Current source behavior | What the data is needed for |
| --- | --- | --- |
| Node's history/rejection/completed-event tables | `RETENTION_DAYS` age cutoff, with the completion guards above | Recent queries and event bookkeeping |
| Node's block payloads | Required millisecond horizon, or authenticated removal; retain the confirmed head and all live queue headers; no payload pruning without an L1 view | Validate blocks and keep evidence for unresolved protocol work |
| Committee's block payloads | Shared required-horizon decision with confirmed-head/live-queue protections; configured transport days must equal the verified manifest | Provide block data and answer availability challenges |
| Watcher's canonical evidence records | Manifest days converted to slots; expiry starts at observation; explicit still-challengeable records survive expiry | Retain authenticated inputs needed to investigate and prove faults |

The table describes inspected policy functions, not evidence that every maintenance loop is active in a live deployment. The watcher pruning function was present, but this inspection did not establish a production runtime caller scheduling it; the watcher canonical evidence store has since been deleted. See [node payload deletion, line 264](../../../demo/midgard-node/src/database/daPayloads.ts#L264), [node no-view behavior, line 160](../../../demo/midgard-node/src/fibers/retention-sweeper.ts#L160), [committee policy, line 168](../../../demo/da-committee-node/src/store/retention.ts#L168), [committee manifest equality, line 70](../../../demo/da-committee-node/src/config.parse-libp2p-da-committee-peers.ts#L70), watcher expiry, `demo/midgard-watcher/src/storage/canonical-block-store.parse-watcher-canonical-block-store-snapshot.ts:110` (since deleted), and watcher pruning guards, `demo/midgard-watcher/src/storage/canonical-block-store.prune-watcher-canonical-block-store.ts:118` (since deleted). <!-- doc-links:historical -->

In particular, the shared node/committee payload rule uses `requiredRetentionMs` to decide deletion. Its calculated `retainUntilMs`, based on configured days, is not the deletion threshold. Increasing days alone therefore does not extend those payloads' availability. Availability challenges can also run beyond the simple testing horizon: protection of headers still in the live queue is essential, including challenged headers that cannot merge until their challenge is resolved. Preserve that protection rather than treating elapsed time as sufficient authority to delete. See [shared decision, line 105](../../../demo/midgard-core/src/retention-window.da-retention-prune-decision.ts#L105) and [challenge/queue relationship, line 76](../../../demo/midgard-core/src/retention-window.assert-da-challenge-window-within-maturity.ts#L76).

## Tradeoffs and recommended implementation

Keeping zero gives indefinite history in these four tables, but makes storage grow with cumulative traffic. Matching the manifest days gives a conservative, understandable baseline and a finite recent-history window. Choosing more days costs more disk and preserves more query history; it does not itself improve the independent payload-retention rule. Choosing fewer days is rejected by the current node policy. I recommend matching the manifest for the normal devnet profile, with longer history available through an explicitly configured archive service.

Use the verified manifest as the actual input, not an unrelated literal `15`. There is a small implementation gap to address: `assertRetentionDaysMatchesDeployment` accepts a manifest value, but the current config loader calls it with only the environment value, so it compares against the compiled canonical default. A future manifest advertising more than 15 days would not automatically update this call's comparison. Generate the devnet setting from the verified manifest and validate the same value at startup. See [validator arguments, line 39](../../../demo/midgard-node/src/database/retention-policy.ts#L39) and [current call, line 543](../../../demo/midgard-node/src/services/config.make-config.ts#L543).

This decision complements A3/A4: each collection must retain what its own recovery or proof operations can still use, and must protect outstanding work. It does not authorize deleting all recovery records after 15 days, replacing rollback-depth limits with day limits, or resetting durable state. It also does not settle E3. A node offline longer than the public payload window needs an authenticated catch-up path, snapshots or an archive source; changing `RETENTION_DAYS` cannot create one. An archive should have its own capacity, retention and availability policy, and must not be an unstated prerequisite for answering a live challenge.
