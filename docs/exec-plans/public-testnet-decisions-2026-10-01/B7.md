# B7 — Kupo growth and which Cardano history Midgard must keep

Recommendation researched on 2026-10-01 against the current working tree. This
is a design recommendation; it changes no running service or configuration.

**Keep the existing wildcard, non-pruning Kupo configuration for the initial
public testnet. Do not replace it with a guessed list of Midgard addresses. The
complete solution is to separate live wallet queries from a durable store of
Midgard's required historical evidence, then narrow the live index only after
every reader can obtain that evidence independently.** This preserves valid
user orders and the ability to prove faults while removing unrelated Cardano
history from each operator's long-term storage obligation.

## What the current problem actually is

Kupo is a searchable copy of selected Cardano transaction outputs. An output is
an individual piece of a wallet's balance or contract state. Midgard uses Kupo
to find those outputs, their attached data, and the blocks that created or spent
them. Ogmios supplies the actual transaction and block history.

Both the ordinary operator compose file and the isolated process devnet use
`--match "*" --since origin` and omit `--prune-utxo`. They therefore retain
outputs belonging to the entire Cardano network, including spent outputs. This
means unrelated testnet activity increases Midgard's database forever. Narrowing
the selection reduces the growth rate; keeping all selected history still grows
with use. Deleting spent history stops that accumulation, but can also delete
data Midgard still needs.

This does not inherently crash the node today. It is an accumulating storage and
query-cost problem. Eventually exhausted disk space can stop Kupo making
progress or accepting writes, and Midgard then loses an essential data source.
Restarting services does not recover the missing free space. No measurement in
this review establishes when the current testnet would reach that condition.

The distinction is important:

| Choice | What it changes | What it does not guarantee |
| --- | --- | --- |
| `--match` | Which outputs enter Kupo's index | A fixed maximum size or retention of omitted dependencies |
| `--prune-utxo` | Deletes old spent outputs | Preservation of Midgard proof and replay evidence |
| HTTP query filters | Which already-indexed rows a request returns | Smaller stored history |
| `--since` | Where initial indexing begins | Access to relevant outputs created before that point |

Kupo accepts repeated address, credential, policy/asset, and transaction/output
patterns. Its documented pruning delays removal for rollback safety rather than
using Midgard's challenge period. The manual describes at least 36 hours/2,160
blocks; this is not a universal Midgard retention setting. `--since` starts
after the supplied block. `--defer-db-indexes` speeds initial loading by omitting
query indexes; normal serving should restart without that flag. Removing an
active pattern does not remove existing matches. These are different tools for
different problems. [Kupo v2.12 manual and API](https://raw.githubusercontent.com/CardanoSolutions/kupo/master/docs/api/v2.12.0.yaml)

The ordinary compose file currently leaves `--defer-db-indexes` enabled; the
isolated process devnet does not. Removing it after synchronization is a useful
query-performance improvement, but it is not the storage solution.

## Why a contract-address filter is unsafe with today's code

Some requirements are straightforward: find the state queue, deposits,
withdrawals, transaction orders, operator lists, bonds, challenges, correction
locks, reference scripts and funding wallets. The less visible requirements
prevent a static list from being complete.

**A user can put required order data at their own wallet.** A forced order is a
user instruction that the operator must process. Larger instructions refer to
published data or certificates instead of placing all bytes directly inside
the order. The protocol deliberately permits publication at the creator's own
wallet address, with immediate reclaim by an ordinary spend. The order mint
has already checked the bytes; reclaim does not invalidate the instruction.
Those historical bytes must remain retrievable even after their outputs are
spent. The wallet address can belong to a participant who has never interacted
with Midgard before. A raw data output can contain no Midgard asset for a policy
filter to recognize.

This is not a hypothetical future use. The current node's carriage reader
explicitly states that arbitrary creator wallets require wildcard coverage and
spent data must remain readable. See
the deployment requirements in `demo/midgard-node/src/l1-tx-order-carriage.l1-chain-point.ts` (since deleted)
and [the custody and reclaim rule in section 8.11](../../spec/midgard-tx.md).

**Relevant transactions have unrelated inputs and outputs.** The watcher's
local proof source asks Kupo for all outputs of a transaction, checks output
indices, retrieves the complete transaction through Ogmios, and resolves its
spending inputs and reference inputs. Those can include ordinary fee inputs,
change outputs, collateral, external data and reference scripts at other
addresses. Indexing only the output with a Midgard token does not satisfy the
current reader's requirements. The source also reconstructs historical address
states using creation and spending records. See
[the local raw proof source](../../../demo/midgard-fault-proofs/src/workflow/local-kupmios-http-ogmios-source.create-local-kupmios-http-ogmios-raw-source.ts),
especially `resolveTransactionInclusion`, `readTransaction`, `scanAddressPage`
and `scanUnitHistoryPage`.

The committee also retrieves spent state-queue transaction outputs and
correction-lock history. Its independent replay reader must remain supported;
it cannot rely on an operator telling it the result. See
[committee transaction replay](../../../demo/da-committee-node/src/l1/state-queue-replay-provider.parse-transaction.ts).

Consequently, turning on pruning or replacing the wildcard today can make a
valid order unreadable or prevent an honest watcher from producing evidence.
A missing Kupo result must never become proof that an event did not happen.

## The alternatives and their tradeoffs

| Alternative | Benefit | Cost or failure mode | Judgment |
| --- | --- | --- | --- |
| Keep the wildcard and spent history | Supports today's readers and arbitrary users | Accumulates unrelated L1 activity; needs capacity planning | Safest launch configuration |
| Keep wildcard coverage but enable pruning | Removes most spent history | Breaks historical carriage, replay and proof reads | Reject with current readers |
| Narrow to contracts, policies and known role wallets, without pruning | Much less unrelated history | Misses unknown user carriage and transaction dependencies; selected history still grows | Reject as a flag-only fix |
| Add patterns on demand and rewind Kupo | Can recover newly discovered dependencies | Potentially deep replay disrupts the shared provider; retries and restarts complicate completeness | Useful for an isolated backfill worker, poor primary live-provider design |
| Require all carriage at a known script or require a recognizable marker | Easier selective indexing | Protocol and user transaction changes; existing orders and arbitrary funding inputs still require historical resolution | Consider only as a separate protocol change |
| Split live queries from a selective evidence archive | Removes unrelated long-term output storage from normal nodes while keeping relevant history | Requires a new collector, recovery path, coverage checks and storage lifecycle | Best complete solution |

The Kupo maintainer explains that a newly added pattern only covers history
replayed from the requested rollback point. Earlier matching outputs remain
missing; deep rewinds of a pruned index can temporarily produce incomplete
historical states. Merely adding the user's address after seeing their order is
therefore insufficient. [Kupo maintainer explanation](https://github.com/CardanoSolutions/kupo/discussions/137)

## What the complete solution must contain

**1. A generated coverage inventory, not a manually maintained filter list.**
For each enabled reader and transaction builder, record the deployment
addresses, policies, wallets and historical lookups it uses. Generate the
ordinary patterns from the verified deployment manifest and active role
configuration. The inventory must include:

- Every deployed contract role and fault-proof catalogue role, including all
  retained deposit/withdrawal history addresses, state queue, operator lifecycle
  lists, bonds, availability challenges and correction locks.
- All applicable minting policies and authenticated reference-script outputs,
  the reference-script publishing address, and oracle/nonce dependencies.
- Operator spending and collateral wallets, watcher/prover wallets, committee
  submission/response wallets, setup funding wallets when enabled, and their
  configured change addresses.
- Arbitrary user data and certificates; all inputs, reference inputs, relevant
  transaction outputs, datums, scripts, creation/spending points and transaction
  witnesses required by ingestion, recovery, independent replay and proofs.

The first three groups can usually be selected directly. The final group must
be discovered from relevant transactions and resolved through a historical
source. It cannot be replaced by an extra guessed policy pattern. Coverage is
complete only when following every such reference finds its evidence. This
document intentionally supplies no deployable filter set: the current source
demonstrates that the arbitrary-reference requirement cannot be met by one.

**2. Independent capture of complete relevant history.** A collector follows
the locally validated Cardano chain through Ogmios, recognizes Midgard events,
and stores the full transaction data and resolved dependencies required by the
readers. It must handle chain rollback, preserve the original transaction/output
identities and bytes, and use the current canonical-chain and content checks.
Watcher, committee and node can each run this component. It must not introduce
a dependency on an operator node or make a centrally hosted archive a trusted
authority.

**3. Historical resolution that survives late discovery.** A newly observed
order may reference a data output published before indexing began and already
spent by the time a node catches up. The resolver needs an independently
reconstructible archival source, including creation transactions and their
chain locations. A pruned wildcard Kupo is insufficient. An isolated full
history replay/backfill index is a safe fallback; an archive can accelerate it
only if returned evidence undergoes the required chain and content checks.
Downloading bytes and checking a transaction hash alone does not prove its
canonical inclusion.

Historical backfill must be a durable, bounded-job workflow with visible
progress and retry, rather than repeatedly rewinding the live Kupo or scanning
from origin inside every order-ingestion request. When coverage is missing,
expose the affected operation as unavailable while recovery runs. Never
silently treat a partial result as complete.

**4. A separate live provider.** Once historical readers use that store,
live balance/input selection can use Kupo with generated patterns and pruning.
Initially keeping the live instance wildcard-pruned can simplify arbitrary
wallet coverage; narrowing comes after the inventory and new-role lifecycle
are proven. Both designs still store currently unspent outputs. Their size can
grow with active users and live balances, so neither promises a fixed disk size
independent of network demand.

**5. Storage tiers with retention derived from actual obligations.** Keep
challengeable blocks, unresolved orders/disputes, in-flight signed transactions,
live reference dependencies and rollback/recovery history in fast local
storage. Move older completed evidence to a compact archive when it is no
longer needed by those operations. Delete only evidence whose future replay,
proof and recovery requirements are discharged by a verified replacement or an
explicit protocol rule.

In particular, an old data output can still be required by a live order. Age
of the output and age of its spend are not sufficient deletion conditions.
Midgard's DA retention period, its watcher rollback limit and Kupo's L1 pruning
delay cannot be substituted for one another.

The current specification treats these bytes as permanent L1 history. A
selective archive will therefore still grow with relevant Midgard history
unless another protocol decision bounds that obligation. The achievable
improvement is a bounded working history plus explicit archival capacity, and
removal of unrelated whole-Cardano output history from every normal node.
It would be misleading to promise constant total storage using flags alone.

**6. Deployment and role changes are first-class events.** Persist the
inventory, its version, the earliest required chain point and backfill
completion. Before enabling a new wallet, operator, committee member, contract
role or deployment, establish its coverage and catch up through the activation
point. A wallet funded before activation needs its funding outputs indexed too.
Preserve old deployment coverage until its unsettled activity and recovery
requirements have finished. Do not remove a pattern just because a role left
the active set. Restarting after an interrupted update must resume the coverage
work rather than claim completion because the pattern now exists.

## What I would do for public testnet

Launch with the present wildcard, non-pruned provider and an explicit storage
plan. Record database size and filesystem free space, measure growth over a
representative interval, and alert on projected exhaustion early enough to
expand or migrate storage. Use a dedicated volume so Kupo cannot consume the
disk reserved for Midgard's own durable state. No arbitrary lifetime fuse or
automatic history deletion should turn a capacity issue into a safety issue.
Ensure query indexes are enabled after initial catch-up.

For a node joining an existing deployment, do not assume the official pruned
Kupo snapshot is sufficient. The current bootstrap explicitly documents that
outputs spent before its snapshot point are absent. It recommends origin mode
for deployments predating that snapshot. Even a deployment created after the
snapshot is not, by itself, proof that every externally published carriage
dependency was created afterward. The coverage requirement is the oldest
needed dependency, not simply the deployment's initialization time. See
[the bootstrap modes](../../../demo/midgard-node/scripts/bootstrap-kupo-snapshot.sh).

Build the evidence store and historical resolver before changing the provider
flags. Run the new provider alongside the current one and compare complete
order ingestion, committee replay and watcher proof construction at the same
chain points. Exercise unknown creator wallets, reclaimed carriage, earlier
publication than initialization, fee/change outputs, arbitrary reference inputs,
old deployments, role rotation, downtime catch-up, rollback and interrupted
backfill. Turn on pruning/narrowing only after those paths succeed and the
storage inventory reports complete coverage.

This does not require changing the forced-order protocol. It costs more
engineering than a compose-file edit, but directly addresses the actual
problem: Midgard needs selected durable evidence while today's provider stores
an entire network's output history to obtain it. Capacity planning protects the
testnet during that work; the selective archive fixes the ongoing scaling
burden.
