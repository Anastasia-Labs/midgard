# A2 — What an unresolved foreign block should do to readiness

**Recommendation:** distinguish evidence still being collected from work that cannot safely proceed. Report the unresolved-record count as a detail, but keep the node unready when an unresolved foreign block actually prevents safe block production or settlement. Do not make the current count informational by itself: the current source still uses those records to stop commit attempts.

**Direct answers:** this readiness condition does not itself crash the node. It makes `GET /readyz` return HTTP 503, meaning “not ready.” A separate safety check can defer block production while the process remains running. Demoting the readiness reason changes the status response; it does not fetch missing block data, complete foreign-block processing, prevent unrelated crashes, or restart stalled production.

This is a source-based assessment dated **2026-10-01**, against checkout HEAD `3027be19cb3bc740f83af0e155e34ab38c7cf894`. No code was changed and no tests or live failure reproduction were run for this item.

## What the terms mean

A **foreign block** in this discussion is a block outside the local candidate the node expected to follow, commonly from another operator. The recording path detects a different header; it does not itself establish who submitted it or that anyone misbehaved. The **tip** is the latest block it is trying to follow. A block **header** contains compact commitments to the block's contents; the **payload** contains the actual contents needed to check those commitments and apply the block.

When the node prepared work on one block but subsequently encounters a different confirmed tip, it saves a **reconciliation record**: a durable reminder to establish what the foreign block did before reusing local pending work. The record retains the foreign header, the previous base, its time interval, the commitments to deposits, forced transactions and withdrawals, and the current evidence and resolution status. It starts as `awaiting` with reason `pending_evidence`. This is recovery bookkeeping, not proof that another operator did something wrong. See [the mismatch recording call](../../../demo/midgard-node/src/fibers/speculative-commit-builder.persist-authenticated-foreign-tip-mismatch.ts#L197) and [the record's initial contents](../../../demo/midgard-node/src/database/foreignTipReconciliations.record-mismatch.ts#L199).

The bookkeeping exists to avoid processing a deposit, withdrawal or forced transaction twice. For example, if another operator already included a deposit, this node must learn that before deciding to include the same deposit itself. Missing evidence means “we cannot yet determine what happened,” rather than “it did not happen.”

**Liveness** means the service can make progress. `/healthz` checks whether the HTTP server is running. **Readiness**, reported at `/readyz`, checks whether the node considers itself able to provide its intended service. An **informational detail** can appear in the readiness response without changing its `ready` flag or HTTP status. A **hard readiness reason** adds a reason that makes the flag false and the HTTP status 503. Neither term means process termination.

## What the current source actually does

The readiness handler counts every database row whose status is `awaiting`. It does not distinguish an old record from the current chain, missing evidence from invalid evidence, or a harmless backlog from an active production hold. Any positive count creates `foreign_tip_reconciliation_awaiting:<count>`, sets `ready=false`, and returns HTTP 503. The existing unit-test source explicitly expects this result for two unresolved records. See [the database count](../../../demo/midgard-node/src/database/foreignTipReconciliations.mark-resolved.ts#L78), [the readiness rule](../../../demo/midgard-node/src/commands/readiness.ts#L87), [the response status](../../../demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts#L410), and [the test assertion](../../../demo/midgard-node/tests/readiness.test.ts#L68). The test was read, not executed.

The same response already includes `awaitingForeignTipReconciliations` as a field. Therefore, demotion can retain visibility without inventing a separate endpoint. The handler also already reports settlement health separately, with an explicit comment that a payout delay should not remove healthy transaction admission from service. See [the settlement distinction](../../../demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts#L276) and [the existing count field](../../../demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts#L348).

There is also a separate production check. On the ordinary commit path, the node reviews retained foreign-tip evidence. That review returns the first unresolved result, and the commit worker returns `AwaitingForeignDaOutput` before proceeding with a new commit. The caller logs a warning and continues through normal output handling. This is a deliberate refusal to do unsafe work, not a thrown error or process exit. See [the retained-history review](../../../demo/midgard-node/src/workers/t2-foreign-event-reconciliation.reconcile-overdue-awaiting-events-against-retained-foreign-tips.ts#L125), [the early commit return](../../../demo/midgard-node/src/workers/commit-block-header.database-operations-program.ts#L567), and [the warning-only output branch](../../../demo/midgard-node/src/fibers/block-commitment.build-and-submit-commitment-block-action.ts#L523).

An unresolved result has several meanings:

| Situation                                           | Why the node waits                                                                                    | What changing readiness would accomplish                       |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Required payload is missing                         | It cannot check which events the foreign block included.                                              | Changes the reported status; supplies no evidence.             |
| Available evidence is invalid                       | The payload does not match the authenticated header, roots or counts, or cannot be decoded correctly. | Changes the reported status; does not make that evidence safe. |
| Payload proves a pending event was already included | The node needs foreign-block finalization before safely accounting for the event locally.             | Changes the reported status; does not implement finalization.  |

These are explicit result categories in [the resolver](../../../demo/midgard-node/src/workers/t2-foreign-event-reconciliation.resolve-t2-foreign-event-evidence.ts#L165), including the [foreign-finalization hold](../../../demo/midgard-node/src/workers/t2-foreign-event-reconciliation.resolve-t2-foreign-event-evidence.ts#L248). They all become `awaiting` records with a stored blocking reason; [the update](../../../demo/midgard-node/src/database/foreignTipReconciliations.mark-resolved.ts#L291) preserves that distinction in text, but the readiness count ignores it.

The proposed DA client in A1 helps the missing-payload case. It does not automatically solve invalid evidence or the case where the foreign block included an event and must be finalized. Giving up a download must not be treated as evidence that a block was empty or that an event was absent.

## Does this take the whole service down?

The process can remain running and its HTTP server can keep answering. `/healthz` simply returns an `ok` response. The router registers readiness, query, deposit-building and transaction-submission handlers independently, with no global readiness check around them. Thus a failed `/readyz` probe does not itself force every request to return 503. The submission handler still has its own validation and capacity limits. See [health handling](../../../demo/midgard-node/src/commands/listen-router.post-tx-status-batch-handler.ts#L204), [the router](../../../demo/midgard-node/src/commands/listen-router.build-listen-router.ts#L137), and [submission processing](../../../demo/midgard-node/src/commands/listen-router.post-submit-handler.ts#L56).

Operational consequences depend on who consumes readiness. The checked-in node Compose configuration probes `/readyz` for its health check, so persistent 503 responses fail that check. A deployment that routes traffic only to ready nodes could consequently remove this node from service, even while it can still accept requests directly. The new full-stack startup code also waits on the readiness endpoint. See [the Compose probe](../../../demo/midgard-node/docker-compose.yaml#L39) and [the full-stack readiness poll](../../../demo/midgard-node-tools/src/full-stack/runtime.ts#L63). Actual restart or traffic-routing behavior in a deployed environment was not inspected or exercised here.

Other failures in this area can return database or integrity errors. Those are separate from an ordinary `awaiting` result; this review does not establish that all such errors are harmless or that the entire node is crash-free. Repeatedly restarting the ordinary waiting case would not manufacture missing evidence.

## A material correction to the decision memo

The memo says an unresolved row “withholds no block” and that its 503 is “pure liveness loss.” That is **not true of the current checkout**. Required foreign payloads remain necessary even when no candidate events are locally visible, and the retained-history review returns an unresolved result without a narrower event-window exception. See [the explicit payload requirement](../../../demo/midgard-node/src/workers/t2-foreign-event-reconciliation.resolve-t2-foreign-event-evidence.ts#L157) and the commit early return cited above.

The memo also mentions `pendingFinalizationAgeDetail` as an existing pattern. That symbol was not found in the current checkout. The settlement detail described above is the current example. Treat the memo's later-wave implementation statements as unverified until they are reconciled with the actual code to be deployed.

## Alternatives and their tradeoffs

**Keep every unresolved row as a hard reason.** This is conservative and reflects the present ordinary commit refusal. It also lets background or historical bookkeeping decide the readiness of all service capabilities, without proving that each record prevents useful work. A single persistent row keeps the probe red. It is a defensible interim behavior while the existing production gate remains this broad.

**Demote every unresolved row immediately.** This is small and avoids a failed probe based only on record count. It preserves consensus safety if the independent production checks stay intact. But it can announce a ready node that repeatedly refuses block production, hiding the exact failure the owner wants unattended operations to detect. It is insufficient in the current checkout.

**Report backlog separately from actual capability holds — recommended.** Keep the count, oldest unresolved age and reason breakdown visible. Determine whether the node can safely produce or settle blocks from the actual active chain and execution gates. Make a genuine safety hold a named readiness reason. Retain the ability to serve safe queries and, within existing capacity limits, accept durable submissions while held. This needs more plumbing than deleting one condition, but provides a truthful operational signal without weakening block verification.

In a larger deployment, separate readiness for serving user requests from readiness for operator duties. For the current single combined endpoint, keep it unready during an actual production or settlement hold and include capability details explaining what still works. Treat `/healthz` as the process-liveness signal; do not use the existence of this recoverable hold as a reason to shut the process down.

## Safeguards and acceptance conditions

The runtime that refuses work should publish why it is held, with the relevant header and when the hold began. A background row count should not substitute for that state. Re-evaluate the hold when the payload arrives, the foreign block is safely finalized, or authenticated chain evidence removes the dependency. Clear it only when the condition truly clears. Never clear a safety hold merely because a retry budget expires, the record becomes old, or a retention job deletes bookkeeping.

Before adopting the revised policy, execute checks showing that a harmless background record can be reported without failing readiness; missing evidence that actually blocks production remains unready; invalid evidence and the foreign-finalization case stay held; recovery clears the hold; and healthy request paths remain usable while unrelated operator work is held. Also test each HTTP status through the real router and the deployment's probe consumer. These are proposed acceptance conditions, not completed tests.
