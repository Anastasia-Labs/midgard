# B3 — Should service wallets refill automatically?

Recommendation, 2026-10-01: allow an explicitly enabled, bounded refill service for private test runs. For the public testnet, use a separate wallet containing a limited operating budget, with automatic transfers only to approved service addresses. Keep the larger reserve outside the service hosts. Do not deploy an unrestricted refill loop holding the original funding key, and do not make either test funding or treasury funding part of the node's default behavior.

This is a proposal for a funding design, not an implemented or tested refill service.

## What the question means

Midgard has several wallets because different jobs need to send Cardano transactions. One wallet runs operator operations, another pays for merge transactions, another supports settlement, and others support proving faults or challenging unavailable data. A wallet is an account controlled by a secret signing key. It needs available ADA to pay fees and supply the outputs required by transactions. Separate keys keep these responsibilities separate.

The proposed loop means: periodically inspect these wallets; if a wallet lacks enough money for its job, send it more from a central funding account. For example, an operator may remain correctly registered but its merge wallet may eventually lack the money needed to submit the next merge. Automatic funding could restore that capability without requiring someone to transfer ADA by hand.

The current Preprod configuration names nine roles, including test users and recipients. Those test accounts are different from service operating accounts; a public deployment should not automatically replenish arbitrary user accounts. The code rejects roles sharing a payment key. Evidence: [config.ts:130–149](../../../demo/midgard-node-tools/src/full-stack/config.ts) and [wallets.ts:11–23](../../../demo/midgard-node-tools/src/full-stack/wallets.ts).

This is separate from B2, replenishing a security bond, and A10, registering a removed operator again. A bond is money locked under protocol rules and potentially taken away after a fault. Ordinary wallet balances can decline through legitimate fees or money being moved into required transaction outputs. Funding a wallet must never automatically refill a slashed bond or authorize registration after removal. Your B2 and A10 decisions continue to apply even when an operator wallet receives more operating money.

Some ADA required by a transaction is retained in outputs or reserved as collateral rather than spent as an ordinary fee. Here, collateral means a suitable separate ADA output available for a script transaction's failure rules. A large total balance alone therefore does not establish that the wallet can perform its next job.

## What the code does now

The source question refers to a **local Cardano test chain** whose initial funding account is controlled by a generated signing key. “Genesis key” in this funding path means the key for its initial spendable funds, specifically `utxo-keys/utxo1/utxo.skey`; this is not a proposal to use a Cardano governance key.

The local generator creates that key and the initial distribution: [generate.sh:65–75](../../../demo/midgard-node-tools/devnet/phase4-process/scripts/generate.sh). Bootstrap then calls a funding script: [bootstrap.sh:43–47](../../../demo/midgard-node-tools/devnet/phase4-process/scripts/bootstrap.sh). The script creates transfers to seven distinct role addresses, giving each 9,990 ADA plus a separate 10 ADA output. It selects funds from the initial account, signs with its key, submits, and checks confirmation. Those are fixture amounts, not measured operating budgets or recommended public-testnet allocations. Evidence: [fund-wallets.sh:11–55](../../../demo/midgard-node-tools/devnet/phase4-process/scripts/fund-wallets.sh).

That script is initial provisioning, not a recurring balance-based refill service. It does not first calculate the shortage in each recipient wallet; invoking it again builds another fixed transfer. Reusing it as a maintenance loop would therefore repeatedly spend the reserve even where a wallet needed no funding. The isolated-chain documentation also warns against casually repeating the wider bootstrap on an initialized chain: [README.md:35–42](../../../demo/midgard-node-tools/devnet/phase4-process/README.md).

The current, uncommitted Preprod stack takes a different approach. It checks externally funded wallets: before initialization it checks configured budgets, and after initialization it checks a 5 ADA minimum. It also requires a plain ADA output of at least 5 ADA. It throws an error when those conditions fail; this path does not send a refill transaction. These minimums demonstrate the current checks, not that 5 ADA covers every service's worst-case task. Evidence: [deployment.ts:55–95](../../../demo/midgard-node-tools/src/full-stack/deployment.ts) and [PREPROD_STACK.md:35–40](../../../demo/midgard-node-tools/docs/PREPROD_STACK.md).

A Midgard deployment on public Cardano Preprod does not get the generated funding key from our private chain. Public testnet wallets can receive test ADA from the official faucet or another funded wallet. The official [Cardano faucet documentation](https://docs.cardano.org/cardano-testnet/tools/faucet/) and [network selection guide](https://developers.cardano.org/docs/get-started/testnets-and-devnets/) describe this public-testnet funding route. Consequently, “from the genesis key” is a local-test convenience; the comparable public deployment design is transfers from an ordinary, deliberately funded treasury wallet.

## Why an unrestricted loop is risky

To sign transfers automatically, a process must have access to a signing key or to a signer authorized to approve its requests. If it holds the unrestricted reserve key and that host is compromised, the attacker can authorize transfers from the reserve. Application settings such as “at most 100 ADA per day” do not prevent an attacker using the key outside that application. Keeping only a limited amount in the online funding wallet imposes a real limit on the funds that key can spend.

Even without compromise, a coding bug, stale balance observation, duplicate retry, or rapidly draining recipient can keep triggering transfers. A refill loop can conceal abnormal spending until the source wallet is empty. Sending more money to a stolen recipient key also gives the attacker more to take. Monitoring spending and pausing suspicious refills matters alongside the normal low-balance check.

Test ADA does not represent a mainnet financial reserve, but draining it can still stop the testnet, interrupt fault proving, and invalidate an endurance experiment. Production uses valuable ADA and therefore needs a stronger separation between the online operating budget and the larger reserve. The same wallet architecture can be rehearsed on the public testnet.

## Options and tradeoffs

| Choice | Benefit | Cost and limitation |
| --- | --- | --- |
| Fund once, alert when low | Smallest implementation; no extra reserve key online | Someone eventually transfers more; choose enough initial funds for the expected run |
| Refill directly from the local initial funding account | Convenient for isolated tests | Gives the maintainer access to that account's reserve; unsuitable as the default public deployment model |
| Refill from a limited operating wallet | Routine fee depletion recovers automatically; reserve exposure is bounded | Needs a separate maintenance process, durable accounting, and periodic replenishment of its finite budget |
| Larger reserve with an independently enforced signing policy | Can support larger deployments with restricted destinations and spending | Adds signer operations and security review; a shared unrestricted seed would defeat the restriction |

I recommend the third option for a public testnet. Initial funding plus alerts remains a reasonable first release if a measured budget covers the intended test period. The fourth option is a later operational choice when scale justifies it, not a prerequisite for a small public launch.

## What the recommended service must enforce

The maintenance process should be separate from the operator, watcher, and committee processes. They should not receive the funding wallet's key. It should have these explicit rules:

1. **Approved destinations and purposes.** Fund only configured service addresses for the identified deployment and Cardano network. Test-user funding belongs to an explicitly separate test or faucet budget. Contract publication and first registration are setup expenses, not routine recurring refills.
2. **Measured low-water and target balances per role.** Transfer only the amount needed to reach the target, with fees included in the source budget. Preserve the required separate collateral output. Derive proving/challenge reserves from complete task costs, not the current 5 ADA startup check. Choose thresholds early enough that a funding transaction can confirm before urgent work needs the money.
3. **Finite spending authority.** Set a maximum transfer, a per-role budget over a stated period, and a cumulative deployment budget that survives process restarts. Keep only that limited reserve available to the online key. A cumulative cap deliberately requires a new allocation eventually; no finite reserve can fund positive fees indefinitely.
4. **Reconcile before repeating.** Record the intended transfer and signed transaction durably; after a timeout or restart, determine whether that transfer landed before authorizing another. Fresh observations must distinguish “wallet is empty” from “the provider is unavailable.” Count pending transfers and reserved funds when deciding whether another transfer is needed.
5. **Bounded recovery and clear signals.** Retry temporary provider failures with a delay and a limit. Emit source reserve, spending rate, pending transfers, and budget exhaustion. A depleted budget or unexplained drain calls for attention, not a process restart or an unlimited refill. Mark the operations that lack funds unavailable while continuing to expose health information and recover automatically once confirmed funds arrive.

There is no measured refill threshold or burn rate in this assessment. Before choosing ADA amounts, measure ordinary fee spending and the maximum complete urgent workflow for each role under the deployed parameters. A public testnet should explicitly fund the fault-proving reserve as well as routine operator operations.

The decision to adopt is therefore: **approve bounded automatic replenishment of service operating money, using an isolated funding wallet; retain manual or separately controlled allocation of the larger reserve; keep all bond recovery and removed-operator registration outside this mechanism.**

## Evidence and limits

Read-only inspection on 2026-10-01 covered the supplied request/context, the repository and devnet instructions, production principles, verification guidance, the initial-chain generator and funding/bootstrap scripts, and the current dirty Preprod wallet/configuration/deployment paths. The dirty stack files were read only. The official Cardano pages above were consulted for the public faucet route.

No service was started, no secret contents were read, no funding transaction was built or submitted, and no runtime behavior or spending rate was measured. No code was changed. Runtime acceptance, wallet transaction tests, and deployment checks were not run because this task produces a decision document only; they will be required for an implementation touching those flows. The proposed duplicate-transfer and budget protections have not been tested.
