# E3 — rejoin from a verified checkpoint, keep history in separate archives

Recommendation, 2026-10-01: choose **state checkpoint recovery plus a separate archive service**, with a defined recent-history guarantee. Normal nodes should recover current state from an eligible checkpoint and replay the bounded history after it. Independent archives should preserve historical block inputs for full verification and older queries. Recent state, challenge evidence and unfinished settlements must remain available for their actual safety deadlines.

Do not make “restart from genesis” the response to a long outage. Reinstalling cannot recreate bytes that every holder deleted. Do not make every ordinary operator retain all history forever either: that makes storage costs rise for everyone and eventually prices out participation. Separate current operation, challenge support and historical verification.

This complements A6's proposal to publish execution inputs each block and complete checkpoints separately. It also requires E1's shared peer-block import path. A checkpoint download without event reconciliation or a reviewed checkpoint trust rule is an incomplete solution.

## What has actually gone missing

An offline node can miss peer-produced blocks. It returns with a local ledger and pending deposits, withdrawals or forced transactions referring to earlier history. The network has advanced, and its old payloads may have been pruned after the agreed safety period. The node cannot simply apply a newer block to its old ledger.

Current ledger reconstruction follows locally recorded parent journals. It explicitly refuses if the required parent journal is missing. Foreign-base selection searches local candidate roots and otherwise refuses with “Awaiting authenticated foreign ledger finalization before rebuilding.” Neither path implements importing a portable checkpoint. [Parent-journal dependency](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/transactions/state-queue/confirmed-ledger-snapshot.ts:211), [foreign-base refusal](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/commit-block-header.resolve-commit-base-ledger-entries.ts:291).

There is an important qualification to the older scenario: committee retention exempts the **current confirmed head** and live queued headers, in addition to retaining challengeable data. A former confirmed head can become prunable after a newer one takes its place; the current head is protected by that rule. Today's payload includes the resulting full ledger, as A6 establishes. Therefore a correctly available latest confirmed-head payload could supply current ledger entries even when the missed intermediate payload vanished. That is a useful interim recovery source, not proof that the complete recovery path exists. [Committee retention exemptions](/home/gumbo/midgard-hub/midgard/demo/da-committee-node/src/store/retention.ts:16), [A6's state-format analysis](/home/gumbo/midgard-hub/midgard/docs/exec-plans/public-testnet-decisions-2026-10-01/A6.md:20).

Ledger state is only part of the problem. The node separately reconciles overdue user events against foreign payloads, and an unresolved payload dependency produces `AwaitingForeignDaOutput`. A current ledger cannot reveal that an old deposit was included if its resulting output has since been spent. Losing that distinction can duplicate an event or hold it indefinitely. [Foreign event reconciliation](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/t2-foreign-event-reconciliation.reconcile-retained-foreign-tip-entry.ts:82), [commit hold](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/commit-block-header.database-operations-program.ts:567).

## A checkpoint has two different guarantees

First, **is this exactly the state committed at the chosen chain point?** Fetch complete entries, rebuild the ledger tree and compare its root with an independently authenticated Midgard root on Cardano. Check the exact deployment, protocol version and block identity. This rejects missing entries, changed values and a snapshot for another network. Individual chunk hashes are also checked, but a manifest supplied by the same untrusted server cannot authorize an arbitrary state root.

Second, **was the execution producing that root correct?** Root matching cannot answer this. Cardano authenticates the accepted Midgard commitment; it does not execute every L2 transition. Committee availability signatures promise access to bytes, not correct execution. The specification says that hashed contents are not validated merely because their header is on L1. [Protocol security](/home/gumbo/midgard-hub/midgard/technical-spec/C-considerations/3-protocol-security.tex:43).

There are two defensible adoption policies:

- **Full historical verification:** begin from genesis or a state this operator previously verified, obtain all necessary inputs and independently execute to the target. This preserves the strongest local assurance, but requires historical availability and more time.
- **Protocol-settled checkpoint adoption:** accept an authenticated, sufficiently stable confirmed checkpoint under Midgard's stated optimistic-security assumptions: correct fault-proof coverage, available data throughout the dispute period, and an honest capable challenger. Then independently execute everything after that checkpoint. This is much faster but does not retrospectively validate every prior transition.

I recommend implementing both, with **settled checkpoint adoption as the intended normal recovery mode only after the protocol explicitly authorizes it**. The checkpoint source need not be trusted to change the ledger, because the root is independently checked. The correctness of the historical root still relies on the settlement assumptions. Operators must record which mode established their starting state. A known fraudulent state never becomes acceptable merely because time passed or a committee signed its snapshot.

This matters for E2's rule against extending fraudulent ancestry. The checkpoint rule must specify which settled starting points an honest operator may extend, and how known invalid ancestry is handled. If current policy requires local validation of all ancestry, a snapshot cannot quietly override it. Until that policy and fault-proof coverage are resolved, operator recovery uses its own previously verified anchor plus archive replay. This note does not certify the existing settlement machinery or proof coverage as sufficient.

Cardano finality is also probabilistic. Eligibility must bind the merge transaction and relevant history to an authenticated chain point and the configured stability policy, not just an elapsed timestamp or “merged” database field. Recovery after a rollback remains necessary. [L1 finality requirements](/home/gumbo/midgard-hub/midgard/technical-spec/C-considerations/3-protocol-security.tex:11).

## What the recovery package must contain

A checkpoint should be a canonical, portable protocol artifact rather than a copy of one operator's entire private database. Its manifest identifies the deployment, protocol rules, settled header and Cardano chain point; the ledger root; complete entry count; ordered chunk commitments and byte bounds; relevant event-state commitments; and the replay interval it supports. Large checkpoints use bounded chunks without inheriting the normal per-block total-frame ceiling.

The imported state must cover every item that affects future validity: complete unspent outputs with their exact output references, values, scripts and datum material; authenticated execution parameters; the L1 event-processing position; pending settlement capabilities; and authenticated information proving which events were already applied. A full ledger is not a full node database.

For events, use **a protocol-authenticated consumed-event set or cumulative commitment**, together with exact L1 origin identities, inclusion receipts and any exceptions still pending. A consumed-event marker, sometimes called a nullifier, says that one uniquely identified event has already been used. Alternatively, reconstruct this information from authenticated L1 history and committed block inclusion proofs. Choose the representation during protocol design; do not trust a provider's ordinary list of “processed” event IDs.

A time cursor alone is insufficient unless the protocol proves every event before it was handled exactly once and binds omissions or exceptions. An absence proof is needed where the node intends to reapply a formerly pending event. For already-applied events, preserve ancestry and inclusion evidence connecting their block to the surviving settled history. If those commitments do not currently exist, the initial implementation needs retained replay evidence; adding an unauthenticated event-status field to a snapshot does not close the gap.

Watcher state needs its own reconstruction rules. The existing watcher checkpoint explicitly describes structural storage as insufficient for event admission or challenge authority. Its archive reader refuses missing or mismatching declared objects. Reuse that discipline, without treating its local checkpoint as an already-complete network sync protocol. [Checkpoint authority boundary](/home/gumbo/midgard-hub/midgard/demo/midgard-watcher/src/storage/user-event-checkpoint.ts:47), [required archive objects](/home/gumbo/midgard-hub/midgard/demo/midgard-watcher/src/storage/user-event-checkpoint.ts:316).

Do not import another operator's signed transaction intents, keys, wallet reservations or unpublished decisions. Recover this operator's existing intents against authenticated history, preserving original signed bytes. Install imported derived state in a separate generation, then atomically switch only after root, event-state and continuity checks. A crash leaves either the old complete state or the new complete state. Readiness stays false for producing blocks until recovery catches up; retained-data serving can continue where safe.

## Retention must serve three separate promises

**Recent safety tier.** Keep the complete input history, operator-claimed traces, scripts, historical ledger/output material and proof witnesses for every still-disputable block. Retain a checkpoint at or before the earliest starting state needed for those disputes. A current snapshot omits outputs already spent, so it cannot replace this material. Also retain what is required for the supported rollback depth and pin evidence for live disputes and unfinished settlements until their obligations resolve. Derive deadlines from the active deployment rather than giving every table the same age.

**Recovery tier.** Keep multiple verified settled checkpoints and a gapless replay interval after each advertised recovery anchor. Publish a successor, verify it is retrievable from independent holders and confirm continuity before retiring the older anchor. Derive checkpoint cadence and replay retention from the promised maximum checkpoint age, download time, replay time and outage margin. Pruning must not leave a gap between a checkpoint and the earliest available input. An admission-controlled recovery lease can protect a bounded session from concurrent deletion; a stalled client cannot pin storage forever.

**Historical tier.** Preserve complete published block inputs, header/merge ancestry, relevant L1 origin evidence, exact execution rules and code, and hashes/manifests from genesis in immutable archive segments. At launch, provide at least two independently operated retrieval sources and regular complete-segment retrieval checks. Signed promises and checksums help accountability and integrity; only actually available bytes provide recovery. Extra operators may mirror the same content without becoming authorities over its meaning.

Historical archive is not necessarily an always-running database of every past state. Compact inputs plus periodic checkpoints permit replay on demand. Faster historical proof queries may justify a separate retained tree-node index. That index has a different cost and retention promise from old block inputs.

A full lifetime archive cannot have fixed total storage forever while the chain keeps creating data. “Bounded archive” must mean bounded processes, segment sizes, local caches, concurrent work and explicitly funded storage growth. A finite rolling archive is acceptable only when its published guarantee says older history is unavailable or older segments have been handed to a durable successor. It cannot simultaneously promise genesis verification forever.

I recommend a rolling local archive cache backed by durable, segmented cold storage, with public manifests and multiple mirrors. Ordinary operators carry the recent safety tier and current recovery basis. The archive service funds lifetime input retention, while historical-state query providers choose whether to pay for faster indexes. Archive failure should prevent new history guarantees and trigger repair; it must not silently erase the last copy required for an advertised promise.

## Costs and measurable guarantees

The main cost variables are average published bytes per block, blocks per day, checkpoint size and cadence, replica count, proof-index size, and recovery traffic. A simple estimate is:

`recent input storage = average block bytes × blocks per day × retention days`

`checkpoint storage = checkpoint bytes × retained checkpoint count`

`archive growth per day = average block bytes × blocks per day × replica count`

Add historical proof storage and transfer costs separately. Copies sharing one failure domain do not provide independent durability.

For illustration only, one MiB per block every ten seconds is about **8.44 GiB per day**, or **253 GiB over thirty days** before indexes and replication. This is arithmetic, not a Midgard measurement. Repeating a large full-state snapshot every block makes that rate depend on total state growth; A6's input-only publication avoids that multiplication. Periodic checkpoints still grow with the live state, which is why cadence must be measured rather than fixed to every block.

Define the service promise in observable terms: oldest supported recovery anchor, oldest historical input, earliest available proof state, maximum advertised checkpoint age, complete replay coverage, independent mirror count, and last successful retrieval drill. Measure checkpoint download, tree reconstruction, event reconciliation and replay separately. Recovery must outpace current production or the node never finishes; publish performance for specified hardware and network conditions. Do not announce a dollar budget or sync-time target until representative measurements and provider quotes exist.

## Alternatives and rollout

| Choice | Benefit | Limitation | Decision |
| --- | --- | --- | --- |
| Longer retention on every operator | Easy bridge while recovery is built. | Moves the outage boundary and increases everyone's costs; still fails after a sufficiently long outage. | Temporary measure only. |
| Archive replay only | Independent execution from a previously valid anchor or genesis. | Slow on mature chains and depends on archive availability. | Keep as strict verification and fallback mode. |
| Snapshot only | Fast current-ledger recovery. | Does not restore event history, old proofs or independently verify historical execution. | Insufficient alone. |
| Redeploy from genesis after the window | Superficially simple operating rule. | Cannot work if inputs are gone; redeploying protocol state would be a destructive reset. | Reject. |
| Eligible checkpoint plus recent replay and independent archives | Fast rejoining, bounded ordinary-node history, retained auditing and proof support. | More protocols and explicit availability/trust obligations. | Recommended. |

Start public-testnet work with the shared authenticated importer, exact event reconciliation and archive retention of current inputs. Today's latest-head full-state payload can be an interim checkpoint source where its size still fits. Then deploy portable chunked checkpoints and the A6 input format together, with settlement eligibility and event commitments reviewed before making checkpoint mode the normal operator path. Do not remove old format-dependent proof material before replacement challenge construction works.

The decisive acceptance drill is a node offline beyond local retention while several operators continue producing and pruning normally. Delete no required canonical history. On return, it must recover through checkpoint and retained replay, reconcile old user events exactly once, recover its own pending signed operations, and resume production. Repeat with one mirror unavailable, interrupted downloads, a bad snapshot, missing proof history, a rollback of the target merge, and a crash during installation. Also demonstrate strict historical replay from archive and challenge construction for the oldest still-disputable block after pruning. These are proposed requirements, not results obtained here.

## Evidence and limits

Read-only source inspection used `rg`, `sed` and numbered `nl` excerpts from the repository root on 2026-10-01. Primary documentation linked above was consulted on that date. Some exploratory filename globs did not exist; the actual foreign-reconciliation and checkpoint paths were subsequently located and read. Only this recommendation document was changed for E3.

No implementation tests, builds, live outage/pruning/recovery drills, performance measurements, archive-cost quotes, or settlement/ancestry soundness audit were performed. The existing confirmed-head retention and local checkpoint types are source facts; a complete distributed checkpoint importer, authenticated event-state snapshot and historical archive availability guarantee are proposals. Committee-signed snapshots were not treated as validity proofs. No protocol redeployment or state reset was performed.
