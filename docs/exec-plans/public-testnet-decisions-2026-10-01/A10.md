# A10 — Stop an operator after authenticated removal

Implemented: the operator first becomes unready and stops new duties when its key is authoritatively missing from the current active directory. It shuts down after a separately authenticated, finalized ledger point confirms removal. Registration and fresh bond spending remain explicit operator commands.

The membership monitor runs even when the inactivity watchdog is disabled. This separates monitoring this node's own eligibility from deciding whether to take over another operator's overdue shift. An ordinary registered operator waiting for activation remains unready without shutdown. An absent key with no retained evidence of previous activity is unknown, rather than declared removed. Only authenticated removal, pending finality or confirmed, holds duties. A failed, stale or malformed check changes nothing: the node keeps its last authenticated state, so a transient provider fault can neither stop an active node nor lift a removal. An `unknown` result never lifts a pending removal either; only an authenticated `active` or `awaiting_activation` does. Before its first authenticated check the node is unknown: `/readyz` lists `operator_membership_unavailable` among its `details` and stays ready, since no duty waits on that check. ## Evidence and restart behavior

Kupo supplies candidate references only. Four policy-scoped queries have the configured provider timeout; only the deployment hub NFT and the three directories' root/node assets are selected. Unrelated donations cannot turn an otherwise valid check into a missing-output failure. Ogmios acquires the history owner's exact head on a newly authenticated Shelley-genesis socket, authenticates the deployed hub, and returns the candidate outputs from that single state. The monitor decodes every node, verifies singleton NFTs and the correct root, and follows each complete root-linked list. Missing roots, spent candidates, missing successors, duplicate/disconnected nodes and malformed datums refuse the proof. A partial indexer result alone never proves absence. See [candidate selection, line 289](../../../demo/midgard-node/src/fibers/operator-membership.ts#L289), [directory validation, line 49](../../../demo/midgard-node/src/fibers/operator-membership.ts#L49), [exact-reference reader, line 160](../../../demo/midgard-node/src/l1-ledger-snapshot.ts#L160), and [bound socket and hub validation, line 422](../../../demo/midgard-node/src/l1-event-history-source.ts#L422). Ogmios documents [acquired ledger states and output-reference queries](https://ogmios.dev/mini-protocols/local-state-query/).

Migration 3 adds `operator_membership_observations`, keyed by verified manifest ID and operator key. Every authenticated active observation refreshes its block hash, slot and height. A restart can therefore recognize a removed key even when slashing removed it from both active and retired lists. Before using that record, the monitor calls the real retained-ancestry check. A rolled-back observation, including an orphan that aged below the anchor, cannot prove previous activity. See [migration](../../../demo/midgard-node/src/database/migrations/sql/0003_operator_membership.sql#L1), [registry, line 30](../../../demo/midgard-node/src/database/migrations/index.ts#L30), [ancestry check, line 170](../../../demo/midgard-node/src/fibers/operator-membership.ts#L170), and [canonical reader, line 305](../../../demo/midgard-node/src/database/eventHistoryJournal.load-locked.ts#L305).

An installation upgrading after it was already slashed may have no authenticated observation in the new table. A node offline beyond retained history may have an observation whose ancestry can no longer be proved. These cases remain unknown, with duties not held (their on-chain work is refused by the validators) and readiness reporting the `operator_membership_unavailable` detail, and need authenticated evidence or operator intervention; local unsigned/prepared journals and old record age do not justify inventing a removal proof. No existing deployment was migrated or reset during this work.

Once current absence is authenticated, duties pause while the observed missing point reaches the manifest's `l1Finality.confirmationDepth`. The monitor then performs a full address-scoped ledger scan at a retained finalized point. The scan runs outside the history producer section, so history recovery, which drains producers, never waits on its deadline. Before publishing its verdict the monitor re-enters the producer section and requires that exact point to be still retained and canonical; its ancestors, including the recorded activity, are then canonical too. If the recorded activity ages below the retained anchor while removal is already pending, it still counts as proof: an aged record is final, so the finalized scan still runs and confirms removal. An observation still inside the retained window that is no longer canonical remains unproven. Before removal is pending, an aged record does not prove activity. This expensive scan is reserved for confirmation of suspected removal; steady-state checks use exact references. A finalized retired-list node is sufficient removal evidence because the retired validator requires the matching transfer from the active set. See [pending/finality decision, line 368](../../../demo/midgard-node/src/fibers/operator-membership.ts#L368), [scan outside the producer, line 409](../../../demo/midgard-node/src/fibers/operator-membership.ts#L409), [retirement transfer, line 50](../../../onchain/aiken/validators/operator-directory/retired-operators.ak#L50), and [scan deadline, line 134](../../../demo/midgard-node/src/l1-ledger-snapshot.ts#L134).

## Duty and diagnostic lifecycle

Membership is a liveness halt source, `operator_membership`, like the node's other holds. Publishing `removal_pending` raises `operator_removal_pending_finality` and publishing `removed` raises `operator_removed_from_active_set`; either holds block commitment, speculative commit building and submission, merge, settlement and the inactivity watchdog, while every other fiber keeps running. Publishing `active` or `awaiting_activation` clears it; publishing `unknown` over a pending removal changes nothing. Removal is sticky: once `removed` is published, later checks cannot replace it. The halt source is the only membership hold: the L1 control plane does not refuse work by membership, so block confirmation, ingestion and the readiness refreshers keep running. Genesis startup is not held; it runs once at startup and submits deposits, not operator duties. `/readyz` reports the raised reason through its ordinary liveness reasons, with HTTP 503, its source and its age. Publishing `removed` then completes the shutdown signal. `untilOperatorRemoved` ends the node's fiber set one second later, so the held duties' finalizers run and readiness can be read before exit. The diagnostic HTTP server is owned outside that fiber set. See [publication, line 198](../../../demo/midgard-node/src/fibers/operator-membership.ts#L198), [halt source, line 32](../../../demo/midgard-node/src/services/liveness-halt.ts#L32), [exit, line 462](../../../demo/midgard-node/src/fibers/operator-membership.ts#L462), and [readiness, line 90](../../../demo/midgard-node/src/commands/readiness.ts#L90).

The membership monitor starts with the node's other fibers after authenticated history becomes ready; it does not gate startup. Genesis startup keeps its configured policy and its existing background launch. The implementation leaves signed intents, unknown submissions and other durable state intact. It adds only membership observations, rather than clearing existing journals. See [fiber set, line 106](../../../demo/midgard-node/src/commands/listen.node-fibers.ts#L106), [program, line 328](../../../demo/midgard-node/src/commands/listen.run-node.ts#L328), and [standalone registration command, line 142](../../../demo/midgard-node/src/index.registration-8.ts#L142).
