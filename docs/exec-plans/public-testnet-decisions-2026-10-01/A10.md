# A10 — A removed operator stays up, unready

Implemented: once this operator's own nodes show it removed, it holds its duties and fails `/readyz` with the reason `operator_removed` (plan §7.5 R7, D-N7). The process stays up. A restart reads the same facts back to the same state, so there is no restart loop, and a rollback that undoes the removal makes the operator ready again with no restart. Registration and fresh bond spending remain explicit operator commands; the node never registers itself again.

## Where membership comes from

Membership is a view of the L1 follower's facts, derived once per follower change by the operator-set hook in the follower-change driver (`settlementAndOperatorSet`). It needs no provider, journal load or ledger scan. The hook keeps the operator set in memory: the registered and active lists, the scheduler, the hub oracle, this operator's own retired node (read by its exact asset, never the whole retired list), and the history of this operator's own active node. Its first read, and the first after a rewind or a prune past the last read, loads the live outputs. Every later read takes only the rows a block created or spent since the last read. See [operator-set hook, line 56](../../../demo/midgard-node/src/l1-operator-set/hook.ts#L56), [operator-set mirror, line 296](../../../demo/midgard-node/src/l1-operator-set/set.ts#L296) and [driver wiring, line 381](../../../demo/midgard-node/src/services/l1-follower.ts#L381) with [its hook construction, line 64](../../../demo/midgard-node/src/services/l1-follower.operator-set.ts#L64).

The states are:

- `active`: its active node is live.
- `removed`: its retired node is live, or it is in no list after having been active (its active node in the follower's retained facts, or a recorded activation at a final block). A slash, which burns the active node and creates no retired node, reads `removed` this way.
- `awaiting_activation`: registered, not yet active. The node stays ready and holds nothing.
- `unknown`: none of these, including before the first read. `/readyz` lists `operator_membership_unavailable` among its `details` and stays ready, since no duty waits on it.

See [classification, line 62](../../../demo/midgard-node/src/l1-operator-set/membership.ts#L62) and [readiness detail, line 309](../../../demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts#L309).

## Evidence that outlives retention

The follower prunes spent rows k blocks below its tip, so the spent active node of a slashed operator eventually leaves the facts. Migration 3's `operator_membership_observations`, keyed by verified manifest ID and operator key, keeps the evidence: the hook writes the block that created the own active node once that block is final (depth beyond k), so no rollback can take it back. A recorded activation counts unless the follower's facts show its block orphaned. Without a manifest the record is kept in memory only. See [activity record, line 42](../../../demo/midgard-node/src/l1-operator-set/activity.ts#L42) and [migration](../../../demo/midgard-node/src/database/migrations/sql/0003_operator_membership.sql#L1).

An installation that was slashed before it ever recorded a final activation, or one whose activation and slash both fell out of retention while it was offline, reads `unknown`: its duties are not held, and the validators refuse its on-chain work.

## Duties and readiness

Membership is a liveness halt source, `operator_membership`. Publishing `removed` raises `operator_removed`; it holds block commitment, settlement, merge and the inactivity watchdog, while block confirmation, ingestion and the readiness refreshers keep running. Every other state clears it. Nothing is sticky: the next follower change re-derives it. `/readyz` reports the reason through its ordinary liveness reasons, with HTTP 503, its source and its age. No path exits the process on removal. See [publication, line 97](../../../demo/midgard-node/src/l1-operator-set/membership.ts#L97), [halt source, line 33](../../../demo/midgard-node/src/services/liveness-halt.ts#L33) and [held fibers, line 67](../../../demo/midgard-node/src/services/liveness-halt.ts#L67).

The inactivity watchdog plans from the same operator set, never a provider read. A forced retirement reads only its insertion anchor in the retired list, by asset name. See [watchdog directory, line 245](../../../demo/midgard-node/src/fibers/operator-watchdog.ts#L245) and [retired insertion anchor, line 106](../../../demo/midgard-node/src/l1-operator-set/snapshot.ts#L106).
