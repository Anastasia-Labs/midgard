# A7 — live Cardano parameters and watcher funding

The watcher accepts a legitimate parameter change reported by its verified
local Ogmios endpoint. Boot still requires the verified signed deployment,
network identity and local endpoint checks. A live parameter snapshot is no
longer required to equal the older deployment snapshot. Malformed or substituted
responses remain hard failures. A temporary outage (a transport failure or
timeout, a body that fails to arrive, HTTP 408, 425, 429 or 5xx, or a JSON-RPC
`error` answer whose code `isTransientOgmiosJsonRpcFailure` classes as
"cannot answer now", such as an era mismatch while the node syncs) is a
`WatcherProverFundingUnavailableError` whose cause is a
`LocalKupmiosTransportUnavailableError`, so it is both a funding deferral and an
L1 transient. Ogmios answers every JSON-RPC error with HTTP 400, so only the
code separates these; any other 400 or JSON-RPC error stays hard. During runtime it defers funding. At startup the
`protocol_parameters` stage waits it out in place, retrying only the parameter
query and never reopening the funding store; startup still needs a successful
local parameter query before it continues.

Every funding invocation queries current parameters. New reservations use the
current fee, collateral and size bounds. Existing reservations retain their
original reservation ID, policy digest and basis digest. Their original
parameter snapshot is authenticated with the watcher's existing 32-byte rollback
key and persisted alongside the SQLite reservation before signed intent creation.
Only authenticated history or the signed original deployment can restore that
basis; a record digest or caller-created authority cannot substitute for it.

Idle continuation steps select wallet inputs using current prices and the current
collateral-input cap. A separately authenticated, monotonic maximum-capacity
snapshot permits recovery of leases created during earlier cap increases. This
snapshot is bound to the same reservation and immutable original policy/basis;
it cannot replace their identity or authorize a fresh spend. Parameter policy
admission preserves deployment, runner/category, credentials, economics,
reference scripts and the existing contract roster. The current policy still
controls fresh begin, signed transaction admission and submission rechecks.

Historical pending signed bytes can be read and confirmed before demanding
current-cap inputs. A cap sequence of one, three, then one can therefore recover
an intermediate signed two-collateral intent after restart, reconcile it, and
rotate the next idle action to one collateral input. Rotation requires existing
journal reconciliation and idle-release authorization. Unknown signed attempts
retain their exact intent and leases; an unrelated parameter change cannot turn
an uncertain submission into a replacement transaction.

Availability runtime refreshes Lucid's parameters and cost models through the
same provider before each reconciliation. A failing unsigned availability build
can refresh, reselect inputs and rebuild once if the parameter digest changed.
Repeated failure stops that turn. Signing, intent persistence and submission are
outside this retry wrapper. Fault-proof application invocations already construct
a fresh Lucid; a stalled preflight resumes through the supervisor on a later
observation, with newly queried funding parameters. No whole-workflow immediate
retry was added around a potentially submitting invocation.

The runtime file also integrates A4's replay-transcript retirement hook, including
its local observation runtime. That additive integration belongs to the separate
A4 report and tests, not the A7 funding change.

## Limits

Authenticated history requires the same durable rollback key. Missing, swapped
or tampered capacity evidence cannot admit a historical lease set above the
original/current bound. Missing original nondeployment parameter evidence leaves
funding pending rather than reinterpreting signed intent. An insufficient wallet
also remains pending; current bounds are never reduced to make a build succeed.

The sealed funding measurement/profile artefacts remain bound to the parameters
under which they were measured. This runtime repricing does not regenerate them
or establish a new measured fee/execution recipe. Unit tests use deterministic
local RPC responses, real SQLite reservations and signed CML transaction bodies;
they do not prove ledger acceptance of a live parameter-epoch transition. No live
Cardano parameter change, deployment, service restart, commit or push was performed.
Workspace-wide preflight and SDK/node/emulator transaction preparation are
outside these A7-only evidence lines and are reported separately in the
integration evidence.
