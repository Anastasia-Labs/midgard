# A5 — What the availability-journal halt protects, and how far it should reach

**Recommendation:** adopt scoped containment, with a shared-source safety hold. Quarantine the affected transaction, its dependent transactions and the challenge workflow and wallet resources whose correctness depends on it. Continue other headers only after their independence and the canonical chain view are positively established. Keep a broader hold whenever the source itself is untrusted or the affected set cannot be bounded. Do not implement the historical memo's recommendation as simply replacing the global halt with one blocked row.

This answers the request for full context in [user-request.txt:15](user-request.txt:15). The [historical A5 memo:71](source-context.md:71) correctly identifies the persistent global latch, but its phrase “one contradicted intent” omits a second, broader trigger in the current watcher. The recommendation above refines that memo; it is a design proposal, not an implemented recovery path.

## What this machinery does

Availability means that the data behind an L2 block can actually be obtained. A watcher can challenge an attested block whose data it cannot retrieve. Committee responders answer by publishing the committed data in ordered chunks, settling those chunks and closing the challenge. A watcher can time out an unanswered challenge. These are Cardano transactions with real inputs, collateral, fees and deadlines. This journal is the local durable record of those transactions; it is separate from the operator's block-submission journal.

An **intent** is a transaction already signed and recorded on disk: which deployment, wallet, header and action it belongs to; its exact signed bytes and transaction hash; the inputs and collateral it may consume; its expected outputs; and its validity deadline. “Intent” therefore means an actual signed transaction that may already be circulating, rather than an unsigned plan the process can freely replace. The executor persists it before submitting it. After an ambiguous submission error it observes or rebroadcasts the same bytes, avoiding a second transaction that competes with the first. [Intent fields:5](../../../demo/midgard-core/src/availability-operation-journal.ts#L5), [persist-before-submit:90](../../../demo/midgard-sdk/src/availability-challenge-operation.run-da-availability-operation.ts#L90), [exact-byte recovery:244](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L244).

The journal also coordinates every process using the same wallet. It grants one mutation lease for that wallet, reserves inputs and collateral, and records parent-child relationships when a transaction spends an earlier transaction's output. Those controls prevent two processes from budgeting the same money or signing competing spends. Some collateral can be shared by transactions from the same wallet, so different headers are not automatically independent. [Shared database requirement:133](../../../demo/midgard-core/src/availability-operation-journal.ts#L133), [wallet lease:144](../../../demo/midgard-sdk/src/availability-challenge-operation.build-da-availability-funding-preparation-tx.ts#L144), [reservations and dependencies:491](../../../demo/midgard-core/src/availability-operation-journal.ts#L491).

## What “contradicted” means, and how it can happen

The normal progression is signed/pending → seen on the canonical chain → confirmed after the configured number of blocks have been built on top. This is a depth policy, not a guarantee that a sufficiently deep chain reversal is impossible. On confirmation, the journal releases the transaction's reservations; a confirmed terminal action also removes its live workflow row. Later actions may therefore already have relied on that result. [Confirmation policy:74](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L74), [reservation and workflow release:575](../../../demo/midgard-core/src/availability-operation-journal.ts#L575).

There are **two current global-halt triggers**:

1. **A previously confirmed transaction fails a later finality audit.** If the journal says it is confirmed, the SDK requires a later positive observation to show that same transaction included at sufficient depth. A report that its inputs are all unspent, a conflicting-spend report, or inclusion below the required depth triggers the halt. A malformed positive inclusion report also enters that refusal branch. The error says “Finalized availability transaction rolled back,” but that wording is broader than the evidence: the observation contradicts the journal's finality claim; the code has not separately proved whether the chain reversed or the observation was wrong. [Exact branch:42](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L42).
2. **The watcher receives a rollback crossing its accepted finalized availability observation.** It halts if rollback goes to origin, an earlier slot, or another block at the same slot as its current observation. This names no intent and requires no previously confirmed intent. It is a hold on the observation underpinning availability decisions. Treating this as one bad transaction would lose its meaning. [Watcher rollback branch:835](../../../demo/midgard-watcher/src/availability/runtime.create-watcher-availability-runtime.ts#L835).

For example, transaction A publishes a chunk, reaches the configured confirmation depth, and the process records it as confirmed. Transaction B then spends A's chunk receipt to settle it. A deep rollback can remove A and B together. The local journal still remembers that A succeeded, while its input may now be spendable again. Merely clearing A's refusal would leave B, the recorded challenge progress and possibly later wallet budgeting inconsistent. This example follows from the dependency and release rules; it is an illustrative scenario, not an observed testnet incident.

Other possible explanations include a wrong depth/inclusion report or an inconsistent chain/index view. The live responder checks its canonical boundary before and after reading, and a boundary change becomes an unknown observation. That reduces the risk of interpreting a moving chain as contradictory evidence, but does not prove that every provider response is correct. No live incidence or frequency estimate was established here. [Observer boundary checks:173](../../../demo/midgard-sdk/src/availability-challenge-operation.create-da-availability-operation-observer.ts#L173), [moving-boundary handling:300](../../../demo/midgard-sdk/src/availability-challenge-operation.create-da-availability-operation-observer.ts#L300).

## Which ordinary problems do not create this halt

| Situation                                                                       | Current behavior                                                                                                        |
| ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Provider cannot prove inclusion, including for an already confirmed transaction | Wait. `unknown` and `inputs_missing` do not globally halt a confirmed transaction.                                      |
| A shallow, not-yet-final transaction loses its inclusion evidence               | Return to pending and reconcile.                                                                                        |
| All inputs are positively unspent before the transaction expires                | Rebroadcast its exact signed bytes.                                                                                     |
| Transaction expires with positive evidence that it cannot land                  | Mark expired and release reservations.                                                                                  |
| Another participant wins a publication/settlement/close race                    | A verified final competing spend can expire our intent after its validity ends; derive the next action from live state. |
| An unresolved intent receives an explicit conflicting-spend observation         | Record `conflict`; the caller blocks new work, but this does not itself write the global halt flag.                     |

These distinctions are implemented in [reconcile.ts:42](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L42), [unknown and conflict handling:94](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L94), [positive expiry evidence:145](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L145), and [unspent rebroadcast:224](../../../demo/midgard-sdk/src/availability-challenge-operation.reconcile.ts#L224). The concrete committee observer reports ordinary foreign spends as missing-input evidence; it does not emit the SDK's explicit `conflicting_spend` status. [Observer outcomes:260](../../../demo/midgard-sdk/src/availability-challenge-operation.create-da-availability-operation-observer.ts#L260).

## What happens today after a global halt

The halt is one SQLite metadata entry for the whole database. It is not keyed by transaction, header, wallet or deployment. Once present, it prevents acquiring a lease, asserting a lease, enumerating pending/included/finalized work and reading reservations. Mutations that require a lease consequently stop too. The database can still be opened, closed and inspected through individual record reads; “halted” does not mean SQLite corruption. There is no recovery or clear-halt method in the journal interface or implementation, and no clear-halt path was found in the current callers. Restart preserves the flag and encounters the same refusal. [Global guard:210](../../../demo/midgard-core/src/availability-operation-journal.ts#L210), [guarded reads:322](../../../demo/midgard-core/src/availability-operation-journal.ts#L322), [halt write:594](../../../demo/midgard-core/src/availability-operation-journal.ts#L594).

**The normal committee service does not immediately crash because of this error.** Its polling runner catches responder failures and logs them. The watcher catches reconciliation errors, reports availability as blocked and includes that state in readiness. The committee's current readiness inputs do not include a responder halt snapshot, so this hold is not explicitly exposed there. Other fatal policies may independently stop a process; this investigation did not demonstrate such an exit caused by this latch. The one-shot committee mode lets the responder error propagate. [Committee polling catch:240](../../../demo/da-committee-node/src/tick-runner.ts#L240), [watcher blocked report:747](../../../demo/midgard-watcher/src/availability/runtime.create-watcher-availability-runtime.ts#L747), [watcher readiness:732](../../../demo/midgard-watcher/src/runtime/watcher-runtime.create-watcher-runtime.ts#L732), [committee readiness inputs:400](../../../demo/da-committee-node/src/index.ts#L400), [one-shot mode:385](../../../demo/da-committee-node/src/index.ts#L385).

The operational cost is serious even if the process remains up. A stopped committee responder cannot answer other challenges. A stopped watcher cannot open or time out other challenges. Missed Open deadlines allow withheld blocks to escape availability challenges; unanswered head challenges can time out and slash the DA pool. A challenged queue head also blocks new appends until closure or timeout. These are the reasons to contain a local failure rather than let it disable unrelated work indefinitely. [Watcher deadlines:174](../../../demo/midgard-watcher/README.md#L174), [response liability and append stall:68](../../../demo/da-committee-node/docs/availability-responder.md#L68).

## The tradeoff and the proposed ruling

| Policy                                                                                           | Benefit                                                              | Cost or risk                                                                                                                                                  |
| ------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep today's journal-wide permanent halt                                                         | Simple conservative containment after a trusted fact is contradicted | Every challenge using that database stops; restart cannot repair it; unrelated deadlines may be lost.                                                         |
| Block only the named intent, always continue the rest                                            | Small apparent blast radius                                          | Unsound when later transactions, shared collateral, wallet budgeting or the chain view depend on it. The watcher rollback trigger may have no intent to name. |
| Quarantine the affected dependency/resource/workflow set, with a broader source hold when needed | Limits disruption while preserving the safety boundary               | Requires explicit dependency tracking, resource recovery and an authenticated recovery path; it is more than a one-row patch.                                 |

I recommend the third policy, applied as follows:

1. On a contradiction, immediately revoke new submissions that could depend on the disputed fact. Persist the reason and evidence, identifying the transaction/header where possible.
2. Re-read authenticated canonical evidence. Distinguish source unavailability from a proved chain change and from corrupt/inconsistent source or journal data. A genuine source-integrity failure keeps all affected actuation held until that shared trust boundary is repaired.
3. Bound the affected set using transaction ancestry, challenge state and wallet resources. Affected confirmed transactions already released reservations, so quarantine must reconstruct the resources that may have become live again. Retain original signed bytes and ensure no replacement competes with a transaction that can still land. Preserve the one-lease-per-wallet rule and the existing cross-deployment capital guard. [Existing capital guard:261](../../../demo/midgard-core/src/availability-operation-journal.ts#L261).
4. Permit unaffected work only with a current healthy source, independently valid protocol inputs and available wallet resources outside that affected set. If independence cannot be established, widen the hold to the wallet, deployment or source that shares the uncertainty.
5. Lift a scoped hold only after positive evidence and an atomic repair of the affected durable state. Missing data, elapsed time or a restart alone cannot prove recovery. Do not delete the journal, blanket-clear the metadata flag or declare a contradicted confirmed intent expired merely to get progress.
6. Report the affected headers, wallet/source scope and recovery progress through status/readiness and logs, without stopping read-only observation and data serving. This proposal needs specific tests for parent-child rollback, shared collateral, cross-process leases, restart during recovery and safe progress on independent headers.

Changing the halt flag alone will not achieve this policy. The SDK first reconciles a pending intent or audits finalized anchors before building any new transaction. The committee responder refuses discovery while reconciliation is pending and throws on conflict. The watcher explicitly skips actuation if any recovered intent remains unresolved. These gates must understand scoped quarantine and dependency safety; otherwise an intent-scoped flag still produces an actor-wide stall. [SDK gate:33](../../../demo/midgard-sdk/src/availability-challenge-operation.run-da-availability-operation.ts#L33), [committee gate:157](../../../demo/da-committee-node/src/availability/factory.availability-responder-operations.ts#L157), [responder discovery gate:75](../../../demo/da-committee-node/src/availability/responder.ts#L75), [watcher actuation gate:682](../../../demo/midgard-watcher/src/availability/runtime.create-watcher-availability-runtime.ts#L682).

The requested decision can therefore be expressed as: **“Contain a recoverable availability inconsistency to its proven dependency and resource scope; continue independent challenges on a healthy authenticated source. Preserve a broader safety hold when source trust fails or the scope cannot be proved, and recover through evidence rather than resetting durable history.”** A5 chooses how far a hold reaches; it does not authorize unconditional automatic clearing. Until this fuller containment/recovery path exists, retain the conservative global guard for positive finalized-state contradictions.
