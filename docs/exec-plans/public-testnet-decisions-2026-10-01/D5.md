# D5 — Warn at half capacity, and warn earlier when growth leaves little time

**Recommendation:** use **50% of the effective inner-byte limit** as the first capacity warning, **75%** as an action-required alert and **90%** as an urgent alert. Add a forecast that can trigger those same levels earlier when the remaining usable headroom is likely to run out within **30, 14 or 7 days**, respectively. These are proposed initial operating defaults, not measured safe lead times. If delivering and validating the A6 replacement takes longer, increase the forecast lead time to cover that work and its deployment margin.

Warnings belong in metrics, logs and the detail of `/readyz`. They should **not make the node generally unready just because it crossed 50%, 75% or 90%**. Continue useful work while safe, legal blocks fit. Report a specific block-production failure when no legal candidate fits; preserve data retrieval, observation and recovery capability. A warning does not extend the protocol's actual size limits.

## Which bytes matter

The headline limit is **64 MiB = 67,108,864 bytes**, not 64 million bytes. There are three distinct sizes:

- **Inner bytes:** the canonical payload after decoding or decompression, including the entire resulting UTxO state, transaction representations, events, scripts and trace/proof material.
- **Stored bytes:** the envelope containing the inner data, possibly compressed, plus envelope metadata.
- **Request bytes:** the stored envelope plus the payload-submit request's metadata and framing.

The current pre-submit guard protects all three. Compression uses a conservative worst-case bound rather than assuming the ledger compresses well. The receiver also caps the declared decompressed size and checks the actual decompressed length. Therefore a 5 MiB compressed artifact expanding to more than 64 MiB does not become a valid large block. [Hard limit:82](/home/gumbo/midgard-hub/midgard/demo/midgard-core/src/cek-proof.encode-midgard-cek-term-node.ts:82), [transport bound:41](/home/gumbo/midgard-hub/midgard/demo/midgard-core/src/da-transport.da-libp2p-runtime-manifest.ts:41), [three-size projection:88](/home/gumbo/midgard-hub/midgard/demo/midgard-core/src/da-payload-sizing.ts:88), [receiver limits:332](/home/gumbo/midgard-hub/midgard/demo/midgard-core/src/da-payload-envelope.ts:332).

Executing the current sizing helper on 2026-10-01 gave these exact maximum inner sizes. These are deterministic calculations from source, not measurements of a live payload or a compression benchmark:

| Envelope mode         | Maximum inner bytes | Approximate MiB | Why it is below 64 MiB                                                                         |
| --------------------- | ------------------: | --------------: | ---------------------------------------------------------------------------------------------- |
| Identity, the default |          67,108,710 |       63.999853 | Envelope and submit-request framing consume 154 bytes.                                         |

Use `maxDaPayloadInnerBytes(mode)` for the warning denominator; do not duplicate these constants in alert logic. ## Distinguish a large block from a growing ledger

Two different pressures need separate visibility:

1. **Candidate-block size.** A busy block can be large because it contains many transactions, script programs or traces. The full candidate ratio tells the builder when it must select less optional work, and tells operators when that is happening repeatedly.
2. **State floor.** Even a block doing no new work repeats the existing UTxO set. Growth in that unavoidable state cost is what eventually prevents any block from fitting. Report the exact state aggregate and a no-work payload projection separately, plus a projection for the minimum legal next block including mandatory due events.

The current node already maintains an exact UTxO entry count and sum of encoded tuple bytes, and updates them as outputs are inserted and deleted. Its final candidate size includes the other payload components. That is a better basis than multiplying a historical UTxO count by a constant. [Aggregate accounting:20](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/mpf/payload-size.ts:20), [insertion/deletion accounting:94](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/mpf/payload-size.ts:94), [full candidate sizing:142](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/commit-block-header/submission.assert-pre-submit-da-payload-size.ts:142).

A no-work projection is a useful diagnostic floor, but not permission to omit an event the protocol requires. If a legal block must include overdue forced transactions or other due events, its required size can exceed the no-work floor. A shrinking ledger is also not automatically easy to obtain: the transactions consolidating or withdrawing outputs need room for their own data and execution evidence. Reserve that working room before assuming the final few MiB can be used for growth.

Use the actual projected post-state of a candidate. As [A6 explains:17](/home/gumbo/midgard-hub/midgard/docs/exec-plans/public-testnet-decisions-2026-10-01/A6.md:17), the UTxO list is the resulting block state, despite the historical memo calling it the base ledger.

## Is half a frame early enough?

**Half a frame alone cannot answer a time question.** With roughly 32 MiB remaining, growth of 1 MiB a day leaves roughly a month, while growth of 32 MiB a day leaves a day. There is no measured growth rate or UTxO mix in this report, so neither result is a prediction for lc1 or public testnet.

Forecast the state headroom using:

`usable_headroom = effective_inner_limit − current_no_work_inner_bytes − working_reserve_bytes`

`estimated_days_remaining = max(0, usable_headroom) / conservative_positive_state_growth_bytes_per_day`

The working reserve is room for expected required events, ordinary useful transactions, their scripts/traces and measurement uncertainty. Derive it from bounded supported workloads and observed payload costs, rather than hardcoding a fraction as proof of safety. If today's minimum legal block already exceeds that reserve, report that fact and use its actual requirement. No reserve sufficient for Midgard's workload was measured here.

For illustration only, assume an identity-mode no-work payload of approximately 32 MiB and an **assumed** 8 MiB reserve. Approximately 24 MiB remains for state growth:

| Assumed sustained net growth in encoded state | Illustrative time until the reserve is exhausted |
| --------------------------------------------- | -----------------------------------------------: |
| 1 MiB/day                                     |                                    About 24 days |
| 10 MiB/day                                    |                                   About 2.4 days |
| 32 MiB/day                                    |                                   About 18 hours |

Similarly, **assuming** each net new output adds 150 encoded bytes, 10,000 additional unspent outputs a day add about 1.43 MiB/day and consume that illustrative 24 MiB in about 17 days. This 150-byte assumption is not an executed encoding measurement. Output sizes vary with address, assets, datum/script material and encoding; ordinary transfers can add or remove outputs without deposits. The historical “226k at half a frame” implies about 148 bytes per output if other bytes are ignored. It does not validate a universal 148-byte constant. The encoder actually sizes each key/value tuple. [Tuple sizing:36](/home/gumbo/midgard-hub/midgard/demo/midgard-sdk/src/da-payload.encode-da-payload.ts:36).

Estimate growth from timestamped canonical state samples. Start with the larger positive trend over a short window, such as one hour, and a longer window, such as one day, once enough samples exist; retain visibility of bursts rather than smoothing them away. Report sample period, freshness and uncertainty. A flat or negative trend should show “no exhaustion projected from this sample,” not an unconditional promise of infinite capacity. Insufficient or stale samples mean “forecast unavailable.” Percentage alerts continue to function while the forecast is unavailable.

A sudden externally driven burst can outrun any trend prediction. Keep the hard bound and size-aware legal block selection, and evaluate the next candidate before signing. An operator must not dismiss repeated size reductions because the selected smaller block now fits: the original candidate size and deferred work are evidence of throughput pressure.

## Alerting and readiness behavior

Use a small number of distinct, actionable alerts:

- **Warning:** state floor plus working reserve, or repeated full candidates, reaches 50%; or usable state headroom is forecast to last 30 days or less. Begin the capacity/upgrade work and confirm the payload mix and growth estimate.
- **Action required:** 75% or 14 days or less. An upgrade or other approved remediation needs a dated execution plan; confirm enough space remains for required work and safe ledger consolidation.
- **Urgent:** 90% or 7 days or less. Escalate immediately; do not count on compression, a restart or smaller optional batches to solve unavoidable state growth.
- **Production blocked:** authenticated current state and required work admit no safe legal candidate within the exact bounds. Expose a specific reason and mark block-production readiness false. Keep read-only serving and recovery available. A transient oversized optional batch that can be safely reduced is not this condition.

Persist severity across a few consecutive measurements for trend/percentage alerts and clear with a lower threshold, such as five percentage points below the entry threshold, to avoid flapping. Positive evidence that the minimum legal block cannot fit takes effect immediately. Emit alerts on severity changes and rate-limit reminders; do not log a warning on every commit indefinitely. Publish the current numbers even when no alert changes.

Current `/readyz` derives `ready` from blocking reasons and returns HTTP 503 if any exist. Adding a warning to that reasons array would automatically turn a planning alert into general unready status. Instead add a separate `daCapacity` detail with severity, candidate size, state floor, usable headroom, forecast status and sample age; leave warning severity out of blocking reasons while production is possible. For an actual production hold, identify the capability that is blocked and the unaffected capabilities explicitly. [Current readiness response:348](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts:348), [HTTP mapping:410](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts:410).

Expose gauges for effective limit, candidate inner size, stored/request upper bounds, UTxO tuple bytes/count, no-work and minimum-legal size projections, reserve/headroom and sample age. Add counters for overflow refusals and size-selection reductions. Export a forecast only with an accompanying validity indicator; unknown must not become zero days or a silently healthy value. Header hashes belong in structured logs, not metric labels that create one time series per block.

This is additional wiring, not an existing dashboard. The pre-submit guard currently reports these projections through logs. The commit worker runs in a separate thread; its ordinary successful output contains L1 transaction and selected-transaction sizes, not these DA projections. The Prometheus exporter is created by the main process when monitoring is enabled. Carry a bounded projection snapshot back to the parent and update its metrics/status there, including failed or reduced candidates. Logging a ratio or updating a worker-local gauge alone does not establish that `/metrics` or `/readyz` receives it. [Current size log:210](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/commit-block-header/submission.assert-pre-submit-da-payload-size.ts:210), [worker creation:189](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/fibers/block-commitment.build-and-submit-commitment-block-action.ts:189), [successful output:75](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/workers/utils/commit-block-header.ts:75), [main-process exporter:404](/home/gumbo/midgard-hub/midgard/demo/midgard-node/src/commands/listen.run-node.ts:404).

## Alternatives and the structural fix

| Alternative                                | Tradeoff                                                                           | Ruling                                                                                           |
| ------------------------------------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Warn only at 90%                           | Fewer early alerts, little time for protocol work                                  | Too late as the first warning.                                                                   |
| Warn at 25%                                | More notice, greater likelihood of a long-running warning with no immediate action | Useful if upgrade lead time demands it; the forecast should normally supply this earlier notice. |
| Warn only at 50%                           | Simple, but cannot distinguish a year's growth from a day's growth                 | Keep as the fallback, supplement with time remaining.                                            |
| Warn at a fixed UTxO count                 | Easy to explain, wrong when output sizes or block proof material change            | Show counts as context; alert on bytes.                                                          |
| Warn using compressed wire size            | Reflects bandwidth, hides the decompressed limit and changing compressibility      | Track separately; do not use as the capacity denominator.                                        |
| Make the node unready at the first warning | Attracts attention, but can remove useful capacity while blocks still fit          | Use explicit alerts and status detail instead.                                                   |

The durable solution is [A6's replacement of repeated full-state payloads](/home/gumbo/midgard-hub/midgard/docs/exec-plans/public-testnet-decisions-2026-10-01/A6.md:5): publish authenticated execution inputs and retained proof material, with separate state checkpoints for catch-up. Then an unchanged large ledger need not consume most of every empty block. Size limits, warnings and selection remain valuable after that replacement, but their state-floor forecast changes. Raising the cap or compressing better merely postpones the present cliff. This warning policy should accompany the replacement, not become a justification to defer it indefinitely.
