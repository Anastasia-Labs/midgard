# A4 — What the retention ruling means

Recommendation: apply the accepted general retention rule, with one correction to the earlier wording. **Keep information for as long as any supported recovery, challenge, or unfinished operation can still need it; then remove it safely.** Use 2,160 L1 blocks as the baseline for the watcher's supported deep recovery, including its boundary ancestor. Do not apply 2,160 as a universal number of database rows or as a replacement for the protocol's time limits.

The sentence about “the trusted-head record floor and the replay-transcript archive's 100,000-row / 64 GiB ceilings” means that those two stores must follow this same lifecycle: identify what remains necessary, preserve the links that authenticate it, and retire completed history before ordinary operation exhausts a fixed budget. It does not mean deleting either store's oldest 2,160 records or removing its safety checks.

This is a recommendation checked against source on 2026-10-01, at repository HEAD `3027be19cb3bc740f83af0e155e34ab38c7cf894`. It is not an implementation or a runtime verification.

## Why 2,160 and the challenge duration answer different questions

The watcher records what its L1 sources observed and whether they agreed. This lets it prove which Cardano history supported its decisions and undo those decisions when that history changes. The configured maximum deep recovery is 2,160 **L1 blocks**. Recovery checks both the old branch and replacement branch against the configured block depth. Its path reader accepts up to 2,161 entries because the common ancestor is included as well as the blocks after it. [Sources 1–2]

A challenge duration instead answers: “How long can someone still contest this L2 block or require a response about its data?” That is a time-based obligation, measured in milliseconds and derived from the deployment's protocol settings. The shared required retention window currently derives from block maturity plus half of maturity for the proof-time bound. It is not simply the DA challenge-opening window. A header that remains in the live state queue is retained even after the ordinary time horizon, because an open availability challenge may still require its payload. [Sources 3–4]

These quantities cannot be directly compared as `max(2160, challengeWindowMs)`. Blocks, milliseconds, authority revisions, transcript versions, and bytes are different units. A quiet period can consume time without producing many blocks, while a busy block can produce several observations or records.

The safe rule is to delete an item only after **all applicable reasons to retain it have ended**. If a collection is used only for recovery, its ordinary block-history floor can follow the recovery depth. If it also supplies a challenge, its applicable time deadline must pass too. If an unfinished operation still refers to it, keep it until that dependency has safely ended.

For a recovery anchor at L1 block number 10,000 and an allowed depth of 2,160, the boundary ancestor is block 7,840. Keep that ancestor and the necessary evidence after it. Keeping only the newest 2,160 rows is insufficient: it could omit the ancestor, discard another provider's evidence for a retained block, or discard the old branch while retaining the replacement branch. Recovery explicitly requires linked consecutive block numbers and matching parent hashes. [Source 2]

There is another qualification: 2,160 is the maximum depth the recovery verifier accepts, not proof that the live store already contains a complete recovery path for every incident. Quiet blocks are explicitly not persisted into the rollback authority by the observation path; a separate progress store records quiet and touched blocks. Retention must preserve the appropriate evidence sources together. [Sources 5 and 12]

## What the trusted-head floor means

The trusted-head authority is a separate, durable witness to the latest watcher state. Each record names a revision, the state snapshot's digest, and the previous authority record's digest, with keyed authentication. The watcher publishes a new head only as a direct successor to its expected prior head. This helps prevent an old or substituted watcher snapshot from being accepted as current. [Sources 6–7]

A proposed **record floor** means an authenticated starting point for the retained authority history: records before that point have been safely retired, and verification starts from a durable checkpoint that explains where the surviving chain begins. The floor must preserve the independent authority's existing freshness guarantees.

The current source does **not** implement that disk-retention floor. It writes one new file per revision and scans the directory from revision zero, checking every link. Removing the earliest files today would make verification fail with a revision-chain gap. The 4,096-record setting is only a memory-cache limit; the source explicitly says every scan still reads every disk record. It is not a disk-history limit or a rule permitting deletion. [Sources 6–7]

Therefore my recommendation is **authenticated compaction**, not a file-deletion script:

1. Persist a checkpoint containing the retained chain's starting revision and digest, tied to the current independent authority and deployment.
2. Verify that the surviving chain connects to that checkpoint and the current published head before deleting its predecessor files.
3. Make publishing the checkpoint and retiring the old segment safe across crashes. After a restart, either the old complete chain or the new checkpoint plus suffix must be verifiable.
4. Preserve any authority records actually needed by current recovery or unfinished publication. Refuse substituted checkpoints, disconnected suffixes, and stale state under the same trust assumptions as the present independent service.

Those are proposed implementation requirements; the current format and scanner need changes before this is safe.

Do not infer this floor by retaining the last 2,160 authority files. Authority revisions track durable state updates, including observation and user-event checkpoint updates, and are not one revision per L1 block. The head itself identifies a snapshot, not an L1 block number. The implementation must explicitly connect the floor to the retained snapshots and obligations, or compact authority history into a verified monotonic checkpoint once older revisions are no longer needed. [Sources 6–8]

## What the 100,000-row and 64 GiB ceilings mean

A replay transcript is the saved evidence used to repeat and check a validation replay for an L2 header. The archive groups transcripts by the deployment, header, and exact L1 inclusion point. If that capture changes, it appends another version linked to its predecessor; it retains the original. The validation-fault classification path reads the archived transcript, captures a fresh checked transcript, and saves it before returning the completed decision. Stored bytes undergo fresh semantic replay rather than becoming authority merely because they are on disk. [Sources 9–10]

The current limits are:

| Limit                 | What it counts                                                                                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 100,000 rows          | All transcript versions across the entire archive, not 100,000 L1 blocks or 100,000 live challenges.                                                          |
| 64 GiB                | The sum of saved transcript-byte lengths across the archive. This is 68,719,476,736 bytes, not a measurement of the SQLite file, indexes, or write-ahead log. |
| 4,096 linked versions | The version chain for one deployment/header/inclusion identity.                                                                                               |
| 128 MiB               | The maximum bytes in one transcript.                                                                                                                          |

These constants and the global SQL usage query are present in current source. Overrides may only lower the limits. The store has no pruning operation and describes its originals as never pruned. Adding a version that would breach any append limit throws an error. A read also checks global usage and rejects an archive already over its global limits. [Source 9]

Consequently, the ceilings currently limit lifetime accumulated history. Sufficient new validation-fault captures eventually prevent further transcript writes even if all older disputes have ended. A global over-limit archive can also make reads fail for otherwise unrelated identities. The code establishes failure of the archive-dependent classification operation; this review does not establish that the whole watcher process necessarily crashes. [Sources 9–10]

The accepted rule changes the intended role of those numbers: they should bound the **history still needed at a given time**, with room for normal workload and recovery, rather than determine how long the service can exist before maintenance becomes mandatory.

My recommended first implementation is to retire **whole transcript identity chains** once the header is outside the applicable challenge and recovery horizons, every associated proof or response operation is complete, and nothing current refers to that chain. Delete its head and rows together in one transaction. Keep all versions while that identity is still needed.

Deleting only the oldest versions of a live chain is unsafe with the current verifier: it follows each predecessor back to the original and checks that the number of linked rows equals the recorded chain length. A missing original or intermediate version is treated as corruption. A future design could compact versions behind a separately authenticated checkpoint, but whole-chain retirement is simpler and preserves the present “original remains available throughout the live case” property. [Source 9]

The 128 MiB per-transcript bound remains an individual-input/resource safeguard. Pruning completed identities also does not solve the 4,096-version ceiling for one still-active identity. That separate limit needs evidence about legitimate recapture rates; if necessary, a verified compaction mechanism must preserve the original and required versions. Simply raising or removing every bound is not the retention ruling.

## Preserve unfinished evidence, even when it is old

“Pinning” means marking a record as temporarily ineligible for deletion because something still depends on it. Examples include an open dispute, a response awaiting confirmation, a signed submission whose outcome is still unknown, an unresolved recovery incident, or a checkpoint whose publication is incomplete. These are proposed retention obligations; this report does not claim all stores already implement these pins.

Keep the full dependency set, not just its top-level record. An agreement references observation digests; those observations reference chain points. The current verifier rejects an agreement if any referenced observation or point is absent. The snapshot loader verifies this relationship on reload, so a deletion that appears harmless during one live session can prevent restart. [Source 11]

The current commit helper already filters consistency history to entries whose referenced observations remain present. That is useful referential cleanup, but it is not age-based pruning: the ordinary append builder keeps older observations and chain points, and both canonical progress and observation persistence append consistency entries until their 6,483-entry check refuses further growth. Retention must select the safe set first and commit the store, consistency history, and authenticated snapshot coherently. [Sources 5, 8, and 11]

A recovery incident should pin both required branches and its ancestor against the incident's recovery anchor. It must not lose its evidence merely because the current L1 tip keeps advancing while recovery waits. Similarly, a quiet-block progress record may be needed to connect to an older finalized authority head: the progress store already permits an older `retainFromBlockNo`, and its coordinator supplies the finalized block number. This is an existing example of a dependency taking precedence over the ordinary ring floor. [Source 12]

## Assertions, capacity protection, and the tradeoffs

An **assertion that retention works** means a limit should remain unreachable during the supported normal workload because completed history is removed before new records are admitted. Monitor retained bytes, row counts, oldest required item, cleanup progress, and how much space pinned work consumes. Test boundary recovery and restart after pruning, not just successful deletion.

An **uptime fuse** means the service predictably refuses ordinary future work merely because its total lifetime history reaches a fixed number. The current append-only transcript archive has that shape. The consistency-history checks have the same problem if their prerequisites never retire old observations.

Changing the intended role of a limit does not justify continuing a protected operation without its evidence. If all retained data remains necessary, safe cleanup cannot reclaim it. Capacity must then be handled explicitly: alert before exhaustion, limit new work where possible, and refuse only operations that cannot safely persist their required evidence while continuing independent safe work. An unresolved obligation cannot be erased to make a graph look bounded. A transient “full” result should clear when legitimate cleanup or an explicitly provisioned capacity increase resolves it.

Also, a retention horizon alone does not bound storage bytes. Traffic volume, bytes per observation, provider count, repeated transcript captures, and long-running disputes affect the live set. The 100,000-row / 64 GiB settings therefore need capacity measurements under the intended public-testnet workload. Neither the source nor this review establishes that those values are adequate after safe pruning exists.

The tradeoffs are straightforward:

- Keeping every record forever preserves a convenient audit trail, but disk usage and verification work grow with uptime. Current trusted-head scans illustrate the latter directly.
- Deleting everything below a uniform row count is simple, but can break evidence links, omit the recovery ancestor, or remove data still required for a challenge.
- Purpose-based retention plus dependency pins costs more implementation and testing effort, but keeps the ordinary live set bounded without discarding a current safety obligation.
- Optional long-term archival preserves historical investigations without making the operational node keep all expired material online. Required evidence may be moved out of the active store only if its availability and verification remain guaranteed for the operation that needs it.

I recommend the third approach for public testnet, with optional archival for expired history. Your acceptance supplies the policy direction. The correction is that **2,160 is a recovery baseline with its ancestor and dependencies, not one universal expiration rule**, and authenticated histories require safe retirement mechanisms before their predecessors can be deleted.

## Accepted implementation: rollback evidence and trusted-head authority

The preceding sections record the original source review and proposal. After acceptance, the following implementation was added on 2026-10-01. Replay transcript retirement is a separate implementation lane; the changes described here cover rollback observations, consistency history, and the independent trusted-head authority.

Rollback evidence retention is the recovery-horizon retirement that already shipped on the lifecycle branch (`nextAuthenticatedEvidenceWithinRecoveryHorizon`); this lane's separate retention selector was removed rather than kept beside it. Each observation and canonical-progress publication takes the horizon from the durable frontier (the pending or finalized block) minus 2,160. It retires consistency-history entries whose agreement lies below the horizon, the observations that back only those entries and lie below it, and the chain points that no remaining observation, protocol output, spent output, reconstructed state or confirmation references. The new input and every retained entry's observations are never retired. Without a pending or finalized frontier nothing is retired. The history bound remains an invariant assertion. [Recovery-horizon retirement](../../../demo/midgard-watcher/src/l1/rollback-engine/durable-authority.commit-rollback-durable-authority.ts#L297)

One rule from this lane's selector was carried into that retirement: an observation is retired only together with every other observation of its block hash, so provider agreement on any block that keeps one observation remains checkable. A second ported rule, pinning all evidence while the rollback state held an open incident or unconsumed transitions, was removed in review: every reader of this evidence already lies within the horizon, and an incident that stayed open would have grown the history until the bound refused every durable write. The broader pins this lane first proposed (quarantine, pending DA decisions, unprovable gaps, unfinished faults or submissions, proof/computation threads) were not carried over: none of those records reads rollback evidence below the horizon. Consistency-history entries come only from authenticated canonical blocks, so every entry carries an agreement and at least one observation digest; the retirement's "agreement is null" exemption is not reachable through these append paths. [Observation publication](../../../demo/midgard-watcher/src/l1/rollback-engine/durable-authority.persist-watcher-rollback-durable-observation.ts#L163), [canonical-progress publication](../../../demo/midgard-watcher/src/l1/rollback-engine/durable-authority.persist-watcher-rollback-durable-canonical-progress.ts#L110)

Trusted-head authority retention is the bounded live suffix of the selected SQLite authority store. The file-store retention floor and its compaction that this lane first added were removed as a superseded parallel variant; the append-only file store remains only for offline legacy import, audit and repair. Each authority generation is created explicitly (`initializeSelectedAuthorityStore`, or `midgard-watcher authority-init --config <path> --generation <UUID>`), and `authority-backend.json` selects `generation-<UUID>/authority.sqlite`. The store requires an explicit `liveRecordLimit` K between 1 and 4,096 that must match the initialized store. K counts authority revisions, not L1 blocks, and is not a rollback horizon. [SQLite store](../../../demo/midgard-watcher/src/runtime/trusted-head-authority.sqlite-store.ts#L248), [limit bound](../../../demo/midgard-watcher/src/runtime/trusted-head-authority.envelope-codec.ts#L13), [process config](../../../demo/midgard-watcher/src/runtime/process-config.parse-watcher-process-config.ts#L218)

The live store holds the exact current head, at most one authenticated boundary checkpoint, and the latest `min(K, revision + 1)` records. Each read verifies the whole live suffix: the record chain links back to the checkpoint's boundary record, and the current row binds the tip record's digest and the checkpoint's digest. Retirement happens inside `compareAndSwap`. In one `BEGIN IMMEDIATE` transaction, compare-and-swap verifies the current suffix and checks that the proposed head is the direct successor of the expected head. It then inserts the new record. Once the revision reaches K, it replaces the checkpoint with the oldest live record and deletes that record. Finally it updates the current row and verifies the result before `COMMIT`. A new head and its retirement therefore commit together or not at all; no separate compaction step can fail after a publication. No caller retrieves retired revisions. Current-head and direct-successor publication still check freshness against the latest head. Retired legacy-archive edits are detected by `auditLegacyWatcherTrustedHeadAuthority`, not by current reads.

A failure anywhere in that transaction, the retirement included, rolls it back and leaves the previous head and suffix intact. The authority service answers that request with HTTP 500 `persistence_failure` and keeps serving. The watcher client never retries a CAS; it raises the error. `publishDirectSuccessor` then surfaces it as a `WatcherDurableAuthorityConflict`. The chain coordinator turns that conflict into a `durable_authority_conflict` integrity hold, and `/readyz` reports `coordinator_recovery_hold` while the hold lasts. A one-second integrity retry, or the next chain event, runs durable reconciliation. Reconciliation reads the authority's current head. It then either re-publishes the locally committed snapshot as the direct successor, or adopts the head when the earlier commit did land and only its reply was lost. The failure is therefore a transient, unready state that retries, not an exit or a wedge. One edge is not specific to retirement. If `COMMIT` and then `ROLLBACK` both fail and leave the SQLite connection inside a transaction, each later `BEGIN` on that handle fails. The watcher then stays held and unready until the authority process is restarted. Coordinator hold and retry: chain-coordinator.create-coordinator.ts line 541 (since deleted), [publication](../../../demo/midgard-watcher/src/storage/durable-runtime.load-published-authority.ts#L237)

The store remains inside the independent authority service, outside the rollback snapshot backend. This keeps the existing assumption that an attacker cannot restore the entire independent authority volume to an old valid state. A MAC alone cannot detect such a whole-volume restore. The retained suffix supplies operational freshness. It is not a permanent audit archive of every historical revision.

Verification for the SQLite retention (restored on the lifecycle integration branch, Node 22.22.2, 2026-10-04): `vitest run` over `tests/runtime/trusted-head-authority*`, `authority-initialization-command`, `review-authority-resume-fsync`, `process-config`, `scaffold`, `trusted-head-process-fixture` and `chain-coordinator-integrity-retry` from `demo/midgard-watcher` passed 19 files with 175 tests. The rollback fixtures are structural durable-evidence fixtures, not a long-running native-provider workload. The SQLite crash fixtures inject commit-acknowledgement loss and race real OS processes; they do not kill a process at every write boundary. ## Accepted implementation: replay transcript archive

The archive implementation was added after acceptance, against the same base commit `3027be19cb3bc740f83af0e155e34ab38c7cf894`. It replaces lifetime accumulation for **proven eligible identities** with atomic whole-chain retirement. It keeps every original and intermediate version while the identity remains necessary. It does not delete the oldest rows, discard evidence to fit a ceiling, or treat an arbitrary caller's “finished” flag as completion.

Archive writes now persist a dependency for the exact classified decision in the same SQLite transaction as the transcript and head. That dependency binds the privately admitted deployment and header, inclusion point, header end time, and retention window derived from the actual signed deployment manifest. Pin checksums cover their lifecycle fields; a summary binds the complete set of pins, so removing one pending pin is detectable. The existing transcript-byte, version-link, original-root, and exact-chain-length checks still apply before whole-chain deletion. [Lifecycle storage](../../../demo/midgard-watcher/src/storage/replay-transcript-lifecycle.ts#L60), [signed retention authority](../../../demo/midgard-watcher/src/runtime/deployment-authority.ts#L129)

The lifecycle distinguishes three facts that the old archive could not distinguish:

1. Classification has begun but has not supplied a privately admitted current capture. This remains unresolved, including after a classification failure or process interruption.
2. Classification succeeded, but its capture was never made available to a proof runner. This can happen when the classifier identifies several faults and the supervisor selects an ancestor first. A discarded descendant's classification can expire once its authenticated absence, challenge horizon, and recovery horizon are established; it does not need an invented successful proof workflow.
3. A proof runner obtained the capture. The application durably marks this **before returning any usable challenge**, including direct runner capture reads. That dependency remains pinned until the existing canonical raw-L1 verifier accepts the exact completed journal and terminal. Inclusion alone, a provisional terminal, a pending verification result, or an in-memory completion cache does not finish it. [Capture doors](../../../demo/midgard-watcher/src/fault-proofs/fault-proof-application.create-application.ts#L266), [completion authority](../../../demo/midgard-watcher/src/storage/replay-transcript-completion.ts#L73)

Fresh successful runner outcomes now go through that same canonical verifier before the supervisor caches completion or removes the objective. Completed journals also remain indexed after restart, and after a verification result that asks for another observation, until canonical verification succeeds. Historical recovery supplies a permit only for observing the exact previously signed workflow. The changed reconciliation constructor preserves its refusal of preflight and submission, its authenticated decision and prepared-evidence checks, and revocation. The restart regression removes the target from the current queue, then checks both immediate verification and pending verification followed by a later observation; neither path calls the runner or funding provider. [Fresh completion admission](../../../demo/midgard-watcher/src/fault-proofs/fault-proof-supervisor.admit-runner-completion.ts#L13), [historical objective index](../../../demo/midgard-watcher/src/fault-proofs/fault-proof-progress-authority.ts#L173)

Retirement requires all of the following together:

- An admitted current observation for the same deployment and network, with an initialized, authenticated **Idle** correction lock. A missing lock and a Locked lock both retain evidence.
- The header is absent from both the current queue and retained finalized-header observations. Every recorded dependency is classified without having exposed a proof capture, or has canonically verified completion. Unknown legacy dependencies remain pinned.
- The deployed retention duration has passed after the header's end time and inclusion time, and after terminal completion when proof work was started. Time comes from the admitted L1 slot and the verified network clock, never local wall time.
- Inclusion is outside the supported 2,160-block recovery window. In addition, a privately admitted observation of the header's absence, after all dependencies are eligible, must itself be **more than 2,160 blocks old**. This second boundary protects a recently removed header whose original inclusion is much older: recovery can resurrect that header even when its inclusion and time horizons have expired.

The first-absence witness binds the exact native block, slot, and complete pin set. A live header, unresolved dependency, or non-Idle lock clears that witness. Store startup and rollback clear all witnesses; recovery, quarantine, interrupted authority, or pending proof work also clear them through the runtime hook. These operations clear only retirement eligibility, leaving transcript evidence and durable completion pins intact. A restarted node therefore waits for a fresh absence and another supported recovery window instead of trusting old branch membership. Altered witness bytes refuse retirement. [Absence witness](../../../demo/midgard-watcher/src/storage/replay-transcript-absence.ts#L8), [eligibility and atomic deletion](../../../demo/midgard-watcher/src/storage/replay-transcript-lifecycle.ts#L307)

The live watcher runs this policy after serialized canonical delivery, once its durable finalized anchor covers that delivery and its supervisor has no unfinished, queued, active, or blocked objective. Ordinary quiet deliveries ahead of the next durable checkpoint defer a sweep without clearing the absence witness. When the queue observation is older, the hook periodically obtains a fresh local observation and passes it through the existing exact-point state-queue observation source. The interval is measured from the latest admitted observation, so an initial checkpoint off the absolute block-number grid cannot starve cleanup. It rechecks recovery and queue identity after both asynchronous reads. It never changes an old observation's point to make it look current. Retirement hook: replay-transcript-retirement.ts line 14 (since deleted), [live runtime integration](../../../demo/midgard-watcher/src/runtime/watcher-runtime.create-watcher-runtime.ts#L648)

Deletion audits the complete version chain and dependency set, then removes its versions, head, pins, summary, and absence witness in one transaction. The SQLite regression forces a deletion failure and proves that every component rolls back. It then proves successful reclamation and a new append under a two-row limit, including reuse of previously allocated SQLite pages. This measures reusable capacity, not a shrink of the database file on the operating system. Row/blob capacity refusal now has the explicit `capacity_intervention_required` code; required evidence is preserved.

### Review findings and regression evidence

The first implementation was insufficient in several reachable cases. Each was confirmed against the composed production path and corrected:

| Finding                                                                                                                                                     | Correction and regression                                                                                                                                                                                                                |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A non-null correction lock was always retained, including production's initialized Idle lock.                                                               | Require authenticated Idle; the SQLite fixture uses a real initialized lock and retains null/Locked negatives. Restoring the old guard makes the intended case fail.                                                                     |
| Unselected descendant captures had no successful proof workflow to finish their pins.                                                                       | Persist classification completion and capture exposure separately. Classified, never-exposed work can retire after authenticated absence and all horizons; exposed work remains pinned.                                                  |
| A freshly completed runner bypassed the verifier and populated the completion cache.                                                                        | Require canonical verification before caching and objective completion. The helper regression checks the verifier before completion publication, and retains pending/retryable/failing outcomes.                                         |
