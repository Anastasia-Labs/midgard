# A6 — Stop sending the entire UTxO set in every block

Recommendation prepared 2026-10-01. This is a researched architecture proposal, not an implemented or verified protocol change. Repository inspection used the current working tree at HEAD `3027be19cb3bc740f83af0e155e34ab38c7cf894`; other work was already present and was preserved.

## Recommendation

**Your intuition is correct: a node that already has the correct state can derive the next state from the block's transactions and other authenticated inputs. Midgard does not fundamentally need to send every unspent output in every block.**

Replace the current per-block full-state payload before public testnet with a payload containing the ordered inputs that change state: full transaction data, deposits, withdrawals, forced transactions, their originating L1 evidence, and the exact context needed to execute them. Keep the current transition and validation proof material in the first replacement. Keep compact commitments to the state before and after the block. Publish complete state checkpoints separately for catch-up, and retain enough history and historical proof material to challenge every block that can still be disputed.

This is a coordinated protocol and recovery change. Removing the `utxos` field alone would break current verification and challenge construction. Raising the size cap, compressing snapshots, or splitting them into chunks would postpone the problem while preserving its underlying cost.

The recommended decision is to put this replacement in scope for launch, with the safety and recovery gates below. The existing size refusal and better block selection remain useful protections while the replacement is built; they do not make the full-state design capable of indefinite growth.

## What the current code actually sends

A UTxO is an output that has not yet been spent. The UTxO set is the current ledger: all of those outputs, not the transaction history. An unchanged output may live there for years.

The current payload builder copies every supplied output into `block_body.utxos`, alongside transactions, deposits, withdrawals, execution traces, and script program material. It also carries compact transaction sources and their full preimages; these are different representations used for different purposes, rather than two identical transaction lists. See the [payload builder](../../../demo/midgard-node/src/workers/commit-block-header/da-payload.build-da-payload-insert.ts#L96) and [payload schema explanation](../../../demo/midgard-sdk/src/da-payload.write-cbor-argument.ts#L122).

There is a small but relevant correction to the original question's background. **The payload's UTxO list represents the resulting state of that block**, whose root is `header.utxosRoot`. The committee builds that root from the payload's complete UTxO entries and compares it with the current header. Backfill materializes the current journal's state and passes that complete list to the builder. Evidence: [committee root construction](../../../demo/da-committee-node/src/da/payload.verify-da-payload-against-header.ts#L38), [comparison with the header](../../../demo/da-committee-node/src/da/payload.verify-da-payload-against-header.ts#L228), and [backfill snapshot materialization](../../../demo/midgard-node/src/workers/commit-block-header/da-payload-backfill.ts#L52).

The starting state for challenging the next block comes from the **predecessor payload**. Validation replay checks the predecessor's identity and root, constructs its starting ledger from that predecessor's UTxOs, and checks that the reconstructed root matches `prevUtxosRoot`. The event replay API explicitly requires a complete prior ledger. Evidence: [predecessor admission and starting-state construction](../../../demo/midgard-fault-proofs/src/validation-dispute/replay.admit-validation-trace-replay-context.ts#L102) and [complete-ledger replay requirement](../../../demo/midgard-validation/src/validation-machine/event-replay.ts#L35).

That explains the current convenience: someone with the predecessor payload can obtain the full starting state without replaying older blocks. They can construct ledger membership proofs, check scripts and values, and replay this block. The code demonstrates that dependency; it does not establish that repeating the snapshot was the only possible or original intended architecture.

## Why the size cliff is real

The hard payload cap is 64 MiB. The pre-submit guard also accounts for the stored envelope and submit-request overhead; compressed mode uses a conservative worst-case compression bound. Its usable inner limit is therefore slightly smaller than the headline transport cap. Evidence: [hard cap](../../../demo/midgard-core/src/cek-proof.encode-midgard-cek-term-node.ts#L82), [size projection](../../../demo/midgard-core/src/da-payload-sizing.ts#L88), and [pre-submit refusal](../../../demo/midgard-node/src/workers/commit-block-header/submission.assert-pre-submit-da-payload-size.ts#L194).

Consequently, a quiet block still pays to repeat all unchanged ledger entries. As deposits and new outputs accumulate, that fixed cost grows. Eventually a block with no events cannot fit because the state alone exceeds the cap. Ordinary transfers may then be impossible to include, including transfers intended to consolidate outputs and reduce state size.

Reducing the chosen transaction count addresses an oversized busy block. It cannot address a starting ledger so large that even the unchanged resulting state cannot fit. There is no universal UTxO-count threshold: outputs differ in encoded size, and the payload includes other material. This report does not invent a measured count or daily growth rate.

Sending a snapshot each block also multiplies storage and bandwidth. If unchanged state doubles while activity stays constant, the repeated state bytes roughly double. With state growing by a similar amount every block, cumulative snapshot bytes grow roughly with the square of the number of blocks. This is a consequence of the format, not a benchmark measurement.

## What other L2s publish

The research below distinguishes transaction data, changes to state, and complete state. Only the last one repeats every unchanged entry.

| ZKsync              | Compressed changes to state, together with necessary bytecode and messages, rather than detailed transaction data. These changes permit reconstruction of state. [DA documentation](https://docs.zksync.io/zksync-protocol/rollup/data-availability), [publication and proof binding](https://docs.zksync.io/zksync-protocol/era-vm/contracts/handling-pubdata) |
| Starknet            | Its official release explanation describes publishing compressed state differences in blobs and reusing short identifiers for recurring storage keys.                                                                                                                                        | Another example of publishing changes rather than every unchanged state entry; this source is the March 2025 release explanation, not a claim about today's exact mainnet version. Optimism's fault-proof specification is especially relevant. It reproduces state from inputs and agreed prior history, while obtaining state nodes, code, and other required bytes through an authenticated preimage interface. Those bytes need not be repeated in every transaction batch. [OP fault-proof specification](https://specs.optimism.io/fault-proof/)

The comparison does **not** mean copying their DA format would give Midgard Ethereum's availability guarantees. Midgard's retained committee service has its own trust, retention, access, and availability-challenge requirements. Moving fewer bytes does not remove those requirements.

## What “transactions are enough” must include

For an ordinary transfer, the idea is straightforward. Start with the correct ledger, verify the transaction, remove the outputs it spends, add the outputs it creates, and compute the resulting root. Repeat in the exact agreed order.

Midgard also changes state through deposits, withdrawals, and forced transactions originating on Cardano. A list of ordinary L2 transactions leaves those changes out. Replay must also know the applicable execution rules, time and slot context, fees and network identity, scripts and data, and the original L1 events. Current challenge replay already refuses non-L2 events without admitted originating L1 evidence: [L1-origin requirement](../../../demo/midgard-fault-proofs/src/validation-dispute/replay.admit-validation-trace-replay-context.ts#L117).

The replacement should therefore mean **all information required to independently reproduce and dispute the state transition**, not merely transaction identifiers or compact transaction bodies. A hash tells a verifier whether fetched bytes are authentic. It cannot reveal missing bytes.

There are two separate questions:

1. Can a node reproduce the correct state from an authenticated starting state?
2. Can an independent challenger prove on Cardano that an operator's claimed result is wrong, using available evidence before the deadline?

The second is why a transaction-only encoder patch is unsafe. Midgard's current challenge builder derives state and proofs from complete prior entries. An implementation can keep that API initially by reconstructing those entries locally from checkpoints and replay. A later optimization can build only the authenticated ledger paths needed for a disputed event, but that is further proof-engine work. Deleting network snapshots does not by itself eliminate current local whole-ledger copying or root computation.

A claimed state root can be wrong even when every transaction is available. Committee availability signatures establish access to bytes under the committee's assumptions; they are not proofs that execution was correct. Nodes must keep a bad operator claim separate from their verified local state, preserve its committed trace evidence for challenges, and refuse to extend it. A verifier must not substitute its own corrected traces and lose the operator's original claim.

## Proposed replacement

### Normal block publication

Publish one canonical, bounded payload containing:

- Deployment identity, header identity, parent identity, and commitments to the starting and resulting state.
- Full transaction preimages, signatures and witness data, including forced transactions; deposit and withdrawal inputs; authenticated L1 references and source material.
- An unambiguous ordering across all event types, with the committed event-to-step mapping and counts.
- The exact execution context or authenticated references sufficient to derive it.
- The existing claimed transition traces, validation descriptors and witnesses, and required script program material. Retain these initially so the state-format change does not silently remove a fraud-proof family.

Do not include the full unchanged UTxO set. Keep canonical encodings, explicit limits, and the last pre-submit size guard. First preserve the existing compact-source/full-preimage distinction; only deduplicate a representation after proving that consumers can derive exactly the same commitment and evidence.

The target is that normal publication size depends primarily on this block's work and required proofs. A much larger untouched ledger should not force a much larger empty block. Some proof paths may still grow with the tree's depth; that is different from transmitting all leaves.

### State adoption and multi-operator replay

A receiving node authenticates the block inputs, finds a locally verified predecessor state, executes every event in order, and checks the result against the claimed root. It installs the result atomically only after the applicable checks succeed. Missing history starts bounded retrieval and recovery; it never authorizes inventing or trusting a state.

This must be a shared replay/import path for peer-produced blocks, not a path requiring the producer's private journal. Today's foreign-base selector looks for a root-matching local state and otherwise refuses while awaiting authenticated foreign finalization. Local snapshot reconstruction follows parent journals and refuses a missing parent. Evidence: [foreign-base refusal](../../../demo/midgard-node/src/workers/commit-block-header.resolve-commit-base-ledger-entries.ts#L222) and [journal-chain dependency](../../../demo/midgard-node/src/transactions/state-queue/confirmed-ledger-snapshot.ts#L211).

Therefore this work belongs with E1's authenticated peer replay and E3's catch-up work. A payload download client alone does not implement it.

### Checkpoints and retention

Periodically publish a complete state checkpoint as a separate, chunked artifact. Bind its deployment, finalized header, state root, complete entry set, and chunk hashes. A new node obtains a checkpoint, recomputes its root against authenticated finalized chain state, then replays the following block inputs. The checkpoint supplier need not be trusted for correctness if the complete state root is independently checked.

A newer checkpoint is not enough to challenge an older block: it may omit already-spent outputs needed for that challenge. Retain a checkpoint at or before the earliest state still needed for disputes, the gapless input history after it, and sufficient historical tree/output material. Pin material used by live disputes and recovery. Publish a replacement checkpoint and confirm its accessibility before retiring the previous recovery basis.

Distinguish the promise to let a new node catch up from the promise to reconstruct all history from genesis. The former can use authenticated finalized checkpoints. The latter requires an archive of old inputs and execution rules, with an explicit availability commitment. Pruning everything once a short challenge window expires cannot support both promises.

Checkpoint transport must allow state artifacts larger than a normal block frame, while bounding each chunk, aggregate work, concurrency, disk use, and decompression. Existing DA already exposes chunked retrieval and one-MiB chunk limits; that does not establish a completed checkpoint protocol or remove the total payload cap. Evidence: [retained DA protocols and limits](../../../demo/midgard-core/src/da-transport.da-libp2p-runtime-manifest.ts#L31).

## Alternatives and tradeoffs

| Approach                                                        | Benefit                                                                                   | Cost or limitation                                                                                    | Recommendation                                                      |
| --------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Full state in every block                                       | Easy access to the preceding ledger without long replay                                   | Repeats unchanged data; global growth eventually exceeds any fixed cap                                | Replace before launch                                               |
| Bigger cap or better compression                                | Smallest format change; buys time                                                         | Still ties every block to total state size; larger transfers and memory use                           | Temporary guard only                                                |
| Chunk full state every block                                    | Removes a single-frame bottleneck if all aggregate limits change                          | Preserves repeated whole-ledger work and storage; incomplete transfer delays every block              | Use chunking for checkpoints                                        |
| Transaction inputs plus retained proof material and checkpoints | Scales normal DA with activity; preserves independent execution and optimistic challenges | Requires reliable replay, historical evidence, retention and checkpoint recovery                      | Recommended first replacement                                       |
| Publish only inserted/deleted outputs                           | Small changes can reconstruct state cheaply                                               | Does not reveal whether the omitted transactions and scripts authorized those changes                 | Insufficient as sole optimistic DA; optional replay-checked cache   |
| Transactions plus proofs for all touched ledger entries         | Can support verification without holding the full ledger                                  | Extra witness-generation and publication work; proof completeness and evolving roots must be designed | Consider after the first replacement if challenger costs justify it |

A validity proof can attest that a published state difference results from correct execution, which is why the ZKsync comparison does not justify publishing unaudited changes alone in optimistic Midgard. Midgard must retain the input data needed to test authorization and construct fraud proofs. That is an architectural inference from the differing proof models, not a claim that every ZK and optimistic system uses identical formats.

## Required safety and publishability gates

These are required future acceptance cases, not tests reported as having passed:

1. **Independent reconstruction.** Two nodes with different local databases replay the same checkpoint and inputs and obtain identical event ordering, transaction results, and state roots. Include deposits, withdrawals, ordinary and forced transactions, scripts, reference inputs, and intra-block dependencies.
2. **All fraud routes remain usable.** For every affected proof family, an independent challenger constructs and submits the proof with only the public data and authenticated history. Include honest and fraudulent cases, invalid signatures/scripts, nonexistent and double-spent inputs, fabricated L1 events, omitted/duplicated/reordered events, wrong intermediate/final roots, and an event-free block claiming a changed root. Current trace-boundary detection checks first/last transition roots; the replacement must also cover the no-transition case. [Existing boundary checks](../../../demo/midgard-fault-proofs/src/transition-trace/detect.detect-count-faults.ts#L273)
3. **Proof authentication.** Wrong output bytes, membership and absence proofs, checkpoint roots, deployment identities, parameter contexts, or source preimages are rejected. A root match must not be treated as proof of correct execution for an unfinalized claim.
4. **Deadline feasibility.** Measure catch-up, disputed-event replay, evidence generation, and the actual Cardano proof transactions at the maximum supported block work and recovery range. They must complete within the challenge budget with a stated safety margin. A mathematically possible reconstruction taking too long is not a usable security mechanism.
5. **State no longer sets block size.** Use synthetic ledgers whose complete encoded snapshots exceed the present cap, then publish empty and small-transfer blocks successfully. Verify all stored, submitted, fetched, decompressed and reconstructed sizes. Include maximum script/trace work and incompressible inputs; checkpoints must transfer across many bounded chunks.
6. **Peer production and recovery.** Alternate at least two producers; let a challenger and another producer learn state entirely from public DA; restart them; prune to the declared floor; catch up; recover from an L1 reorganization and a disputed block without accessing another producer's private journal.
7. **Unavailable and adversarial data.** Withhold, truncate, corrupt, reorder and duplicate chunks and inputs; crash during checkpoint installation; serve conflicting manifests; disconnect the producer; retire an old checkpoint. Retry must be bounded, installation atomic, and readiness explain the refusal. No partial state becomes an accepted base.
8. **Retention actually supports recovery.** After allowed pruning, all still-challengeable blocks have an available predecessor/checkpoint path and proof material. Exercise the real archive/committee services, not a test fixture that silently keeps unlimited history.

## Prelaunch replacement and existing deployments

For the undeployed public-testnet format, replace the obsolete payload schema, encoder/decoder, commitment verification, replay/import, and fixtures together. Preserve the protocol's upgrade/version seam without maintaining two default prelaunch formats. Review changes across SDK, node, committee, watcher, proof engine, specification, and any affected validator commitments or availability rules. Rebuild and retest deployment artifacts where required.

An already running private deployment still has real protocol state and signed availability obligations. “Not launched” does not authorize discarding them. Either carry out an explicit upgrade at an authenticated boundary while honoring old retention obligations, or perform a separately authorized complete on-chain redeployment with matching local state. Do not pair a cleared local database with old on-chain state. [Repository reset and redeployment rule](../../agents/state-reset.md#L3)

Until the replacement meets the gates above, retain the current sound size refusal and improve observability and deterministic block selection. Describe the ledger-growth ceiling honestly. The proposed architecture is preferable, but this report is not evidence that it already works or that it is a small patch.
