# D4 — Verify the provider's chain, distinguish startup from bad responses, and share one freshness policy

Recommendation: adopt all three changes together. Treat explicit “no tip yet” responses as temporary, but treat entirely omitted required fields as a provider-format error. Verify the node's Ogmios network against the configured deployment before accepting its timing evidence. Replace the fixed two-minute tip-age policy with one shared policy derived from the verified chain's block cadence, and use it in every caller. None of these conditions should create a permanent database quarantine or a repeated process restart loop.

This report is based on current source inspected on 2026-10-01. The earlier context says a new genesis-derived limit exists and missing fields currently cause waiting. I could not establish either statement in the inspected code: the shared helper still defaults to 120,000 ms and throws ordinary errors for missing tip fields. Caller behavior varies. These recommendations therefore describe work still needed, not a verified landed fix.

## The full picture

Ogmios is the bridge through which Midgard reads and submits to a Cardano node. Three different questions matter:

1. Is this the intended Cardano chain?
2. Is the bridge returning a response in the format we understand?
3. Is its chain information fresh enough to use?

An HTTP success answer proves none of those by itself. Nor does a plausible slot number identify the chain: two test networks can have similar clocks. Conversely, a chain can legitimately produce no new block for a while. Treating these different cases as one generic error makes recovery unreliable and operator diagnostics misleading.

The current helper reads `/health`, requires a connected and at least 99% synchronized provider with a tip slot and update timestamp, checks timestamp age, then queries `queryNetwork/tip`. Its returned submit slot is the greater of the queried slot and a slot extrapolated from the health timestamp. This is operational timing evidence, not proof that another block exists or that a transaction is finalized. See [health requirements, line 259](../../../demo/midgard-core/src/ogmios-slot.ts#L259), [snapshot queries, line 320](../../../demo/midgard-core/src/ogmios-slot.ts#L320), and [returned slot, line 355](../../../demo/midgard-core/src/ogmios-slot.ts#L355).

## Missing tip fields: refuse the evidence, distinguish the reason, keep recovery possible

The official Ogmios monitoring documentation explicitly allows `lastKnownTip` and `lastTipUpdate` to be null. Its client documentation explains that a null update can occur while Cardano checks its database during startup, which can take minutes. That is a normal unavailable-provider condition. The documentation describes these fields as part of the response; it does not document entirely omitting them as the normal startup representation. Calling omission a format problem is therefore a design inference from the documented contract, not a measured observation of our pinned server. See [Ogmios monitoring](https://ogmios.dev/getting-started/monitoring/) and [Ogmios ServerHealth](https://ogmios.dev/typescript/api/interfaces/_cardano_ogmios_client.ServerHealth.html).

The current parser loses the distinction: an absent field, null tip, `origin`-shaped tip and invalid slot all fail to produce `lastKnownTipSlot`; a non-string timestamp is omitted. The subsequent validator throws the same missing-field error. See [parser, line 234](../../../demo/midgard-core/src/ogmios-slot.ts#L234) and [missing-field checks, line 278](../../../demo/midgard-core/src/ogmios-slot.ts#L278).

I recommend preserving the original shapes and classifying them explicitly:

| Response | Meaning and recommended behavior |
| --- | --- |
| Valid response with explicit null tip/update, or a supported chain-origin representation | Provider has no usable tip yet. Stay unready for dependent operations and retry with backoff. |
| Required fields entirely absent, invalid types or an invalid timestamp | Provider response is incompatible or malformed. Refuse that response, publish the specific format error and alert if persistent. |
| Valid but disconnected, catching up or too old | Temporary lack of usable chain evidence. Defer affected work; recover automatically when fresh evidence returns. |
| Valid response proving the wrong chain | Identity mismatch. Stop using that provider for chain-dependent work until it proves the configured identity. |

“Fail closed” means do not use unproven evidence. It need not mean terminate the process. During startup, keep the diagnostic server reachable and withhold dependent operations. During operation, probe again with bounded requests and backoff; a corrected response can clear the current error without rewriting durable protocol evidence. For a one-shot command, return a clear refusal rather than wait forever. Do not reinterpret omitted fields as a healthy response, invent a slot, or silently switch chains.

Treating every missing shape as transient is simpler, but an incompatible proxy or wrong URL can leave the service waiting forever with a misleading explanation. Killing the process for every missing field creates avoidable restart loops. Strict parsing with a recoverable diagnostic state gives both correctness and useful recovery. A timeout or temporary outage does not prove that previously stored chain evidence is corrupt.

## Network magic: add the check, preserve the stronger existing identity checks

Network magic is Cardano's numeric network label. Check it before building or using the node's transaction client and before accepting timing from a newly established provider route. Derive the expected value from the admitted network/deployment authority; a custom network needs its configured identity. Do not accept the provider's own answer as both the expected and actual identity.

The committee already compares live genesis magic against Mainnet, Preprod, Preview or the configured custom magic. Its Custom Lucid setup also checks magic before deriving the clock mapping. The node's Custom Lucid setup fetches a tip and genesis timing, checks that their clocks agree, and then builds Lucid; that path contains no magic comparison. The node DA-bond CLI has the same timing-only Custom setup. See committee comparison, `demo/da-committee-node/src/l1/provider.ogmios-rpc-session.ts` (since deleted) line 243 (since deleted), committee Custom setup, `demo/da-committee-node/src/l1/lucid-network.ts` line 68 (since deleted), [node setup, line 40](../../../demo/midgard-node/src/services/lucid.ts#L40), and [bond CLI, line 66](../../../demo/midgard-node/src/commands/da-bond.load-da-bond-context.ts#L66). Ogmios officially provides the genesis query needed for this check: [network queries](https://ogmios.dev/mini-protocols/local-state-query/). <!-- doc-links:historical -->

This is a gap in the timing/client path, not proof that the node has no identity protection. Its event-history machinery authenticates an approved complete genesis digest on each exact capture/follower socket, and checks deployment/network binding. Its native-ledger authority also checks local genesis magic. Preserve those protections. A matching numeric magic is weaker than a matching approved genesis: custom chains can reuse a number. The shared provider context should carry verified genesis identity, expected magic, timing parameters and the route/session to which they apply. A URL string alone is insufficient when a proxy can change its backing node. See event-history binding, line 105 (`demo/midgard-node/src/l1-event-history-source.ts:105`, since deleted), exact-socket genesis check, line 185 (`demo/midgard-node/src/l1-event-history-source.ts:185`, since deleted), and [native authority magic, line 138](../../../demo/midgard-core/src/native-reward-account.ts#L138). <!-- doc-links:historical -->

Prefer reusing shared identity parsing and the existing approved authority over adding a separate, weaker expectation to every call site. Recheck on reconnect/provider change; do not cache a startup success as permanent authority. A wrong-chain response should fail dependent work immediately and prominently. Reconnecting repeatedly to the same wrong chain does not solve it; a configuration repair or restored route is needed.

## Freshness: one chain-derived operational policy, used everywhere

The inspected helper's default is 120,000 ms. I did not find a genesis-derived tip-age resolver in the current `demo` source. The four named callers omit `maxHealthAgeMs` and inherit that default; the node's main `submitSlotSnapshot` provider also omits it. See [default, line 16](../../../demo/midgard-core/src/ogmios-slot.ts#L16) and these callers:

- [Readiness refresh, line 138](../../../demo/midgard-node/src/commands/listen-router.get-readiness-handler.ts#L138).
- [Merge fallback, line 46](../../../demo/midgard-node/src/transactions/state-queue/merge-to-confirmed-state.capture-merge-local-ledger-gate.ts#L46).
- [Provider preflight, line 257](../../../demo/midgard-node/src/commands/l1-provider-preflight.ts#L257).
- [DA-bond CLI, line 79](../../../demo/midgard-node/src/commands/da-bond.load-da-bond-context.ts#L79).
- [Main node slot provider, line 225](../../../demo/midgard-node/src/services/lucid.ts#L225).

The policy should depend on expected block spacing, not assume every slot contains a block. Cardano describes `activeSlotsCoeff` as the average fraction of slots selected to contain blocks. Expected spacing is slot duration divided by that fraction; Hydra uses this same calculation. For one-second slots and coefficient 0.05, that is about 20 seconds, not one second. This is an average, not a maximum permitted gap. See [Cardano CIP-9](https://cips.cardano.org/cip/CIP-9) and [Hydra's block-time calculation](https://hydra.family/head-protocol/haddocks/hydra-node/src/Hydra.Chain.CardanoClient.html).

As an initial operational recommendation, use the greater of two minutes and twenty expected block intervals, derived from authenticated genesis values. For the 20-second example that is 400 seconds. The multiplier is a proposed tolerance, not a Cardano rule or a measured guarantee; validate it against realistic quiet-chain and outage drills before release. Validate the coefficient and slot duration, display the derived threshold, and refuse an unsupported or impractically large policy rather than silently allowing unlimited staleness. A chain with unusual parameters needs an explicit reviewed profile.

This buys fewer false refusals during ordinary block gaps, with slower detection of a bridge that answers but no longer advances. Mitigate that tradeoff with immediate disconnect/error detection and separate synchronization/chain-point checks. Avoid fixing it by ignoring timestamp age or by increasing only one caller's limit: then readiness, merging and commands would disagree about the same provider. Do not let a larger freshness allowance extend a transaction's validity interval, change finality depth, or bypass maturity checks. Rebuild transactions with fresh evidence when needed.

Freshness also needs honest timestamps: reject implausibly future-dated updates and preserve the difference between a last-block update and the time a successful request was received. The current age comparison only checks whether `now - update` exceeds the limit, so a future timestamp is not rejected there. See [age check, line 284](../../../demo/midgard-core/src/ogmios-slot.ts#L284). Genesis timing used for cadence must not silently replace the correct era-aware slot mapping on named public networks.

## Ownership, tradeoffs and evidence limits

Assign this as one shared provider-evidence change: one implementation in core, adopted by node startup, readiness, merge fallbacks, preflight and CLI, with committee consumers reviewed too. The change should produce typed reasons for unavailable provider, bad format, stale evidence and wrong identity, rather than classifiers that depend on English error messages. This is an implementation responsibility, not an additional owner policy decision.
