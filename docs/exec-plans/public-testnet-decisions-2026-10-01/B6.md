# B6 — Kupmios reads, upstream changes, and safe recovery

Researched 2026-10-01 against Midgard commit `3027be19cb3bc740f83af0e155e34ab38c7cf894` and the current working tree. This is a decision note; it changes no runtime code or dependencies.

**Recommendation:** keep Kupmios reads as bounded single attempts, use the structured failures supplied by the pinned dependency, and put bounded retry and eventual recovery in Midgard's operation owners. Do not create another upstream PR or a compatibility wrapper for functionality that already shipped. A new upstream contribution is appropriate only for a specific missing transport capability demonstrated by a failing case. The present node retry classifier does have a demonstrated integration gap: it rejects a temporary HTTP 503 even when Kupmios correctly labels it retryable.

## What the question means

Lucid Evolution is the library Midgard uses to construct and interact with Cardano transactions. Its Kupmios provider combines two services: Kupo indexes transaction outputs and associated data; Ogmios exposes Cardano ledger queries, evaluation, and submission. Midgard asks this provider for things such as wallet outputs, protocol parameters, reference scripts, or the status of an already submitted transaction.

“Single-attempt read” means that one call asks once and either returns an answer or fails. If Kupo briefly restarts or a proxy returns “service unavailable,” that call fails even though another attempt seconds later could succeed. A timeout limits how long the call waits; it does not itself retry the call or recover the caller.

The B6 entry proposes “upstream PR + version bump, or a local normalisation seam,” but supplies no particular proposed patch or PR. Consequently, we cannot truthfully describe a specific pending upstream diff. The useful design question is where transport facts should be preserved and where retry decisions should live. The original choice also needs updating: upstream has already delivered much of the necessary transport support, and this checkout already pins the releases that contain it. [Original B6 entry](source-context.md:142).

The node pins `@lucid-evolution/lucid` to **0.6.5**. The lockfile resolves its provider to **0.2.4**. Both are also the versions declared by upstream's current `main` at commit `20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a`, checked on 2026-10-01. GitHub's release API reports publication on 2026-09-17. This establishes that these releases exist and are installed here; it is not a claim that every deployed node has rebuilt against them. [Node pin](../../../demo/midgard-node/package.json#L152), [lockfile resolution](../../../demo/pnpm-lock.yaml#L4988), [upstream provider manifest](https://github.com/Anastasia-Labs/lucid-evolution/blob/20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a/packages/provider/package.json), [provider release](https://github.com/Anastasia-Labs/lucid-evolution/releases/tag/%40lucid-evolution/provider%400.2.4), [Lucid release](https://github.com/Anastasia-Labs/lucid-evolution/releases/tag/%40lucid-evolution/lucid%400.6.5).

Two earlier upstream changes matter:

- **PR #715**, merged 2026-07-16, introduced structured Kupmios and Ogmios errors. A failure can carry its operation, service, HTTP status, timeout/transport/decode category, retryability, `Retry-After`, original cause, and Ogmios error code and data. Its provider-neutral transaction-status API also searches historical outputs, avoiding a false “not found” simply because an output was subsequently spent. [Upstream PR #715](https://github.com/Anastasia-Labs/lucid-evolution/pull/715).
- **PR #726**, merged 2026-08-10, changed UTxO queries to request associated datum and script material through Kupo's `resolve_hashes` response. Previously, reading matching outputs could trigger separate datum/script requests for each output, with their own internal retries. It also made request and confirmation deadlines configurable. The default ordinary request deadline is **30 seconds**; the older `awaitTx` confirmation operation has a separate **160-second** overall deadline. This requires Kupo **2.10 or later**; the checked-in node compose default is **2.11.0**. [Upstream PR #726](https://github.com/Anastasia-Labs/lucid-evolution/pull/726), [current Kupmios source](https://github.com/Anastasia-Labs/lucid-evolution/blob/20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a/packages/provider/src/kupmios.ts#L34), [compose default](../../../demo/midgard-node/docker-compose.kupmios.yaml#L125).

Ordinary reads currently have no automatic failure retry inside Kupmios. `awaitTx` polls successful responses until a transaction appears, subject to its deadline; that successful-response polling is different from recovering a failed request. Submission also makes one provider attempt. HTTP helpers do not add a hidden retry loop. A multi-reference query can make one request per distinct transaction hash, so “single attempt” is not a promise that every public method needs only one HTTP request. Its deadline is applied to each such request; the operation owner still needs an overall work budget. [Kupmios reads, multi-reference query, polling, and submission](https://github.com/Anastasia-Labs/lucid-evolution/blob/20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a/packages/provider/src/kupmios.ts#L210), [HTTP helpers](https://github.com/Anastasia-Labs/lucid-evolution/blob/20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a/packages/provider/src/internal/HttpUtils.ts).

The workspace already patches provider 0.2.6, but the patch changes CML native-script witness verification and lets callers inject a fetch implementation, not retries, timeouts, or error normalization. It does not explain away the behavior above. [Patch declaration](../../../demo/package.json#L49), [actual provider patch](../../../demo/patches/@lucid-evolution__provider@0.2.6.patch#L1).

## The remaining problem in Midgard

The provider now distinguishes temporary transport trouble from a malformed response or a genuine transaction rejection. Midgard does not consistently consume those facts. Its shared `isRetryableProviderError` converts an error to text and searches phrases such as `status code 503`, `status 503`, and `timeout`. Kupmios's structured HTTP error instead says `kupo getUtxos failed (HTTP 503)`.

I reproduced the mismatch using the installed dependency and the current TypeScript helper, with a mocked fetch response:

| Observation | Result |
| --- | --- |
| Number of HTTP fetch calls | 1 |
| Kupmios error category and status | `http`, `503` |
| Kupmios `retryable` field | `true` |
| Midgard `isRetryableProviderError` result | `false` |

This is a concrete classification defect, not a measured live-node crash. Synthetic structured HTTP 429 errors have the same mismatch. There is also an opposite risk: reference-script reads wrap their cause in a message beginning “Failed to fetch,” which the shared predicate always considers retryable. That wrapper can therefore classify even a deterministic failure as temporary. [Classifier](../../../demo/midgard-node/src/provider-retry.ts#L12), [reference-script wrapper](../../../demo/midgard-node/src/transactions/reference-scripts.fetch-reference-script-utxos-program.ts#L125).

A rejected read does not itself terminate a process. Its caller decides whether to retry, skip one cycle, fail startup, or propagate a failure to a supervised task. The available evidence does not establish that every current failure path safely recovers or that this exact mismatch crashes the node. Changing the provider alone cannot guarantee that the node stays up: a caller that treats retry exhaustion as terminal can still fail after any provider improvement.

## Recommended behavior and the tradeoffs

The desired sequence is: a read makes a bounded attempt; a known temporary failure gets a limited retry burst; an exhausted burst releases the current work attempt and leaves dependent operations waiting; later fresh evidence allows them to resume. The process should remain available to explain why it is unready. Waiting must clear when its actual dependency becomes healthy. Retry exhaustion must not change protocol state or turn an unavailable answer into an empty ledger answer.

Transport facts belong in Lucid: HTTP status, timeout, cancellation, decoding failure, and JSON-RPC code. Midgard should consume those fields through a small shared mapping and preserve causes through its own error wrappers. A read failure classified as temporary should become the existing recoverable-source failure category where that caller expects one. Deterministic validation failures, malformed responses, cancelled work, and unknown failures need their own disposition. An explicit Ogmios error-code mapping remains necessary: current upstream's generic `retryable` field does not prove that every JSON-RPC “node unavailable” error is temporary, especially when returned with HTTP 200. [Upstream error classification](https://github.com/Anastasia-Labs/lucid-evolution/blob/20b74d7e9c1df4c0d74b24e819eb47d4e5461e4a/packages/provider/src/errors.ts#L64).

Retry policy belongs in Midgard because it knows what the answer is for, whether the work is stale, whether it holds an ownership lock, and how much time remains before a signed transaction expires. The policy needs an overall deadline as well as an attempt limit, capped backoff with jitter, and bounded handling of `Retry-After`. A worker holding mutation ownership should return a scheduled retry rather than sleep for an extended period while blocking other work. Cancellation must reach the underlying request where supported; a timeout implemented only as racing a promise leaves the original request running. If a retried read observes a different chain point, revalidate the operation's prerequisites instead of combining old and new answers into an assumed snapshot.

| Approach | Benefit | Cost or limitation | Recommendation now |
| --- | --- | --- | --- |
| Upstream capability fix, then a pinned release update | Fixes transport behavior at its source; shared maintenance and tests | Requires upstream review and release; upgrading also requires reviewing existing patches and running Midgard checks | Use for a demonstrated missing capability; the core metadata/timeouts already shipped |
| Shared Midgard mapping of current structured errors | Directly addresses the demonstrated classifier mismatch; lets each owner enforce its own recovery budget | Must preserve fields through wrappers and cover every affected caller | Do this integration work |
| Local replacement Kupmios implementation or legacy-message shim | Could bridge an unavailable upstream fix | Duplicates response parsing and transport behavior; accumulates compatibility debt | Avoid for the pinned current API |
| Automatic retries inside every provider method | Can conceal short interruptions from callers | Can multiply nested retries, exceed caller deadlines, ignore stale work, and mishandle submission ambiguity | Do not make this the default |

A mapping from a current third-party error into Midgard's own recovery model is ordinary integration, not a compatibility implementation of old Lucid behavior. The repository's preference for dependency updates still applies when a released dependency fixes an actual defect. It does not remove Midgard's responsibility to decide how an operation recovers.

## Why submissions need a separate rule

Reading the same output again has no spending side effect. Asking Cardano to accept a transaction does. If Ogmios accepted a signed transaction but its reply was lost, a timeout means **the result is unknown**. It does not mean the transaction was rejected or that its inputs are available for a replacement.

Preserve the exact signed bytes and transaction hash before attempting submission. Reconcile that hash against sufficiently fresh chain evidence. A controlled retransmission of the same signed bytes is different from building and signing a second transaction, but it still needs the submission owner's validity, generation, and ownership checks. A “not found” result from an index that is behind does not establish that the transaction can never land. Release inputs or rebuild only when the existing signed-intent rules establish that doing so is safe.

Midgard already has a dedicated `submitSignedTxWithRecovery`: it persists a signed intent through the configured callback before provider submission, handles validity timing, checks exact transaction confirmation after an unknown-input race, and distinguishes a mode that defers positive waits. Its generic provider-error branch can also retry the same signed object. B6 must not bypass or generalize this flow into a generic “retry anything, then rebuild” wrapper. This note does not independently prove every submission caller installs the persistence callback or every ambiguity case is handled correctly. [Current submission path](../../../demo/midgard-node/src/transactions/utils.submit-signed-tx-with-recovery.ts#L138), [exact-hash race reconciliation and retry branch](../../../demo/midgard-node/src/transactions/utils.submit-signed-tx-with-recovery.ts#L358).
