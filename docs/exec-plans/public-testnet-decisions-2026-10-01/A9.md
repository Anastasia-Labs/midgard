# A9: HTTP probes during startup

The node now binds its configured HTTP `PORT` before runtime service construction, its own worker/cache layers, native owner preflight, DA identity checks, database initialization, and authenticated history startup. While startup is in progress, `GET /healthz` returns HTTP 200 and `{ "status": "ok", "now": "..." }`; `/readyz` returns HTTP 503 and `{ "ready": false, "reasons": ["starting"] }`. Every other request receives the same starting response. No operational route is installed during that interval.

The implementation lives in [listen.starting-http-server.ts](../../../demo/midgard-node/src/commands/listen.starting-http-server.ts#L10). The [operator listen action](../../../demo/midgard-node/src/index.registration-2.ts#L291) wraps runtime service construction in that listener layer, with decoded configuration supplied outside it. The listener therefore binds before Lucid initialization can wait or retry on an L1 provider. The [inner entry point](../../../demo/midgard-node/src/commands/listen.run-node.ts#L417) reuses this preprovided listener; direct source callers receive a scoped listener there. The [reuse branch](../../../demo/midgard-node/src/commands/listen.starting-http-server.ts#L60) borrows the existing service without adding another bind or close finalizer. A bind failure becomes a configuration error naming `PORT` and preserves the underlying cause; it does not proceed with startup. <!-- doc-links:historical -->

The full application becomes available only after the existing startup sequence finishes, including [authenticated history readiness](../../../demo/midgard-node/src/commands/listen.run-node.ts#L274). [Application activation](../../../demo/midgard-node/src/commands/listen.run-node.ts#L311) constructs the existing router with the established service context and admission SQL alias. It then synchronously replaces the target of one native request handler. The same listener and port remain bound, so there is no close/rebind gap and no second request handler delivering duplicate responses. Operational readiness continues to use the existing router's readiness checks.

The helper uses the installed Effect platform's public `NodeHttpServer.make` and `NodeHttpServer.makeHandler` APIs. The former owns the native server's scoped close; the latter captures the application's Effect runtime and supplies the incoming request. The startup application only needs the platform request service, so it does not depend on database, native owner, DA, or history readiness. [The swap](../../../demo/midgard-node/src/commands/listen.starting-http-server.ts#L30) captures those domain services only at activation. A request already dispatched to the starting handler keeps its starting response; subsequent requests use the operational handler. <!-- doc-links:historical -->

The outer server scope also supports the separately requested operator-removal shutdown. The listener stays outside the node's fiber set, so the fiber set carries no HTTP application fiber of its own. [The program](../../../demo/midgard-node/src/commands/listen.run-node.ts#L328) wraps that fiber set in `untilOperatorRemoved`: confirmed removal ends it after a one-second drain, while the starting listener's scope keeps the port answering until the process exits. Membership itself runs as one of the node's fibers and does not delay startup; the A10 module maintains its policy. [Genesis startup](../../../demo/midgard-node/src/commands/listen.run-node.ts#L284) keeps the configured startup policy and the existing background launch after history readiness. Foreign DA reconciliation runs as another node fiber beside publication reconciliation; A1 maintains its policy and transport. These integrations share the entry point but do not change the starting response contract.

## Limits

These tests exercise the actual entry point up to a blocked native preflight, caller bootstrap waiting with listener reuse, and the HTTP helper through activation and cleanup. They do not claim a complete live node startup through real PostgreSQL migrations, native owner startup, DA networking, or authenticated L1 replay. DB and native-build setup were explicitly skipped because these socket tests do not use those systems. The bootstrap test exercises the operator action's layer ordering without invoking the CLI parser or making real L1 provider requests. Actual Genesis transaction cancellation against L1 was not exercised by the startup HTTP tests; its scoped ownership and one-attempt guard were reviewed in the entry point, with the A10 lifecycle suite covering duty drainage separately. No devnet or complete acceptance journey was run for this item. Full workspace lint, dependent-package typechecks, and broader required suites remain the combined change's final verification responsibility.

The operator CLI binds after configuration decoding and before runtime service construction. Direct source callers bind when they execute `runNode`, or can use the same outer layer if their service construction may wait. The listener cannot answer before the process has acquired configuration and begun executing its startup effect. A configuration failure or a fast fatal startup failure closes the scoped listener and exits rather than leaving a permanent healthy server behind. `/healthz` confirms an answering process, not a working database, authenticated history, or permission to perform operator duties. Startup readiness intentionally gives one honest reason, `starting`, until the established operational router can evaluate its richer diagnostics.

No operator-watchdog, readiness-policy, Globals, native-owner, or blueprint implementation was edited for A9. No commits, resets, deployment, or service launches were performed.
