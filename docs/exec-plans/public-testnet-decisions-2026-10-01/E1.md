# E1 — Multi-operator public testnet with high sustained throughput

> Note (deleted 2026-10-03, #752): speculative commit mode and its `SPECULATIVE_COMMIT_BUILD` setting no longer exist, nor does the T2 foreign-tip reconciliation this record describes. File paths cited for them are kept as plain text for history.

Researched 2026-10-01 against the current source at Midgard commit `3027be19cb3bc740f83af0e155e34ab38c7cf894`. This is an architecture recommendation, not an implemented feature or a measured performance result.

**Recommendation:** make every operator an independent full replica that executes blocks from every producer; publish a completed candidate's payload before submitting its L1 header; let the next operator download and verify that candidate during L1 inclusion; and advance production from the latest fully verified canonical pending block without waiting for its challenge period to expire. Settlement runs separately. Keep one canonical block order under the current scheduler and queue contracts, with bounded preparation ahead of that order. The public testnet should launch only after this complete path works across independent operators. Fetching DA alone or narrowing a foreign-tip refusal does not meet the user's multi-operator launch requirement. [User instruction](user-request.txt:55).

## What fails today, and why that changes the decision

The old E1 framing asks whether to accept a maturity-window stall after another operator's block or require earlier publication. The later E6/F2 diagnosis is more serious: local ledger advancement is built around blocks for which this node created its own durable journal. I checked the relevant current source rather than assuming the memo remains exact.

- `landedUnfinalizedMerges` follows the confirmed header's predecessors through local pending-finalization journals. It stops at a missing journal, explicitly including another operator's block. [Current walk](../../../demo/midgard-node/src/transactions/state-queue/merge-to-confirmed-state.landed-unfinalized-merges.ts#L37).
- Ledger materialization folds each local journal's delta onto a known base. If the base is not the current confirmed root and its parent journal is absent, it fails. There is no payload fetch or peer-block execution in that branch. [Current materializer](../../../demo/midgard-node/src/transactions/state-queue/confirmed-ledger-snapshot.ts#L199).
- Commit-base resolution can reuse a local snapshot whose UTxO root matches a foreign header. Otherwise it refuses while awaiting authenticated foreign-ledger finalization. Its candidate selector checks the UTxO root and whether entries exist; this is not complete validation of the foreign block. [Foreign-base resolution](../../../demo/midgard-node/src/workers/commit-block-header.resolve-commit-base-ledger-entries.ts#L222), [selector](../../../demo/midgard-node/src/workers/commit-block-header.select-authenticated-foreign-base-candidate.ts#L12).
- Event-window resolution refuses when events due for an earlier block remain locally unassigned. A peer block therefore needs to advance event assignments as well as ledger balances. [Deposit refusal](../../../demo/midgard-node/src/mpf/event-window.resolve-included-forced-transaction-entries-for-window.ts#L34).

An unchanged UTxO root can permit a limited reuse path, so “every foreign block always crashes” would overstate these branches. The established limitation is that the current path cannot generally reproduce and persist a state-changing foreign block, its event effects, and its ancestry. A restart repeats the missing-information problem. Waiting longer does not create that journal.

Some useful components exist. T2 reconciliation checks the payload header hash, eight commitment roots, and counts against the retained header. This protects event reconciliation, but hashing the supplied state and trace material does not prove that executing the transactions from the authenticated parent produces it. A dishonest producer can commit to a self-consistent but invalid transition. Existing checks (`demo/midgard-node/src/workers/t2-foreign-event-reconciliation.resolve-t2-foreign-event-evidence.ts:39`). <!-- doc-links:historical -->

The watcher's bounded public client exists under the actual class name `WatcherPublicDaClient`. It fetches a deployment-scoped payload by header, validates responses, supports chunk retrieval, limits concurrency, and bounds peer attempts by a fetch deadline. Reuse that transport behavior through a shared package interface; do not reach into another package's source or equate a successful download with successful execution. Client entrypoint, payload lookup and bounded attempts: `demo/midgard-watcher/src/storage/public-da-client.watcher-public-da-client.ts`, since deleted.

## The architecture to build

### 1. A common execution history for local and foreign blocks

Give the node a durable verified-block record containing the deployment identity, authenticated header and parent identity, payload digest and location, consensus profile, canonical L1 origin, verified counts and commitments, execution result, and the replay-derived ledger/event changes needed for recovery. Both locally produced and foreign blocks feed this common history. Keep the local signed-L1-transaction intent separate: importing a peer block must never manufacture a local signature, wallet spend, submission status, or ownership claim.

The existing local journal can remain an input to this history, but confirmed-ledger recovery must traverse authenticated blocks from any producer. This removes the ownership assumption at its source rather than inserting isolated exceptions in the three refusal branches. Reuse the production transition and validation logic; factor shared execution primitives where necessary instead of adding a second consensus implementation for imported blocks.

For each imported block, the receiver must:

1. Authenticate the header's deployment, producer eligibility, parent, L1 inclusion/order, and time bounds using the actual protocol rules. A DA announcement supplies a candidate to fetch, not canonicality.
2. Obtain bounded payload bytes and validate their envelope, exact header identity, format, ordering, unique entries, and all lengths and counts. Check `utxosRoot`, `transactionsRoot`, `depositsRoot`, `withdrawalsRoot`, `forcedTransactionsRoot`, `validationTracesRoot`, `transitionTraceRoot`, and `eventToStepRoot`.
3. Execute from the independently authenticated parent state. Validate signatures, transaction semantics and scripts, accepted/rejected forced-transaction outcomes, event ordering and inclusion obligations, and trace relationships. Supplied post-state or trace bytes are claims to check, not authority to overwrite local state.
4. Derive ledger changes, event assignments, counts, and commitments from that execution. Compare them with every relevant header commitment; compare supplied post-state material with the independently derived result under the current payload format.
5. Persist the result with its parent/root/generation and replay cursor. Promotion must preserve the existing native-owner and database crash-recovery ordering; an atomic SQL update alone is not an atomic SQL-plus-native-store commit. Restart must either finish a prepared promotion or resume from the prior durable point.

The node then has three distinct facts: a header is observed on L1; its block is independently executed locally; and its block has reached protocol settlement. The committed pending execution head can be ahead of the settled ledger. Production may use that verified pending head under the protocol's descendant rules. Withdrawal settlement and other irreversible actions retain their own settlement requirements. Do not reuse “Finalized” to mean all three facts.

Peer execution must update the confirmed ledger when the block actually merges and also update the pending/mempool view when it is a valid pending ancestor. Reconcile locally pending transactions that the peer included or made invalid, and assign included L1 events to the correct foreign header. Otherwise ledger synchronization can succeed while the next builder still double-includes an event or remains trapped behind an overdue local row. Current confirmed-merge finalization already couples ledger and event updates for local blocks; generalize the authenticated inputs to that operation. [Current merge effects](../../../demo/midgard-node/src/transactions/state-queue/merge-to-confirmed-state.finalize-confirmed-merge-program.ts#L44).

### 2. Make data available before the header transaction is sent

Today's normal publication trigger follows local finalization and falls back to a durable reconciler. That is useful recovery machinery, but it is not a pre-submission availability prerequisite. Payload construction also materializes a local journal snapshot during local finalization. Move candidate construction and publication earlier while preserving the outbox and reconciliation path. [Current construction](../../../demo/midgard-node/src/workers/utils/commit-submission.finalize-committed-block-locally.ts#L127), [publication trigger](../../../demo/midgard-node/src/fibers/da-publication-trigger.ts#L9).

Recommended sequence: complete and locally verify a candidate; durably retain its exact payload; publish to the configured DA committee; obtain the required authenticated retention receipts for those exact bytes; announce it to peers; then submit its header under a fresh scheduler and tail check. The next operator can download and execute while L1 inclusion is pending. A receiver may cache the execution result provisionally, but it cannot treat the announcement as a landed canonical parent.

Do not require every operator to acknowledge before production proceeds. A single slow or hostile replica could veto the chain. The existing deployment's DA threshold should govern the storage prerequisite, while each operator independently verifies the parent it will build on. The implementation must establish that receipts bind the deployment, candidate/header identity, payload digest, retention obligation, signer, and expiry. A storage acknowledgment is not a proof of a valid transition or an on-chain DA attestation. The current committee record explicitly labels submitted payloads fetched rather than verified and says its ACK proves retention only. [Current distinction](../../../demo/da-committee-node/src/store.libp2p-submitted-da-payload-record.ts#L25).

Pre-header staging must align with A8's admission policy: authenticated eligible producers, per-producer and global byte/work limits, a small bound on candidates per parent, deduplication, expiry, and promotion only after authentic L1 observation. Unlanded proposals cannot acquire canonical retention rights forever or fill committee storage indefinitely. If current serving gates require a landed header, introduce an explicitly bounded staging capability; do not silently relax canonical serving or retention rules. An unlanded proposal needs an honest status that receivers can distinguish from committed data.

This prerequisite is initially an honest-node submission policy. It does not prove that the existing validators prevent a malicious producer from committing a header without early publication. Retain the protocol's availability attestation, challenge, timeout, and removal mechanisms for that case. A peer-data failure pauses dependent production and triggers bounded recovery; a missing-data wait ends only with verified data or an authenticated protocol change that removes the dependency. Neither elapsed maturity nor a retention receipt alone proves the transition valid.

Header time is bound to the commit transaction's validity upper bound, so this is not “publish an arbitrary block and choose its time later.” Choose a valid candidate/time window in advance and leave sufficient time for publication. Recheck expiry and scheduler eligibility immediately before signing/submission. Changing the header changes its identity and requires a new candidate receipt. Once a signed attempt may have reached L1, preserve and reconcile that exact intent before allowing replacement. [Current time binding](../../../demo/midgard-sdk/src/state-queue-transactions.build-commit-block-header-tx-program.ts#L95).

Candidate execution also needs authenticated L1 event history covering the protocol's inclusion cutoff. Early preparation cannot guess that no additional due events will appear. If the cutoff is not yet provable, stage reusable transaction validation and payload fragments, then complete the event list and exact header only when the required history is available. Measure this part of the critical path as well as upload time.

### 3. Pipeline useful work without replacing canonical order

Overlap transaction intake and stateless validation, candidate execution, DA upload, peer download/replay, L1 inclusion, and settlement. The next scheduled operator should already maintain the same execution head and prepare transactions during the preceding operator's turn. Cache results by the exact parent, payload digest, deployment and consensus parameters so handoff uses completed work instead of repeating it.

Bound preparation ahead of the canonical tip. Allow reversible speculative computation, but keep signing and submission subject to canonical-tail, generation, scheduler, and signed-intent checks. When a parent loses its L1 slot or is removed, invalidate descendants' prepared state and event projections and rebuild from the winning authenticated ancestor. No speculative artifact should silently advance the settled ledger.

Initially enable speculation only after foreign replay and rollback are proven. The `SPECULATIVE_COMMIT_BUILD` default was false; turning it on was not a solution to the missing shared execution history (deleted 2026-10-03, #752). [Current default](../../../demo/midgard-node/src/services/config.make-config.ts#L202).

## What limits throughput

The queue remains one canonical sequence. Ordinary appends consume the latest tail output and recreate its continuation. They reference the singleton confirmed-state root rather than consume it. Consequently, concurrent producers racing the same tail do not produce independent useful canonical blocks; one wins and others must reconcile. Merges change the confirmed root and head, while corrections can invalidate referenced queue state, so their interaction with append preparation also matters. [Tail consumption](../../../demo/midgard-sdk/src/state-queue-transactions.build-commit-block-header-tx-program.ts#L205), [root reference semantics](../../../onchain/aiken/lib/midgard/state-queue.ak#L362).

More operators increase availability and independence. They do not multiply the capacity of this one ordered state machine. For sustained operation, every operator that can inherit a turn must replay at least as fast as blocks arrive. Parallelize downloads and state-independent validation, while applying dependent ledger transitions in canonical order. Prioritize the earliest missing parent over later candidates and enforce bounds on bytes, replay work, queue depth, native generations, and retained provisional state.

A useful capacity model is:

`sustained L2 transactions/s <= min(execution capacity, inheriting operators' replay capacity, usable DA bytes/s divided by bytes per transaction, canonical header capacity times transactions per header)`.

This is a planning relationship, not a numerical result. Under a serial handoff, prepublication moves download and replay into the L1 inclusion interval; only the remaining verification work adds to the next producer's critical path. It eliminates a needless challenge-window wait only when verification finishes. It does not remove L1 transaction dependencies or justify using unverified state.

For the current launch, favor well-filled, byte-and-compute-bounded blocks and fast verified handoff. Keep forced-event capacity reserved, limit latency under low load, and apply backpressure before queues exhaust memory. The present full-UTxO payload representation grows with ledger size; it can dominate DA bandwidth and replay even when blocks contain few transactions. A6's compact transaction/event encoding and E3's authenticated snapshot catch-up path therefore affect competitive sustained throughput, not just storage convenience. Do not claim high long-term capacity from a benchmark using a small fixed ledger.

Rotating operators only every longer production interval can reduce handoff overhead, if the protocol permits those intervals, but increases censorship latency and delays another operator's opportunity to produce. Rotating very frequently improves access to turns but magnifies handoff cost. Use measured handoff time and the actual scheduler rules to tune intervals; do not invent a faster local schedule that the validators do not authorize. Scheduler alignment currently checks eligibility against authenticated active/registered sets and the target commit window. [Current eligibility path](../../../demo/midgard-node/src/workers/utils/scheduler-refresh.ensure-scheduler-aligned-for-commit.ts#L97).

A missing producer still needs the existing inactivity/takeover mechanism. The designated successor acts first, with other active operators delayed by a patience window. Distinguish peer-data unavailability from producer inactivity in local status, while preserving the protocol's actual strike rules. A removed operator must become unready and shut down under A10; replay or scheduling recovery cannot automatically register it again. [Current watchdog policy](../../../demo/midgard-node/src/fibers/operator-watchdog-policy.ts#L64).

## What leading rollups teach us, and what does not transfer

OP Stack derives an execution chain from ordered batches and L1 events and can derive eagerly once the necessary data and parent state exist. Its unsafe, safe, and finalized heads distinguish quickly executed information from increasingly durable ordering. These are useful precedents for separating execution from settlement and keeping replicas able to reconstruct state. Its derivation specification explicitly assumes a single sequencer and batcher; it does not establish that copying its pipeline solves Midgard's multi-operator handoff. [OP derivation specification](https://specs.optimism.io/protocol/derivation.html), [OP head definitions](https://specs.optimism.io/glossary.html).

Arbitrum Nitro distributes a real-time transaction feed and later posts compressed batches to L1. Full nodes run the deterministic transition function on the ordered input sequence, rather than depending on the sequencer's private database journal. The feed supplies an earlier, weaker ordering promise; the L1 record provides stronger ordering assurance. Its designated sequencer architecture differs from Midgard's rotating bonded operators. The transferable lesson is independent execution from shared inputs and overlapping delivery with settlement, not importing its trust assumptions. [Arbitrum architecture](https://docs.arbitrum.io/how-arbitrum-works/inside-arbitrum-nitro).

If measurements show that one L1 header transaction per Midgard block prevents the desired capacity or latency, the deeper option is a specified sequence of smaller off-chain blocks committed in larger batches. That requires rules for operator handoff, equivocation, forced inclusion, batch commitments, DA, rollback, settlement, and fault proofs. A signed feed alone does not settle order between competing Midgard operators. Treat that as a separate protocol program with its own adversarial review, not a configuration toggle in the public-testnet fix. Concurrent independent block streams or sharding likewise require conflict/order semantics beyond the current single UTxO-root chain.

| Choice | Throughput implication | Decision |
| --- | --- | --- |
| Wait for maturity after every foreign block | Avoids one uncertain-parent case but retains the missing general import/finalization path; adds settlement latency to production | Does not meet the multi-operator requirement |
| Add DA retrieval only | Makes peer bytes reachable; does not execute or persist peer ledger/event effects | Necessary component, insufficient launch scope |
| Import and execute peers, prepublish, and overlap stages | Removes ownership dependency and hides much handoff work behind inclusion without weakening validation | Recommended launch architecture |
| Let operators build on unchecked headers or trust the supplied UTxO list | Lower apparent latency with incorrect-transition and descendant liability risk | Refuse |
| Add off-chain ordering and batched commitments | May remove the per-block L1 latency bottleneck; substantially changes protocol and security analysis | Follow-on program if measurements justify it |

## Implementation stages and launch gates

These stages are engineering milestones before the same multi-operator public launch, not permission to launch a single-operator substitute.

1. **Make foreign execution durable.** Shared verified-block history, authenticated parent replay, event/mempool reconciliation, foreign merge finalization, and crash recovery. Prove alternating producers can change the ledger and settle while each database contains no private journal from the other.
2. **Complete availability before submission.** Candidate payload construction, bounded staging/admission, exact retention receipts, prepublication, peer prefetch, signed-intent reconciliation, and orphan expiry. A restart at every boundary resumes safely without losing needed payloads or signing a competing spend.
3. **Enable bounded pending-head production.** Verify valid foreign parents before descendants, retain known-invalid refusals, handle L1 rollback/removal across alternating producers, and enable reversible preparation only after those paths pass. E2's descendant/event-obligation specification decision and E4's complete foreign validation/operator-binding issues must be resolved wherever they affect this path.
4. **Measure and tune the shared bottlenecks.** Execution, DA bytes, replay, header inclusion, scheduler handoff, queue/memory bounds, and growing-state payload costs. Tune batch size, permitted turn duration, prefetch, and worker concurrency from those measurements, without lowering protocol finality or bypassing faults.

Before claiming launch readiness, run a fresh live network with at least three independently managed operator wallets, databases, and native stores plus the configured DA committee and watcher. Require:

- Repeated A→B→C→A handoffs with state-changing transactions, deposits, withdrawals, accepted and rejected forced transactions, empty blocks, and eventual matching ledger/event/trace commitments at every replica.
- Progress across several foreign merges and an operator restart while the others continue, including catch-up after the permitted retention horizon through the chosen E3 recovery mechanism.
- L1 rollback, competing same-tail candidates, removed invalid ancestors with pending descendants, DA peer failure/withholding, slow downloads, and producer inactivity/takeover. No dependent block uses unchecked or invalid state, no duplicate event effects occur, and temporary holds clear on valid evidence without a process restart.
- Crash injection around payload storage, publication receipts, signed submission, imported-block persistence, native promotion, and SQL finalization. Restart resumes the authenticated chain and preserves unresolved signed intents.
- Bounded unlanded staging and resource use under unauthorized traffic and hostile eligible producers, alongside successful honest publication and handoff.
- Sustained mixed load on both a small and a growing ledger, including script-heavy transactions. Record canonical committed and settled goodput, not merely accepted ingress; p50/p95/p99 handoff and confirmation latency; DA and replay lag; missed turns; orphan/rebuild rate; memory/disk growth; and time spent blocked on the tail, scheduler, head/root references, and publication.

The slowest supported inheriting operator needs enough replay headroom to catch up under that workload. Define that supported hardware/network envelope and an operating point below saturation from evidence. No particular TPS, speculative depth, timeout, block-fill target, or rotation interval is established by this investigation.
