# D2 — Harden supervision and recover the cause

Decision recommendation, 2026-10-01. Read-only assessment of the current working tree, including the uncommitted full-stack tooling. This document proposes behavior; it does not implement it.

Your concern is correct: restarting a process does not repair a bad configuration, missing authority, corrupt database, or contradictory protocol evidence. The best approach is to make expected failures ordinary recovery states, keep the management process small, and permit automatic restarts only when there is a known safe recovery procedure. A process manager is useful for ownership and host reboot recovery; it cannot decide whether protocol work is safe.

## What the current code actually does

The [earlier D2 memo](source-context.md:192) names `superviseServices` and says that a throw leaves services orphaned. A search of `demo` found no function with that name in this checkout. That claim describes an earlier implementation; I cannot verify its exact throw or cleanup paths here.

The current uncommitted implementation is different. The [stack controller](../../../demo/midgard-node-tools/src/e2e-stack.ts#L91) performs setup and a finite wallet journey, then exits. It starts [runtime containers in detached mode](../../../demo/midgard-node-tools/src/full-stack/runtime.ts#L320). Docker owns the running containers independently of that command; the [current documentation](../../../demo/midgard-node-tools/docs/PREPROD_STACK.md#L91) explicitly promises this. A controller failure interrupts setup or verification, but does not by itself remove Docker's supervision of containers that have already started. Partial setup can nevertheless leave only part of the stack available. <!-- doc-links:historical -->

Existing restart policies are already broad: the [node uses `restart: always`](../../../demo/midgard-node/docker-compose.yaml#L55), Cardano/Ogmios/Kupo do likewise, and [generated DA services use `unless-stopped`](../../../demo/midgard-node-tools/src/full-stack/da-services.ts#L179). These policies react to process exit, regardless of its protocol meaning. An unready response also differs from an exited process: a Docker health check records health, while restart policy governs exit. Neither establishes that a recovery is safe. [Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/), [Docker health checks](https://docs.docker.com/reference/dockerfile/#healthcheck).

Consequently, the earlier recommendation to add an OS restart policy is incomplete for the current tree. We already have container restarts; we need narrower recovery decisions and persistent stop reasons.

## When can it throw or crash?

There are three distinct situations.

**Expected refusal or temporary failure returned through a promise.** The controller catches these, prints a message and sets exit status 1; this is a handled failure, not necessarily a software crash. Its [top-level catch](../../../demo/midgard-node-tools/src/e2e-stack.ts#L142) currently gives all such failures the same exit status. Concrete causes include: <!-- doc-links:historical -->

| Cause in current source | What restarting would accomplish |
| --- | --- |
| A [command fails](../../../demo/midgard-node-tools/src/full-stack/process.ts#L50), including a failed Compose operation or command-lock contention | A retry may help after temporary contention or a restored Docker connection. A missing binary, bad command, or bad configuration needs correction. Preserve the underlying cause rather than classify every nonzero exit as temporary. |
| A [readiness wait expires](../../../demo/midgard-node-tools/src/full-stack/process.ts#L81) | The dependency may recover later. Polling it is usually sufficient; restarting healthy services does not accelerate chain synchronization. |
| A [previous transaction remains ambiguous](../../../demo/midgard-node-tools/src/full-stack/workflow.ts#L47) | Restarting does not establish whether it landed. Continue checking its existing identity; do not construct another transaction merely because the response was lost. |
| A [saved checkpoint is malformed or belongs to another configuration](../../../demo/midgard-node-tools/src/full-stack/journal.ts#L57), or a [storage identity is missing/mismatched](../../../demo/midgard-node-tools/src/full-stack/storage.ts#L166) | The refusal is intentional protection. Repeated startup with identical inputs will refuse again. Do not delete the records to make startup succeed. |
| A checkpoint write fails during [write, sync, rename, or directory sync](../../../demo/midgard-node-tools/src/full-stack/journal.ts#L27) | Temporary filesystem unavailability may clear, but disk exhaustion or lost write permissions is not repaired by restarting. Do not perform further irreversible operations when their evidence cannot be saved. |

**A defect escapes those boundaries.** Asynchronous event callbacks can fail outside the promise being awaited. The existing host-process test harness creates a [log write stream](../../../demo/midgard-node-tools/src/e2e/logged-child-process.ts#L110), but this file has no stream error handler. A filesystem error emitted by that stream can therefore escape normal command error handling. It also retains [combined output](../../../demo/midgard-node-tools/src/e2e/logged-child-process.ts#L267) and [stdout](../../../demo/midgard-node-tools/src/e2e/logged-child-process.ts#L313) in growing strings. Those are concrete hardening opportunities; no live crash or memory measurement was performed. This is the existing command/test harness, not the missing historical supervisor.

**The process cannot run at all.** A host reboot, explicit kill, memory exhaustion, or runtime failure can prevent its own cleanup code from executing. Reliable application code reduces these failures; it cannot recover itself after it ceases to execute. For a truly uncaught JavaScript exception, keeping the same process running can preserve unknown partial mutations. Node's own guidance is to shut it down rather than resume normal execution. [Node.js process guidance](https://nodejs.org/download/release/latest-jod/docs/api/process.html#warning-using-uncaughtexception-correctly).

The separate [host-process supervisor](../../../demo/midgard-node-tools/src/e2e/service-supervisor.supervise-host-process.ts#L213) already limits restarts, defaults to zero, and refuses unknown errors. Its environment construction, attempt execution, and summary parsing can still reject. Its log-text classification is suitable evidence tooling, but should not become the authority for public-testnet protocol recovery. Use structured reason codes whose origin and relevant state are retained.

## Recommended recovery policy

1. **Recover an operation before replacing a process.** For a dropped provider connection, close the old session, reconnect, recheck the chain position, and resume from saved evidence. For a temporarily unavailable database, stop dependent writes and reconnect. For delayed transaction visibility, query the existing transaction. For a reorganization within supported recovery bounds, follow the normal verified rewind/replay procedure. None requires restarting the whole stack.
2. **Make recovery bounded without making an ordinary outage permanent.** Give each request a timeout and a small retry budget, with increasing delays and slight random variation so every node does not retry simultaneously. After that budget, remain visibly unavailable and make low-rate, read-only dependency checks. Resume automatically when those checks establish recovery. Do not continually restart services while waiting. The timeout must not discard the saved transaction or proof intent.
3. **Use restart only for failures with an explicit safe restart procedure.** Recreate a failed session or worker when its ownership and saved state are known. Restart one service when that smaller repair fails and a clean startup can validate all durable state. As an initial deployment policy, allow at most three service restarts per fifteen minutes, then hold it stopped/unavailable. These numbers are proposed operating defaults, not measured protocol constants. Reset the budget only after sustained healthy operation and real progress, not after briefly opening a port. A continuing known dependency outage may re-arm recovery when the dependency actually becomes healthy; an unexplained repeat crash does not.
4. **Require intervention for unresolved integrity or authority failures.** Corrupt records, incompatible deployment identity, contradictory authenticated evidence, invalid release signatures, operator removal, and repeated unknown crashes must retain a durable stop reason. Restarting must not clear it. Automated re-derivation may resolve a contradiction only where a separately specified verification procedure proves the replacement state; D2 grants no new permission to erase evidence, refill a slashed bond, re-register an operator, or redeploy.
5. **Save enough context to enforce the policy across crashes.** Retain deployment/service identity, failure reason, first/last occurrence, attempt count, next allowed recovery, the last verified chain position, and references to pending signed transactions. Store these atomically. On startup, take exclusive ownership, validate the saved identity, inspect existing containers/children, and reconcile pending work before creating new work. A restarted controller must inherit its retry budget and stop reasons. If these records cannot be read or saved reliably, hold state-changing recovery.

Optimism demonstrates the deeper pattern: its rollup node determines the L1 data needed after restart from the execution engine's syncing state, while its derivation specification defines how to reconstruct progress around reorganizations. Its documentation also identifies recovery situations requiring an explicit recovery mode. The useful lesson is to encode a safe reconstruction procedure and its boundaries, rather than assume a repeated process start repairs every fault. This is an architectural inference, not a claim that Optimism's exact policies fit Midgard. [OP node operations](https://github.com/ethereum-optimism/optimism/blob/develop/op-node/README.md), [OP derivation specification](https://specs.optimism.io/protocol/derivation.html).

## How to make the manager reliable

Keep service ownership with one established process manager. Keep the setup/journey command finite; do not turn it into an immortal process that rebuilds images, rechecks funding, and reruns deployments every time an HTTP probe fails. If continuous coordination is needed, separate it from setup and give it only observation, approved recovery, and status-reporting responsibilities.

Catch expected failures at the operation that understands their meaning. Ensure every spawned child and asynchronous task has a completion/error path; handle log-stream errors, bound retained output, respect stream backpressure, and rotate diagnostic logs. Cancel obsolete recovery attempts so an old reconnect cannot publish state after a newer one succeeds. Ensure all waits and shutdowns have deadlines. For directly owned host children, terminate and reap the verified process group; escalate a failed graceful stop only for that owned group. For detached Compose services, leave ownership with Docker and reconnect to the same containers instead of creating duplicates.

Keep health and readiness distinct. The manager can be alive and correctly managing a temporarily unavailable dependency while the stack is unready. A readiness failure must not automatically trigger a liveness restart. Expose the current reason, how long it has persisted, the next recovery action, and whether human action is required. Send a meaningful incident notification once, then update it when the situation changes.

For host services, systemd supplies restart exclusions by exit status and start-rate limits. For containers, Docker offers bounded `on-failure` retries, but does not distinguish different nonzero protocol reasons; its daemon-restart behavior also differs from `unless-stopped`. Therefore replacing `always` with `on-failure:3` alone is insufficient. A durable application stop reason must guard protocol startup independently of the process manager. Choose one owner per service; do not let Docker and a host manager independently restart the same container. [systemd service manual source](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml), [systemd rate-limit defaults](https://github.com/systemd/systemd/blob/main/man/systemd-system.conf.xml), [Docker restart policy documentation](https://docs.docker.com/engine/containers/start-containers-automatically/).

The tradeoff is a little more explicit recovery state and fewer speculative restarts. In return, routine outages clear themselves without repeated deployment work, while serious failures remain auditable and cannot disappear during a reboot. Disabling every external recovery would leave host kills and reboots requiring manual action; unlimited external recovery would hide repeat defects and safety refusals. Bounded, state-aware recovery preserves both reliability and the intervention boundary you requested.
