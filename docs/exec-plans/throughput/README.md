## Cross-cutting binding contracts

1. **P3 ↔ P4:** Phase 3 must export the `LedgerOverlayHandle` lifecycle (`rootHex/fork/applyBlockDelta/promote/discard` + guarantees G1–G3) exactly as named in P4 §8.1; bound in P3 §8. Any rename updates both docs in the same commit. P4's budget assumes P3's exit criterion (50k-tx build <10 s p95).
2. **P1 ↔ P3:** planner caps (`COMMIT_MAX_L2_TX_COUNT` …) are the page-size contract for P1's keyset-paginated `MempoolDB.retrieve`; oldest-first ordering is assumed by P3's EWMA sampling.
3. **P1 C4 atomicity:** ASC flip + both endTime anchors (`commit-block-planner.ts:308-313`, `mpf.ts:1445-1448`) + composite index land as one commit.
4. **P5 ↔ merge path:** threshold-ACK is safe because merge gates on the applied on-chain attestation (`merge-readiness.ts:394-405`), not transport ACKs; startup assert `manifest.threshold >= da_threshold`.
5. **Phase 0 prerequisites (all plans):** per-stage dashboards; MPF phase timers + blake2b digest-throughput measurement + recorded op-stream corpus (P3); baseline p95 builds at 1k/5k/10k txs vs 100k/1M-entry ledgers.

## Sequencing & expected ceilings

P1 (wks 1–3) → Stage A ≥5k admits/s, starvation fixed. P2 (3–7) → Stage B ≥10k tx/s on 8 cores (medium-high; hinges on measured per-tx Phase A cost and P1's accept-path rate). P3 (4–10) → 50k-tx build <10 s (medium-high; residual eager-hashing risk carries a library-fork contingency for incremental 16-ary merkle updates). P4 (8–14) → cadence ≈ L1 confirmation latency; with P3, Stage C ≥2,500 TPS. P5 (10–14, parallel) → DA egress ÷3–6, publish returns at quorum. Then parent plan Phase 6 soak validates end-to-end.
