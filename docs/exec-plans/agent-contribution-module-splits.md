## Scope and behavior

This sweep uses the preceding audit's threshold of more than 5,000 physical
source lines, including tests and generated source. The optional broader
2,000-line threshold was not selected. Nine remaining modules exceeded the
threshold. All nine were decomposed; the final inventory covers 4,784 source files and finds
zero source files above 5,000 lines and 93 above 2,000 lines. The inventory
uses `git ls-files --cached --others --exclude-standard -z`, deduplicates paths,
reads existing source files and counts physical lines. The largest is now
`demo/da-committee-node/tests/provider.test.ts` at 4,474 lines. JSON datasets,
lockfiles and documents are not source modules in that inventory.

The [work plan](agent-contribution-parallel-work.md#oversized-module-sweep)
lists the new concern boundaries. All four production declaration splits keep
their original public import paths. The trace builder is a separately reviewed
refactor because its preparation and execution shared mutable local state.
Its budget record preserves that sharing across the new phase boundary.

The database and committee suites retain their original registration entrypoints,
hooks and registration order. Database helper and subprocess paths are rebased
explicitly to the original test directory. Aiken test helpers become public only
where the new test modules require cross-module access. The CEK generator owns
all 26 new generated modules; its JSON manifest lists the output paths.

## Diagnosed failures and limits

The compiled profile at the base and after the split is `preprod-testing`.
That profile intentionally refuses interactive disputes because its maturity
window is shorter than a complete dispute. The full fault-proof suite still
contains scenarios expecting interactive openings. Two timing tests fail
identically against an untouched copy of the original submission module.
A second baseline run used a temporary Vite resolver that redirected all five refactored production entrypoints to
their original source files and reproduced four selected failures: those two
timing tests, CEK context stage zero, and the deep-deposit transition trace's
unusable validity window. That run collected 51 cases, executed four and skipped
47 by selection; exit 1. It did not validate the skipped cases.

A watcher comparison used the same original-module resolver and ran the three
failing local-capture, objective-progress and decision-journal files serially:
39 passed and 14 failed of 53, exit 1. It reproduced thirteen supervisor
headroom configuration failures and the exact-output CBOR mismatch. The
additional local-capture cleanup failure seen during the broad concurrent run
did not reproduce in this baseline run; its cause remains unconfirmed.

The initial SDK transaction preparation check passed 175 Lucid tests, then the
SDK suite passed 873 and timed out in two unchanged static-completion cases,
exit 1. The initial node run also expired a history-authority lease during its retention test, timed out in the deployable-script setup hook, and failed a scheduler-headroom assertion for an unaligned candidate.
Both SDK files then passed all eight tests with their existing timeouts when run serially (`pnpm --dir demo/midgard-sdk exec vitest run tests/lucid-inline-datum-preservation.test.ts tests/lucid-static-completion.test.ts --maxWorkers=1 --minWorkers=1`, exit 0). The split database file itself collected 128 tests in that run: 127 passed and the unchanged saturated-vs-baseline latency-ratio assertion failed. A focused run loading the original database file and original production modules passed that case (one passed, 127 excluded by selection, exit 0). The comparison used a separate `MIDGARD_TEST_DATABASE_PREFIX` so it could not reset the active run's worker databases. This single baseline observation does not establish a failure rate or prove why the concurrent run failed. The final full database rerun passed all 128 cases with a separate database prefix and unchanged assertions; the full fault-proof result is recorded above.

A further node check ran `tests/deployable-scripts.test.ts` and
`tests/event-history-journal.test.ts` with `-t 'deployable-script catalogue|advances at most RETENTION_BATCH'`,
`--maxWorkers=1 --minWorkers=1 --disable-console-intercept`, `NODE_ENV=emulator`
and a separate database prefix: 11 passed, one failed and 38 excluded by
selection of 50; exit 1. The catalogue setup succeeded; the history-authority
lease expiration persisted. The scheduler's `tests/deposit-flow-emulator-commit-selection.test.ts`
with `-t 'direct wake path'` failed identically with original modules and current
modules: each one passed, one failed, two excluded by selection, exit 1. Both
runs received `SubmittedAwaitingConfirmationOutput` where the unaligned case
expected `SpeculativeCandidateInvalidatedOutput` with reason `T4`.

A second watcher baseline ran the origin, attestation and runtime files with
original modules: 15 passed, two failed and six skipped of 23, plus a failed
origin setup suite; exit 1. It reproduced both attestation timing assertions and
the missing canonical provider-sync setup. The broad-run pending-native-growth
failure did not reproduce. Representative comparisons do not establish that
every broad-suite failure pre-existed.

The full fault-proof suite rewrote the tracked transition-trace workflow fit
ledger with fresh measurements. That test-generated change was restored to its
original bytes; it is not part of the module split. The local blueprint remains
an untracked build artifact.
