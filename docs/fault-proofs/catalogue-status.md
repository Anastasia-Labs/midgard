## 1. The twenty-nine compiled directories (`onchain/aiken/validators/fraud-proofs/`)

Twenty-five directories are registered proof categories; `mpf-chunked-proof`
is shared support machinery and is not a catalogue category. Three further
directories — `value-not-preserved`, `input-set-uniqueness`, and
`mint-authorization` (rows 26–28) — are pre-registration families: built and
compiled, with category ids `00000019`/`0000001a`/`0000001b` reserved but not
yet in the catalogue.

"Registered" = present in the deployment catalogue
(`demo/midgard-sdk/src/fraud-proof/catalogue.ts` —
`FRAUD_PROOF_CATALOGUE_CATEGORY_ORDER`, exactly 25 categories with positional
ids `00000000`–`00000018`; append-only). The same 25 are accepted by generic
`submit-init`, required by deployment inspection, bound into the node/core
manifest identity, and authenticated by the watcher proof-thread deployment
authority. The canonical registrations added at `0000000b`–`00000018` are:
`fabricatedDeposit`, `fabricatedWithdrawal`, `nativeScriptDecoding`,
`missingSignature`, `missingNativeScriptTx`, `withdrawnReferenceInput`,
`canonicalDecodability`, `committedFieldShape`, `minFee`, `withdrawalMistag`,
`doubleWithdraw`, `crossBlockDuplicateEvent`, `l2TxMistag`, and
`withdrawnInput`, in that order. `transitionTrace` remains `00000004` and its
deployed graph is the route validator plus eight possible terminal validators,
not a nine-step linear chain. Every step validator named by this identity must
be published and consumed as an authenticated reference script. Because the
catalogue is immutable and the positional manifest identity moved, adoption is
a fresh genesis/redeployment only; there is no migration or compatibility
path. Watcher family/topology authority does **not** mean that an autonomous
fault detector or prover is mounted.
"Tooling" = prepare/submit modules and, where noted, CLI verbs in
`demo/midgard-fault-proofs`.

### 1a. Transaction binding

Every standalone family binds its disputed transaction through
`verify_native_tx_in_state_queue_node` / `pass_native_tx_to_next_step`
(`common.ak:575-634`): the raw MPF root is authenticated against the header's
**counted** `transactions_root`
(`commit_counted_root(TransactionsRootDomain, raw_root, l2_transaction_count) ==
transactions_root`, `:615-620`), then membership is proven with
`plutarch_phas_raw` over the raw native-V1 transaction CBOR (`:623-631`). No
other transaction-binding path exists under `onchain/`; closure work must not
introduce one. Binding is not closure: each family's remaining evidence,
tooling, and lifecycle state is what the table columns track.

per `docs/consensus-profile-v1.md` §8 (there is no rejecting-successor clearing
clause in `validation-machine-v1.ak`; VM-DEFECT-2 records why one must never be
reintroduced — it made every rejection unprovable). Dispute-level regressions,
green as of the audit date: `submit-init-emulator-soundness.test.ts`
(challenger wins a one-step resolution against an operator-claimed `Accepted`
descriptor carrying a non-empty delta root),
`submit-init-emulator-soundness-honest-operator.test.ts` (the honest operator
cannot be defeated on the same shape), and
`submit-init-emulator-soundness-cleared-delta.test.ts` (a cleared-delta
rejecting successor is rejected). Machine-level positive proof and
mutation/valid-block negative controls: `validation-machine-v1.test.ak`.

**Scope limits of the one-step L2 verifier** (`validate_l2_transaction_transition`,
`proof.ak:1117-1157`): it authenticates preimage hashes and MPF-replays the delete/insert
set against the ledger trie, then asserts root divergence. It does **not** check value
conservation, fee/mint correctness, or spend authorization — `witness_set_hash`,
`required_signers_hash`, `script_integrity_hash` are decoded but unused. Those checks are
(by design) not the trace walker's job: value conservation, mint authorization,
min-ada, min-fee, signatures, and network-id are enforced per transaction in
`validation-machine-v1.ak` and adjudicated through the registered
`validationTraceDispute` family (§1 row 14; single-party obligations in §6).

**Valid forced execution**: bound through complete accepted-transition binding.
A valid
forced source commits an accepted validation descriptor and terminal ledger
frontier; the accepted-transition proof compares that authenticated successor
with the transition trace's post-root. Concrete validator-hash-bound
publication, dispute, and settlement measurements remain release-gating
evidence rather than a disabled protocol branch.

native inclusion path (`verify_native_tx_in_state_queue_node`,
`common.ak:575-634`) binds a new step proof to any L2 tx in a committed block's

`apply_l2_spends` fetches it (ledger-membership witnesses carrying
`witness.value`, `proof.ak:680-692`). A self-consistent trace that faithfully
applies an _invalid_ tx (`validity_code==0`, outputs > inputs) produces a
correct root — so these are **not** trace faults; per GOAL_SPEC §3 invariant 3

Verified non-gaps from the same sweep (recorded in matrix §11c): deposits have **no
refund path** (`deposit.ak` spend is absorb-to-reserve only), so an included deposit
cannot also be reclaimed on L1; tx-order and withdrawal refunds are settlement-gated
(`tx-order.ak:93-97`, `withdrawal.ak:326-349`) and adjudicated by the trace proofs;
reserve→payout→conclude conservation is airtight per-transaction (`payout.ak:271-373`,
`withdrawal.ak:294-321`) — the only residual is that **no L1 check sums aggregate
reserve backing** (the standard optimistic assumption, matrix §14); `header_hash`
transitively binds every root (linked-list key = `blake2b_224(serialise_data(header))`),
so signature-only attestation is **not** a root-integrity hole and must not be
"hardened" with redundant per-root checks.
