# Rule-to-Proof Coverage Matrix

> Audited 2026-07-10 against branch `tx-validation` (HEAD `269bf6b3`) plus its
> contemporaneous working tree; reconstructed on clean base `55afdc54`. This is the completeness analysis for the invariant in
> `technical-spec/C-considerations/1-protocol-invariants.tex:28`:
> _"Every invalid block can be invalidated by an L1-verified fault proof before its
> maturity period elapses."_

## 0. Protocol invariants and scope

Six invariants (`C-considerations/1-protocol-invariants.tex:10-67`): block merging order,
**valid blocks always mergeable (soundness)**, **invalid blocks always removable
(completeness — the subject of this matrix)**, operator rotation liveness, operator bond
locked until maturity, censorship protection via gapless event intervals. There is **no
DA-availability invariant** in that file; DA criticality is asserted at
`technical-spec/6-offchain-data-architecture/1-da-layer.tex:8` and the withheld-data risk
admitted at `:117-118`.

Scope of this matrix: every transaction rule and state-transition invariant an operator
could violate in a committed block, plus the data-availability and state-queue-correction
machinery the proofs depend on. Mempool admission (Phase A/B) is _defense_, not
_enforcement_ — "reject codes and details are operational evidence, not L1 fault proofs"
(`technical-spec/7-phase-two-validation/3-fraud-proofs-involved.tex:9`) — so a row is only
**Complete** when the L1 path works.

correction behavior.

## 11. Cross-cutting disagreements (spec ↔ on-chain ↔ off-chain ↔ ops ↔ tests)

1. **Completeness invariant vs implementation** — spec claims a verifier per violation
   (`1-protocol-invariants.tex:33`); §§4, 5, 7, 9 show whole families missing.
2. **Catalogue: 24 spec violations ↔ 12 compiled types ↔ 5 registered categories ↔ 3–4
   tooled workflows.** Four different notions of "supported" that nothing reconciles.
   _Reconciliation key now exists_: §13 below and
   [`catalogue-status.md`](catalogue-status.md) §6 assign a stable identifier to every
   required-but-missing type.
3. **Phase A/B enforce rules the L1 cannot dispute** — min-fee formula, value
   preservation, Plutus execution, min-ada, network-id. An operator bypassing local
   validation can commit blocks violating rules honest nodes enforce locally, with no L1
   recourse today (the security boundary is the L1 side).
4. **Local reject taxonomy is disjoint from proof categories by design**
   (`FAULT_PROOF_DECISION_RECOMMENDATIONS.md` D9) — fine, but no detector maps a committed
   block's violation to a proof family either (watcher gap).
5. **Retention numbers disagree in four places** (§9) and nothing enforces DA-store
   retention in code.
6. **`maturity_duration = 30 ms`** on-chain vs 3–7 day spec window — every timing-related
   guarantee is dev-configured.
7. **Spec self-inconsistency**: WITHDRAWN-REFERENCE-INPUT defined (`:886`) but missing
   from its rule's violation list (`:837-841`).
8. **Descendant-removal comment vs code** (`state-queue.ak:633-636` vs `:661`).
9. **Naming**: public documentation uses `fault proof`, while several source paths
   still use historical `fraud-proof/` and `fraud-proofs/` names (W-O8).
10. **Preprod blocker freshness**: the canonical-root-mismatch gap report
    (`demo/midgard-node/docs/PREPROD_DOUBLE_SPEND_FAULT_PROOF_GAP_REPORT.md`, 2026-05-08,
    gitignored) predates the counted-root work (PR #458) and the MPF-based rewrite of the
    off-chain proof builders; whether it still reproduces is unverified. Treat as
    "documented blocker, resolution unconfirmed" until a preprod re-run (W-T4).
11. **Witness-set encoding split in the shipped signature proofs**: the
    invalid-signature/missing-signature step validators parse the witness preimage as a
    `Pairs<vkey,sig>` map (`invalid-signature/step-02.ak:77-79`,
    `missing-signature/step-04.ak:76-77`), while the native-tx codec commits
    `addr_tx_wits` as a CBOR list of `[vkey, sig]` arrays
    (`native-tx/components.ak:716-737`). If a block's committed witness-set hash is over
    the native encoding, these proofs cannot match any real preimage — a concrete reason
    the 🔶 rows in §5 are unverified. Several proof families still target the older
    `ledger-state.ak` model; the two on-chain ledger models must be reconciled (W-C13).
12. **On-chain proof decoders are looser than the off-chain canonical codec**: the
    on-chain value decoder accepts duplicate and unsorted policy ids/asset names and
    empty asset names (`native-tx/components.ak:396-450`); required-signer/observer
    entries are not length-checked (`native-tx/preimages.ak:94-108`); the full-body
    decode path skips the `network_id` range check and the 32-byte checks on the two
    integrity hashes that the compact path enforces (`native-tx/transaction.ak:280-292`);
    the mint preimage decodes as raw `Data` with structure enforced only on encode
    (`native-tx/preimages.ak:292-294`). Consequences cut both ways: value-sum proofs
    (W-C2) built on a decoder that tolerates duplicate asset keys can double-count
    (soundness), and preimages only the loose decoder accepts may defeat honest tooling
    (completeness). Needs a stated canonical-equivalence requirement + property tests
    (W-T2 widened to on-chain decoders).

## 11b. Cross-cutting completeness requirement: provability under adversarial sizing

A proof family only satisfies the completeness invariant if its **worst-case evidence
physically fits** Cardano's transaction-size and execution-unit limits — otherwise an
operator can make a violation unprovable by inflating the offending transaction (a
provability-DoS), even though the rule and verifier exist. Current state:

- Only double-spend has an explicit mitigation: the spend-input reference-witness UTxO
  (`demo/midgard-fault-proofs/src/spend-input-witness.ts`), emulator-tested at 180 inputs
  (`tests/spend-input-witness.test.ts:32-68`).
- No systematic worst-case-fit analysis exists for any other family, and the spec's size
  limit rules — the natural way to bound evidence — are commented out
  (`1-cardano-ledger-rules.tex:629-636`).
- **Block-level bounds are off-chain-only**: the node caps blocks by silent pruning
  (`commit-block-planner.ts:70-83,436-521` — 10k txs, 32 MiB canonical bytes, 64 MiB DA
  payload, 40k ledger ops/steps), but no L1 rule bounds a committed block's tx count,
  step count, or payload size. A malicious operator can commit blocks exceeding every
  cap, compounding the per-tx sizing problem with a per-block one (DA burden, watcher
  re-validation cost, proof-construction cost). D-S1 must be widened to block-level
  bounds, not just per-tx size.

Status: ❌ Required but undocumented as a stated obligation. This is the deeper reason
D-S1 is not optional: size limits (or per-family witness-splitting like the double-spend
pattern) are a **completeness prerequisite**, not just a DoS nicety. Every family's
acceptance criteria in [`execution-plan.md`](execution-plan.md) §10 must include a
worst-case sizing argument (W-T8).

## 12. Severity ranking of open gaps (adversarial view)

Fund-theft-capable, in rough order of exploitability:

1. **Value conservation / ADA-minted / negative outputs** (§4) — forge value directly.
2. **Fabricated deposit / fabricated withdrawal** (§7) — mint L2 funds or drain reserve.
3. **Cross-block duplicate event application + evidence-liveness race** (§7) —
   double-credit one L1 deposit, with the only proof route expiring when the first
   block's settlement burns the event NFT.
4. **Native-script-invalid + spend-side withdrawn-input + req-signer set + intra-tx
   duplicate input** (§2, §5) — spend other people's funds / double-count inputs.
5. **Witness-set encoding split** (§11 #11) — the already-shipped signature proofs may
   be unable to verify real committed preimages at all.
6. **DA withholding after attestation** (§9) — make any of the above unprovable.
7. **Adversarial-sizing provability DoS, per-tx and per-block** (§11b) — make any of the
   above unprovable by inflating the offending transaction or block.
8. **Unbounded commit `end_time`** (§6) — distort every due-ness adjudication and stall
   merge liveness with a single commit.
9. **Descendant-removal deadlock** (§10) — strand correction even when a proof succeeds.
10. **Zeroed economics + 30 ms maturity** — remove all deterrence/reward even where
    proofs work.

Everything else (tooling absence, registration gaps, test debt) is operational readiness
rather than protocol soundness, but note that unregistered = unprovable in practice.

**Second-pass additions to the ranking (from §14):** the **binding blocker (F0)** sits
at the very top with the value family — it silently disables eight already-written
proofs, so several gaps below "look implemented" but are unprovable in practice. The
**DA merge veto + missing escape hatch (F3/F4)** and **maturity vs multi-step latency
(F9)** are the top _liveness/completeness_ risks: they can freeze the queue or let a
fault escape regardless of which proofs exist. **Governor capture (F5)** and
**non-retroactive rotation (F6)** rank with DA withholding — they let a captured/rotated
committee undermine the availability layer every other proof depends on.
