## Notes
- CI: the whole chunk runs via the `midgard-watcher` package `test` script in `.github/workflows/midgard-node-ci.yml` and `midgard-watcher-ci.yml`. No file in this chunk is env-gated, skipped, or opt-in; every suite fails closed. Watcher vitest uses `maxForks: 2`, `testTimeout: 60s`, `restoreMocks: true`; the three slow suites (phase-a-verifier, synthetic-native-tip, crash-rollback-matrix) each set their own 120s per-test overrides, so the global timeout is not silently truncating them.
- Environment dependencies worth knowing: `finality-engine.test.ts` shells out to the `openssl` binary in `beforeAll` and writes into `/dev/shm`; several suites `mkdtemp` under `/var/tmp` (not `/tmp` -- `sqlite-durable-backend.test.ts` proves the production loader refuses `/tmp`). All are Linux-only and fail closed if unavailable.
- Two different TLS strategies for the same L1 transport attestation: `finality-engine.test.ts` generates certs at run time with openssl (1-day validity), while `crash-rollback-matrix.test.ts` hardcodes two RSA keypairs whose certs expire 2036-07-27. The hardcoded pair is a latent time bomb and duplicates the other file's setup; a shared `tests/support/tls-transport-fixture.ts` already exists and neither file uses it.
- Shared helper the chunk's correctness depends on: `tests/support/canonical-json.ts` deliberately re-exports the **production** canonicalizer (`watcherCanonicalJson`), so every "digest covers its fields" assertion in `finality-engine`, `crash-rollback-matrix`, `phase-a-verifier` and `authenticated-state-queue-observation` is computed with the code under test. This is the right choice for forging tampered records (the forgery must be canonical), but it means no test in this chunk independently checks the canonicalization rule itself.
- Shared fixture: `tests/support/deployment-authority-fixture.ts` performs real ed25519 keygen/sign and the loader verifies with the production path, so `deployment-authority`, `workflow-funding-profile-overlay` and `authenticated-state-queue-observation` are not signature-stubbed.
- Test-authored production models appear twice and are the chunk's main soundness gap: the W44 lifecycle driver in `crash-rollback-matrix.test.ts` and the durable canonical-progress selection reimplemented inside `finality-engine.test.ts`'s coordinator double. Both are documented in-file, but neither executes the production module it models.
- `unsafe*ForTest` exports are used pervasively (`unsafeDeriveWatcherStateQueueObservationForTest`, `unsafeOpenWatcherSqliteDurableBackendForTest`, `unsafeCreateWatcherChainCoordinatorForTest`, `unsafeRunWatcherCommandForTest`). These are declared seams rather than bypasses of the decision under test -- `sqlite-durable-backend.test.ts` explicitly contrasts the production opener (which refuses unadmitted observations) with the test opener.
- Checked and cleared: the depth constants in `native-exact-point-query.test.ts` (`"3"`, `"4991"`) are not scripted -- `tests/support/native-chain-sync-fixture.mjs` supplies only a tip (blockNo 12, or 5000 in `query_old`) and a target (blockNo 10); production derives tip - target + 1. The oracle is independent.
- Nothing in this chunk was unreadable. The only judgement I could not fully close is how much of `crash-rollback-matrix.test.ts`'s W44 model mirrors the real `src/fault-proofs/` lifecycle; I read the fault-proof module names but not their contents, so the "test-authored model" finding is about what the file executes, not a claim that the model is wrong.
