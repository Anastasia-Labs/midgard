## Notes

- Production paths actually exercised: `availability-challenge-readiness`, `script-reward-registration`, and both `deposit-flow-emulator-*` files run the real Lucid Emulator with the real applied Aiken contracts (`loadRealMidgardContractsForTest`) plus real Postgres and the real MPF engine. `state-queue-mutation-lease-http` and `database.test.ts` run real Postgres with the node's real migrations (the lease helper `tests/helpers/state-queue-mutation-lease-server.ts` creates a per-test database, refuses non-loopback hosts, and serves the node's real `buildStateQueueMutationLeaseRouter`). `submit-l2-transfer`, `commit-source-completeness`, `startup-protocol-status-retry`, `e2e-env` and `da-config-load` are in-process/pure with only the transport, clock or provider injected - in each case the decision claimed (fee convergence, exactness predicate, retry classification, dotenv parsing, config validation) is the real production function.
- `mempool-ledger-cache.test.ts` injects the durable-snapshot loader as a plain Effect returning row arrays, so nothing in that file establishes the Postgres `retrieveSpendable` semantics its L690 case is named after; the cache/epoch/lock decisions it targets are real. `database.test.ts` covers the real `retrieveSpendable`, so the gap is only in naming, not coverage.
- Oracle provenance in the emulator journeys is a re-derivation, not a fully independent source: `expectedAuthenticatedEventRoot` (deposit-flow-emulator-shared.ts L2570) recomputes the root through the production `buildAuthenticatedRootFromEncodedEntries` from independently collected event entries. This proves the committed header contains exactly the expected event set; it cannot prove the MPF root construction itself is correct.
- Shared helper the chunk's largest files depend on: `tests/deposit-flow-emulator-shared.ts` (2,809 lines) supplies `makeFixture`, `initializeProtocol`, `runCommitWorkerUntilSubmitted`, `commitConfirmRecoverAndMerge`, `runSpeculativeWorkerWithInstruction` and the root helpers for both `deposit-flow-emulator-*` files; it was not itself in this chunk and its own correctness is unaudited here.
- CI wiring correction: `ci-summary.txt` line 4 lists `tests/native-tx-workload-utils.test.mjs` among files whose bodies vitest may not collect because they are `node:test` files. It is not - it imports `test` from `"vitest"` (L3) and uses `node:assert/strict` only as the assertion library, so vitest does collect and run it under the midgard-node package `test` script. The other files listed there still need checking; this one does not.
- Nothing in this chunk is env-gated, skipped, or opt-in; every file runs under the midgard-node package `test` script, which CI runs.
- Two timing sensitivities worth naming, both currently bounded rather than sleep-as-evidence: `mempool-ledger-cache.test.ts` L258 asserts the Phase B lock-wait timer's max >= 10ms after a 20ms held section, and `deposit-flow-emulator-merge-payout.test.ts` L440-473 polls `TxAdmissionsDB.claimBatchLease` for up to 30s with `performance.now()` (Date is faked) and dumps the durable rows on failure.
- Readability/audit concern rather than a correctness one: `database.test.ts` holds roughly 140 tests across 18 `describe` blocks in a single 8,257-line file. Its per-test quality is high (deterministic label-derived fixtures via `databaseFixtureBytes`, real SIGKILL child processes for the crash boundary, `TestClock`/`it.live` split for timing), but a reviewer cannot answer the review gate for the file as a unit; splitting per DB module would not change what it protects.
- Could not determine: whether the seven DDL-introspection tests in `database.test.ts` (L647-770) were ever demonstrated to fail against a contract-violating migration, or whether they were written after the fact from the migration's own output. The "drops the superseded admission-payload hash lookup index" case (L705) reads as the latter - it can only ever restate that one specific migration ran.
