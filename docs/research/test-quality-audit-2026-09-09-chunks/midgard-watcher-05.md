## Notes
- Whole chunk runs in CI: the midgard-watcher package `test` script is invoked by both `.github/workflows/midgard-node-ci.yml` and `midgard-watcher-ci.yml`. No file in this chunk contains `it.skip`, `describe.skip`, `todo`, or an env gate. The one `process.env` reference (user-event-runtime.test.ts L170, `MIDGARD_REAL_BLUEPRINT_PATH`) is an override with a real fallback to `onchain/aiken/plutus.json`; if the blueprint is absent the `readFile` throws and the test fails rather than skipping — fail-closed.
- Shared oracle caveat affecting the chunk: `tests/support/canonical-json.ts` is a thin re-export of the *production* canonicalizer (`watcherCanonicalJson` / `watcherSha256CanonicalJson` from `src/storage/durable-store.ts`) — its own header says so deliberately. So multi-provider-consistency.test.ts L405 (`consistencyDigest === sha256CanonicalForTest(canonical)`) and every `canonicalDigest(...)` use in state-queue-indexer.test.ts are self-consistency checks: they constrain *which fields* enter a digest (a real property — no hidden inputs, no omitted evidence) but cannot detect a wrong canonicalization rule. Nothing in this chunk pins the canonical-JSON encoding against an independent spelling or an external vector.
- Two shared fixtures carry most of this chunk's fidelity and their own correctness is load-bearing: `tests/support/user-event-origin-fixture.ts` (~1300 lines; generates the synthetic native chain-sync helper script, including the `nativeStreamInitialAcknowledgement` branch at L817 and the `controlled` tip mode) and `tests/support/tls-transport-fixture.ts` / the inline openssl fixture in multi-provider-consistency.test.ts. The "native" suites therefore exercise the real supervisor, ordering guard, spawn/exit lifecycle and receipt revocation against a **simulated** helper — no real cardano-node node-to-client wire compatibility is established anywhere in this chunk.
- Test-only production API surface is pervasive here: `unsafeSpawnForTest`, `unsafeReadIdentityFileForTest` (src/l1/native-chain-sync.ts L371-516, L1121-1163), `unsafeCreateWatcherFaultProofSupervisorForTest` / `unsafeRunOrResumeForTest` / `unsafeScheduleForTest` / `unsafeNowMsForTest` / `unsafeIsActuationRevokedErrorForTest`, and `unsafeOpenWatcherSqliteProverFundingReservationStoreForTest`. In every case observed these inject transport, filesystem, clock or scheduling rather than the decision under test, so §6 is satisfied — but the surface is large and only fault-proof-supervisor.test.ts L57-76 guards that production does not expose it.
- Shared-state leak: state-queue-indexer.test.ts L4777 calls `closeWatcherL1TransportAttestationContext(providerATransport)` on a context held in the module-level `transportContexts` array, as the last action of the file's last test. Any test added after it in the same file would see a closed transport. This should move into an isolated context created inside that test.
- Duplicated coverage worth consolidating: multi-provider-consistency evaluation is exercised both directly (multi-provider-consistency.test.ts) and again as a sub-step inside state-queue-indexer.test.ts's bootstrap bundles; and the checkpoint/CAS durable machinery is set up twice with near-identical hand-rolled backends and sidecar clients (durable-runtime.test.ts L114-167 `MemoryBackend`/`client`, user-event-runtime.test.ts L39-121 `durableFixture`). One shared, conformance-checked in-memory backend would remove the risk of the two fakes drifting apart.
- Could not determine: whether `MemoryBackend`'s compare-and-swap semantics actually match the production SQLite atomic backend (no conformance test exists in this chunk, and the real backend module was not in my file list); and whether the `Data.to(...)`/`Data.from(...)` Aiken schemas used throughout state-queue-indexer.test.ts are themselves pinned against the compiled blueprint anywhere — that pinning, if it exists, lives outside this chunk.
