## Notes
- **Two clean templates in this chunk.** `execution-source-script-decoding-lifecycle.test.ts` and `resolved-output-non-canonical-lifecycle.test.ts` are the model: they enumerate their authentication seams as a named list, refuse each ON CHAIN (`expectOnchainRefusal`), record coverage while the journeys run, close with `assertCompleteLifecycleCoverage`, and build the Van Rossem fit ledger from LIVE measurements taken during the same run, asserting positive margins on every row. Nothing is transcribed. Every other lifecycle file in this chunk is a partial version of this and should converge on it.
- **The fit-ledger family splits cleanly along one line.** Four files (`*-fit-ledger.test.ts`) read a transcribed JSON measurement table and re-assert budgets over the saved numbers; three of them at least derive `blueprintSha256` from the real blueprint (so a stale ledger fails), while `network-id-wrongful-rejection-fit-ledger.test.ts` does not touch the blueprint at all and only re-computes the file's own digest - it is the one worth deleting. All four assert budget ceilings against a *saved measurement*, which section 13 explicitly says is historical evidence rather than a new execution. The lifecycle files that measure live and gate margins in the same run make them redundant; the right end state is a `--check` regenerator in CI plus the live gates.
- **Fit-ledger gating is inconsistent across the lifecycle files.** Live-measured AND gated: execution-source (L845-854), resolved-output (L866-875), script-integrity-lifecycle (L960-966, contradiction cases only). Live-measured and NOT gated: `cross-block-installed-lifecycle` (write-only under `MIDGARD_WRITE_FIT_LEDGER=1`), `min-ada-wrongful-rejection-lifecycle` (write-only under `MIN_ADA_FIT_LEDGER_PATH`). `transition-trace-subvariants` gates implicitly (buildVanRossemFitLedger throws on a non-positive margin) and additionally pins a roster. The two ungated files do all the measurement work and produce no acceptance criterion in CI.
- **Shared harness.** Every emulator file goes through `tests/support/emulator/harness.ts` -> `buildMinimalFaultProofContracts`, which starts from `makeAlwaysSucceedsContracts(alwaysBlueprint)` (contracts.ts L1279) and swaps in the REAL applied validators for the family under test plus hub-oracle/state-queue/settlement where a `real*` option asks. So these journeys prove the fault-proof validators against the real compiled blueprint, but the surrounding L1 infrastructure they interact with is always-succeeds scaffolding in the default configuration - a fault-proof step interacting incorrectly with a real state-queue or settlement validator is out of scope for most rows.
- **`tests/support/emulator/blueprints.ts` is the load-bearing helper the whole chunk depends on.** Its `#610` arity guards (L103-147) are what prevent an under-applied validator deploying as a silent always-succeeds script - i.e. what prevents every emulator journey in this chunk from being a test that cannot fail. It is also the single point where `MIDGARD_REAL_BLUEPRINT_PATH` / `onchain/aiken/plutus.json` is resolved; the blueprint is a build artifact, so if it is absent or stale every file here fails at load rather than silently passing.
- **A three-file template family with a shared tautology.** `observer-order-invalid-authenticated`, `observers-forbidden-on-untagged-network-authenticated` and `mint-declared-asset-limit-authenticated` are the same file with names swapped. Two of the three open with a runtime assertion over a locally-declared array literal (`expect(keys).not.toContain("submit")`); only the `satisfies` clause carries any real content, and the third does it correctly with `expectTypeOf`. All three are named "authenticated" but none touches a script, an emulator or a signature.
- **Bare `.rejects.toThrow()` is the chunk's most common weakness.** min-ada-lifecycle (nine cases), cross-block (four), script-integrity-lifecycle (six), transition-trace-subvariants (one), fabricated-withdrawal (a broad `/failed script execution.*Spend/`). The files with the strongest negatives (`reference-input-no-idx`, `resolved-output`, `execution-source`) all route through `expectOnchainRefusal` and/or match a specific message; the pattern to spread is already in the chunk.
- **Test-order dependence.** `execution-source-script-decoding-lifecycle` and `resolved-output-non-canonical-lifecycle` accumulate module-level `coverage`/`measurements` across the `it` blocks and assert them in a final `it`; `script-integrity`, `cross-block`, `min-ada` and `transition-trace-subvariants` do the same in `afterAll`. Running any of these with a `-t` filter changes what the final gate sees. This is a deliberate design (coverage recorded, never pre-filled) but it means these files must run whole.
- **CI.** All of these run under the `midgard-fault-proofs` package `test` script in `.github/workflows/midgard-node-ci.yml` (fault-proofs vitest: isolated forks, maxForks 8). No file here is `not-in-ci`.
