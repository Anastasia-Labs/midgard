## Notes

- **CI:** the whole chunk lives in `demo/midgard-fault-proofs`, whose package `test` script runs in `.github/workflows/midgard-node-ci.yml` (isolated forks, maxForks 8). No file in this chunk is unwired. Nothing is `describe.skip`/`it.skip`, and there are no unexplained skips.
- **Two distinct quality tiers in this chunk.** The lifecycle/emulator suites (`observer-order-invalid-lifecycle`, `mint-declared-asset-limit-lifecycle`, `spend-input-signer-missing-lifecycle`, `submit-init-emulator-l2-tx-mistag`, `submit-init-emulator-withdrawal-mistag-cancel-resume`, the four `...script-sources-*` files) drive real compiled Aiken validators from `realBlueprintPath` through a real Lucid Evolution emulator at Van Rossem limits. The family/V1 unit files (`zero-input`, `unused-redeemer`, `distinct-asset-accumulation-limit`, `transaction-output-non-canonical`, `input-set-uniqueness`, `field-opening`) are pure functions over real codec/commitment primitives. Both tiers pair accept and reject and bind the exact typed rejection reason. The only weak family here is the three `*fit-ledger` files.
- **The `assertCompleteLifecycleCoverage` gate (`src/testing/complete-lifecycle.ts`) is the load-bearing shared helper** for the three big lifecycle suites: it fails closed listing every missing reason arm, success direction, base scenario, authentication seam, cancellable step, resume and adjacent-bound refusal. It is itself correct and it is what makes those suites' claims auditable. `expectOnchainRefusal` (`tests/support/emulator/expect-onchain-refusal.ts`) is the other: it requires `/failed script execution/` in the message, so a builder-side throw cannot pass as a validator refusal. Both should be treated as production-grade test infrastructure.
- **Fit-ledger family, ranked.** Correct template (digest derived at test time from the real blueprint, measurements taken live): `observer-order-invalid-lifecycle` L1624-1645, `spend-input-signer-missing-lifecycle` L1568-1594, and `mint-authorization-workflow-fit-ledger` L24-26. Broken: `redeemer-canonicity-fit-ledger` transcribes 14 measurement rows and a blueprint digest into the test, writes the JSON from that table, then asserts the JSON equals the table — it can never fail and never touches a blueprint. `witness-script-decoding-fit-ledger` pins a hand-transcribed digest against the JSON's own hand-transcribed field plus a 72-entry name list.
- **A production invariant already subsumes several fit-ledger assertions.** `entryFromMeasurement` (`src/proof-fit/van-rossem-fit-ledger.ts` L80-89) throws when any signed-byte/memory/CPU margin is non-positive or a publication exceeds the 15,872-byte reserve. Every `margin > 0` expectation in `redeemer-canonicity-fit-ledger` L155-170 and `witness-script-decoding-fit-ledger` L124-146 is therefore unreachable-as-a-failure once the ledger was built. Only the live-measured suites' margin checks carry information, because there the measurement is fresh.
- **Env-gated acceptance criteria in the `...script-sources-*` family.** In `-descriptor`, `-descriptor-max`, `-boundaries` and `-edge`, the entire `afterAll` returns early unless `MIDGARD_WRITE_FIT_LEDGER=1` (L58-59). That means the scenario-count check (`expect(completed).toBe(18/9/25/9)`) and the ExUnit acceptance bounds (`memoryUnits <= 13_200_000n`, `cpuUnits <= 8_000_000_000n`) never execute in CI, and the per-transaction measurements are collected and discarded. The `it.each` bodies themselves do run and are the real value. Recommend moving the count and ExUnit bounds outside the env guard so only the file write stays gated.
- **Assertion weakness shared across the emulator suites:** success is asserted as `txHash` having length 64 and `removal.transactions.length > 0`; refusal in the `...script-sources-*` files is `rejects.toThrow(/semantic-resolution/)`, which `runEmulatorLifecycleStage` (`tests/support/emulator/emulator-context.ts` L136-160) produces for *any* failure at that stage. So those negatives pin the stage, not the validator's reason. The three big lifecycle suites are better: they route every negative through `expectOnchainRefusal`.
- **Small filler observed twice** (`zero-input-wrongful-rejection` L164, `input-set-uniqueness-wrongful-rejection` L171): `expect(Object.keys({ block: null })).toEqual(["block"])` asserts a JavaScript language fact about an object literal written in the test. The `expectTypeOf<keyof …ForcedInput>().toEqualTypeOf<"block">()` on the preceding line is the real (static) check; the runtime line should be deleted. It did not move either file's grade.
- **Could not determine:** whether the committed `docs/fault-proofs/size-plans/*.json` ledgers are currently in sync with the checked-in blueprint — `realBlueprintPath` points at a build artifact that is gitignored in this workspace (so `mint-authorization-workflow-fit-ledger` L24-26 and the two live-measured suites may be red locally for a reason unrelated to their design). I did not run any suite, per the read-only instruction.
