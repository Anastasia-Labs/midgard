## Notes
- Two template families in this chunk. (a) The three `demo/lucid-midgard/tests/native-*-fixture.test.ts` files share one shape: rebuild the fixture from a declared TS construction, then assert the checked-in JSON equals `stableNativeTxFixtureJson(rebuilt)`, with `MIDGARD_SYNC_FIXTURES=1` switching to write mode. The comparison is against the producer's own prior output (self-pin), but the fixtures are consumed downstream by `scripts/generate-native-compact-aiken-goldens.mjs` to seed Aiken goldens, so the pin does guard a cross-language vector. Only the ordinary file adds genuinely spec-derived byte assertions (0x80 sentinel; 38-byte fixed-index inputs); the other two assert against constants exported by the module under test. (b) The `midgard-node-tools` acceptance verifiers (phase4 summary, state-correction reconciliation/local-authority, stress-corpus) all follow a good pattern: build a valid fixture, mutate one field, assert a named refusal. The phase4 summary verifier's mutation loop only asserts `passed === false` plus a nonempty reasons list, never which reason, so a mutation failing for an unrelated reason would pass unnoticed.
- Shared helper the chunk depends on: `onchain/plutarch/tests/Testing/Eval.hs`. Its `psucceeds` is the sole oracle for every membership-validator case, and it cannot distinguish a correct validator from one that accepts everything. Strengthening `MembershipValidator.hs` requires a `pfails`-style helper that does not yet exist in that module.
- `onchain/plutarch/tests/Testing/ScriptContextBuilder.hs` is a semantic ledger fake with no conformance check; every Plutarch validator test's fidelity rests on it.
- CI gaps: both Haskell suites (`offchain/tests` mockchain-tests, `onchain/plutarch/tests` helpers-tests) have no workflow, confirmed against ci-summary line 4 — the presence of these files is not evidence anything runs them. `TransactionProofs.hs` is worse: it is not even reachable from `Test.hs`, so it would not run even if the suite were wired up. `phase1-admission-acceptance.operator.test.ts` is collected by midgard-node-tools vitest but always skips without `PHASE1_ADMISSION_OPERATOR=1`.
- Duplicated coverage: `offchain/tests/Spec/Scheduler.hs` cases "rewind back to the start" (L82) and "rewind with a not yet active operator" (L115) repeat the same five-step script and end on the same assertion; the second differs only by registering `w3` late. They could be one data-driven pair.
- Not determinable from reading alone: (1) whether the Haskell suites currently compile and pass — several modules carry `-Wno-unused-imports`/`-Wno-unused-top-binds` and have doc comments spliced into the middle of expressions (e.g. `Test.hs` L67, `MerklePatriciaForestry.hs` L99, L294), which suggests an automated comment pass ran over them; I did not run GHC (read-only mandate). (2) In `Testing/Crypto.hs` L34-41, whether `Hash.blake2b_224`/`ripemd_160` and the Plutarch builtins bottom out in the same C implementation — if they do, those two cases are near-tautological rather than cross-implementation vectors. (3) In `demo/lucid-midgard/tests/finalization.test.ts` L473-505, whether `midgardFieldCommitment` is the same function the encoder used to build `tx.compact` (which would make those comparisons circular); the independent `computeHash32` cross-check at L503 covers the section 4 rule regardless.
