## Notes

- **CI**: every file here runs. `lucid-midgard` and `midgard-node-tools` package `test` scripts are invoked by `.github/workflows/midgard-node-ci.yml`; `demo/scripts/verify-canonical-v1-header-v1-abi.test.mjs` runs separately under `node --test`. The one effective gap is `phase1-exact-crash.operator.test.ts`, which is `it.skipIf`-gated on an operator token plus a built `midgard-node` dist, a run-scoped Postgres and a pre-encoded tx in env — it reports as skipped in every ordinary run.
- **Two files depend on a build artifact rather than source**: `api-export-snapshot.test.ts` reads `demo/lucid-midgard/dist/index.d.ts`, and `verify-canonical-v1-header-v1-abi.test.mjs` imports `demo/midgard-sdk/dist/index.js` and `onchain/aiken/plutus.json`. The ABI file fails closed with an explicit "run `aiken build` / `pnpm build`" message (an intentional, documented choice); the export-snapshot file simply throws on a missing file. `native-compact-goldens.test.ts` likewise asserts `demo/midgard-core/dist/index.js` exists before running the generator and mirrors `node_modules` by symlink so the tampered-fixture case cannot degenerate into a module-resolution failure — that comment (L61-L65) is the best example of oracle hygiene in the chunk.
- **Shared helper the chunk depends on**: `@al-ft/midgard-test-support/temp-files` (`createTrackedTempDirFactory`, `writeScript`, `waitForFile`) underpins the process-level suites (`e2e-runner`, `e2e-service-supervisor`, `process-ownership`, `pipelined-commit-process-harness`). Its own correctness was not audited here — if `writeScript` silently failed to set an executable/valid script, several "process behaves this way" cases would degrade into "child exited nonzero".
- **Dominant good pattern**: nearly every midgard-node-tools file pairs a real (or realistically produced) artifact with a strict V1 parser and a battery of mutations — missing field / unknown field / wrong schemaVersion / cross-kind artifact / internally inconsistent evidence — plus a no-side-effect check (`expect(submitCalls).toBe(0)`, `expect(await readFile(path)).toEqual(bytesBefore)`). That is exactly §5's causal-negative requirement and it is applied consistently. `stress-wallets.test.ts` is the strongest file in the chunk and a good template.
- **Recurring weakness 1 — source-text oracles**: four files use `readFileSync` + regex over production source or docs as proof of behavior (`safe-program.test.ts` L205, `documentation-examples.test.ts` L42, `api-export-snapshot.test.ts` L162, and, over stub-produced logs, `pipelined-commit-process-harness.test.ts`). All four belong in lint or a generator `--check`, not in vitest, per §7.
- **Recurring weakness 2 — bare `toThrow()` in mutation loops**: `e2e-release-finality-policy` L28, `phase4-t1-recovery` L235/L339/L353, `phase4-process-isolation` L274/L303, `stress-wallets` L1919/L2094. Elsewhere in the same files the specific message is asserted, so this is inconsistency rather than policy; a mutation that broke the object in an unrelated way would still pass.
- **Recurring weakness 3 — fixtures built from the production constant they then assert against**: `e2e-state-correction-acceptance` L162-L167 (worst case: two assertions that can never fail), `e2e-summary` L532/L541, `e2e-release-finality-policy` L11. These are not the `*fit-ledger` self-comparing-digest family — no blueprint digests are transcribed anywhere in this chunk — but they are the same §2 defect in miniature.
- **The one churn pin in the chunk** is `api-export-snapshot.test.ts` (150 hand-maintained export names). No compiled-size, script-hash or measurement-table pins appear in these files.
- **Honest scoping to flag for the reviewer**: `e2e-stress-l2-throughput.test.ts` and `pipelined-commit-process-harness.test.ts` both carry "stress"/"pipelined commit" names but exercise the *tooling harness* with the node mocked or stubbed. The stress file is explicit about it (injected `submitTransfer`/`fetch`/clock) and its assertions are scoped to the harness, so it is sound; the pipelined-commit file's case titles ("elects exactly one journal winner", "accepts the database single-active-journal guard") read as claims about midgard-node that the file does not test.
- **Could not determine**: whether the `phase1-exact-crash` operator drill is ever actually executed anywhere (no workflow references its token; `ci-summary.txt` lists no such job), and whether `@al-ft/midgard-test-support/temp-files` has its own tests.
