## Notes

- Every file in this chunk runs under `demo/midgard-watcher`'s single `test: vitest run` script, which CI executes (midgard-node-ci.yml and midgard-watcher-ci.yml). None are env-gated, skipped, or opt-in. `vitest.config.ts` includes `./tests/**/*.test.ts` with `pool: forks`, `maxForks: 2`, `restoreMocks: true`, `testTimeout: 60_000`; per-test timeouts override it.
- Runtime risk, not correctness: `watcher-installed-journey.test.ts` carries a 3,600,000 ms test timeout with a 3,000,000 ms interior stage deadline, and shares a two-fork pool with `settlement-indexer.test.ts` (6,101 lines, real TLS listeners) and `replay-transcript-capture.test.ts` (180 s per parameterized case). Required CI verification for this package is therefore gated on a job that can legitimately run for an hour.
- Production paths actually exercised: `watcher-installed-journey` runs the full `createWatcherRuntime` against a real Lucid emulator (real Plutus evaluation and submission) with only the Kupmios transport methods and `makeLucidForSubmit` spied onto that emulator. `state-queue-catchup-finality`, `replay-transcript-capture` and the second half of `user-event-origin` run the real Go `midgard-chain-sync` subprocess through `tests/support/user-event-origin-fixture.ts` / `state-queue-observation-fixture.ts` with real CML/SDK CBOR. `settlement-indexer` establishes real TLS listeners (`tests/support/tls-transport-fixture.ts`) and drives the real l1-adapter, multi-provider-consistency, finality, rollback, post-finality-recovery and settlement-indexer evaluators. `durable-store`, `config` and `rule-bundle` are pure-function boundaries. `chain-coordinator` and `fault-decision-bridge` are the only two files whose collaborators are entirely doubled.
- Shared helpers the chunk's verdicts depend on: `tests/support/state-queue-observation-fixture.ts` (builds Init/Commit transactions with real CML + SDK schemas, opens real native exact-point queries, and asserts the SQ source's own admission before returning — it does not stub the observation decision), `tests/support/user-event-origin-fixture.ts`, `tests/support/deployment-authority-fixture.ts`, and `tests/canonical-fraud-proof-catalogue.ts`.
- Two production modules export explicit `unsafe…ForTest` DI seams used here: `unsafeCreateWatcherFaultDecisionBridgeForTest` and `unsafeCreateWatcherChainCoordinatorForTest`. Both forward to the same private `createBridge`/coordinator factory with no test-only branch inside the decision logic, so §6 is satisfied; note only that the bridge seam skips the production `assertWatcherFaultProofApplication` call. `unsafeInspectWatcherUserEventActivationTransactionForTest` is likewise descriptive-only and the test proves at L684-L692 that its output cannot be laundered into `readWatcherUserEventOrigin`.
- Ordering dependency in `settlement-indexer.test.ts`: module-level mutable state (`serial`, `transportContexts`, `tlsIdentityByProviderId`) is shared across all cases, and the final case (L6095) permanently closes `provider-a`'s transport attestation. Any case added after it, or any future reordering, would fail for an unrelated reason. This is currently safe only because the destructive case is last.
- `durable-store.test.ts` exercises atomicity, crash-before-commit and crash-after-commit against `MemoryAtomicBackend`, a fake. The real `src/storage/sqlite-durable-backend.ts` has no test in this chunk; whether it is covered elsewhere in the package I did not verify.
- Repeated §5 weakness across the chunk: identity/fence refusals (`{ ...capture }`, `{ ...origin }`, `{ ...scriptBinding }`, `{ ...pair.finality }`) are asserted with bare `.toThrow()` / `.rejects.toThrow()`. The refusal is real and the fixture is controlled, but the tests cannot distinguish which fence fired.
- I did not attempt to determine whether the chunk's negative cases have recorded failure evidence (§3) — no such record is present in or alongside these files.
