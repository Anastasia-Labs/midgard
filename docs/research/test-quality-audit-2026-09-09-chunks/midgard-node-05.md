## Notes

- **CI reach.** All 35 files are inside `demo/midgard-node`'s vitest include or its explicitly CI-invoked scripts (`throughput-load-watchdog.test.mjs` is named in `midgard-node-ci.yml`). None are unreferenced. But two of the best files in the chunk -- `mpf-native-owner-service.test.ts` (610 lines, grade A) and `mpf-differential.test.ts` -- are `describe.skipIf(!binaryPresent)` on the `architecture-g-owner` native binary via `tests/helpers/native-owner-binary.ts`. If CI does not build that binary they contribute a silent green with zero coverage, which is exactly the rule-14 failure mode. The skip has a documented cause (#642) and a warn, so it is not `skip-no-cause`, but it should fail closed in CI rather than skip.
- **Postgres-backed files.** `admission-writer.test.ts` and `tx-admissions-claim-load.test.ts` run against the real per-worker Postgres shard through `tests/utils.js#provideDatabaseLayers` and both TRUNCATE at the start of each scenario; they are the two highest-value files here and the chunk's correctness claims about durability rest on that helper. `tx-admissions-claim-load.test.ts` additionally creates and drops a plpgsql trigger to pin an MVCC window -- worth knowing when diagnosing cross-test interference.
- **Real-emulator family.** `initialization-emulator`, `availability-challenge-sdk-lifecycle`, `deposit-flow-emulator-recovery-invalidation`, `emulator-submit-slot-snapshot`, `scheduler-refresh` and `mainnet-protocol-parameters` all drive the Lucid `Emulator` with real compiled contracts and `localUPLCEval: true`. They share `tests/helpers/mainnet-protocol-parameters.ts` and `tests/helpers/real-midgard-contracts.ts`; `mainnet-protocol-parameters.test.ts` is the one file that proves the shared parameter table is actually consulted (perturb cost-model entry 29, CPU moves by exactly that amount), so it underwrites the whole family and should not be deleted as "just a pin".
- **Hand-maintained-count cluster.** The chunk's only real churn debt is a handful of transcribed counts, all in otherwise strong files: `deployment-manifest.test.ts` L274-277 (524/517/518/54), `initialization-emulator.test.ts` L268/L279 (13 stake registrations, 9 outputs), `reference-scripts.test.ts` L159-188 (24-name ordered list), `availability-challenge-sdk-lifecycle.test.ts` L284/L291/L300, `throughput-load-watchdog.test.mjs` L212 (9 lines). In every case a set-equality or derivation against a single source of truth already exists in the same file or a sibling, so the counts can be deleted rather than replaced. `reference-scripts.test.ts` L141-152 states this principle explicitly and is the model the others should follow; `mpf-commit-candidate-probe-artifacts.test.ts` L263-269 is the other good example (derives the invalidation key rather than pinning it).
- **Circular-oracle cluster.** Three files use production code to produce the expected value: `da-payload.test.ts` (payload sha256 via `SDK.daPayloadHashHex`, roots via the same root builders, sortedness against a sorted copy of the output), `fraud-proof-catalogue.test.ts` L56 (two builds of the same MPF), and three cases in `midgard-native-tx-codec.test.ts`. These are the chunk's lowest-value assertions and the ones to fix first.
- **Legitimate external pins observed** (do not treat as churn): `mainnet-protocol-parameters.test.ts` (PV11 epoch-654 ledger parameters + cost-model digest, made self-checking by the perturbation test), `scheduler-refresh.test.ts` L157-166 wire bytes and L322 deployed script hash, `fraud-proof-catalogue.test.ts` L44-47 catalogue category ids, `cbor-root-normalization.test.ts` hex vectors, `deployment-run-state.test.ts` L401 sha256 of a literal file.
- **Bare `.toThrow()`.** `mpf-commit-candidate-probe-artifacts.test.ts` runs ~49 mutation cases with no expected message, so error-cause attribution is unverified across the largest negative table in the chunk. Every other negative case in the chunk names a message or error type.
- **Could not determine.** Whether `midgard-node-ci.yml` builds the `architecture-g-owner` binary before running vitest (I did not open the workflow; the ci-summary does not say). That single fact decides whether the two skipIf files are grade-A protection or dead weight in CI.
