## Notes

- **Source-text oracles are the dominant systemic defect in this chunk.** Five files use `readFile` on production `.ts`/`.mjs` sources and assert substrings or `indexOf` ordering as proof of runtime behaviour: `l1-control-plane.test.ts` L1422-1556 (~50 assertions over 12 files plus `.env.example`), `benchmark-regression.test.mjs` L767-836 (~40 assertions over one script), `commit-submission-publication-order.test.ts` L88-117, `commit-worker-failure-lease-classification.test.ts` L30-61. Every one of them guards a real hazard (permit acquired inside a barrier; publication nested inside the permit; submit before journaling; the deadline scheduler regressing to `await sleep`), so deleting them loses coverage — each needs the runtime or type-level replacement noted in its row. They are also the chunk's whole `brittle: yes` population apart from the two mock-boundary files.
- **The two `*-forced-*-deployment.test.ts` files are one template** (missing-signature and network-id), differing only in the chain and titles. Both hinge on `onchain/aiken/plutus.json`, which is gitignored, so in a clean CI checkout their substantive assertions silently skip and only a hand-transcribed manifest-role constant table is compared. `contract-deployment-info.test.ts` covers the same manifest round trip against `AlwaysSucceedsContract`, where — per the network-id file's own comment (L15-19) — every fault-proof step shares one script, so its 16 per-step hash assertions cannot discriminate step-to-role wiring. The real blueprint is the only fixture that can, and no file in this chunk exercises it in CI.
- **Shared helpers this chunk's verdicts depend on:** `tests/deposit-flow-emulator-shared.ts` (2100+ lines; owns the entire confirmation-journal race scenario and its assertions, L2003-2144, and requires a test-only `afterPendingSnapshotGuard` hook in production `buildBlockConfirmationAction`); `tests/helpers/real-midgard-contracts.ts` and `tests/helpers/mainnet-protocol-parameters.ts`; and a cross-package import — `forced-transactions.test.ts` L39-48 pulls fixtures from `../../midgard-validation/tests/validation-fixtures.js`, so a change in another package's test tree can break a midgard-node gate.
- **Hand-written fakes of external systems** carry semantic behaviour with no conformance check: the Kupo HTTP + Ogmios WebSocket fakes in `state-queue-correction-observer.test.ts` (L733-873, L955-1160) and the SQL-text-dispatching `SqlClient` fake in `pipeline-status-route.test.ts` (L43-78). The latter is the worse case, because the package already provisions per-worker Postgres shards that `migration-locking.test.ts` uses properly.
- **CI correction:** `ci-summary.txt` lists `benchmark-regression.test.mjs` among files that may be `node:test` bodies vitest cannot collect. It is not — it imports `describe/expect/it` from `"vitest"` (L16) and matches the midgard-node vitest include `./tests/**/*.test.{js,mjs,...}` (vitest.config.ts L62-65; only `phase4-pipelined-process-summary-verifier.test.mjs` is excluded). It does run in CI via the package `test` script.
- **Real production paths exercised:** real Postgres (`migration-locking`, and via the shared fixture `deposit-flow-emulator-confirmation-journal`); real Lucid `Emulator` with real script application, signing and submission (`availability-challenge-publication-admission`, `lucid-time`, and the deposit-flow fixture); real Effect runtime concurrency with real semaphores (`l1-control-plane`, `admission-writer-collector`, `commit-submission-publication-order`); real CBOR codec and validation machine (`forced-transactions`); real crypto with an independent differential oracle (`mpf-event-flat-digest` vs `@noble/hashes`). Everything else is pure functions or mocked transports.
- **Opt-in / not-really-running:** only the two forced-deployment files gate on an absent artifact. No file in this chunk is env-var opt-in in the `MIDGARD_RUN_*` sense.
- **Third-party surface:** `kupmios-ogmios-v7-protocol-parameters.test.ts` tests behaviour that exists only inside `@lucid-evolution/lucid@0.6.4` — I confirmed the asserted error string is absent from the repo and from all four entries in `demo/patches/`. It is a dependency-conformance guard, not a test of repo code; worth keeping but it should be labelled as such.
- **Could not determine:** whether the `AlwaysSucceedsContract` stand-in truly collapses all fault-proof step scripts to one hash — I took that from the repo's own comment in `network-id-forced-step-deployment.test.ts` L15-19 rather than reading the service, so the severity of the `contract-deployment-info.test.ts` finding rests on that comment being accurate.
