## Notes
- CI wiring for this chunk: `demo/midgard-node/tests/**` runs under the midgard-node vitest project in `.github/workflows/midgard-node-ci.yml` (isolated forks, per-worker Postgres shards). `scripts/mpf-architecture-g-gate-config.test.mjs` and `scripts/phase3-architecture-g-soak.test.mjs` are invoked explicitly with `node --test` in CI. `tests/throughput-benchmark-utils.test.mjs` is listed in ci-summary as a possible node:test orphan, but it imports `describe/it/expect` from `vitest`, so it is collected and executed by the vitest include for `./tests/**/*.test.{js,mjs,...}` — it is not an orphan.
- Two files never run in any CI job: `tests/ed25519-wycheproof.operator.test.ts` (gated on `WYCHEPROOF_ED25519_OPERATOR=1`, and additionally fetches its vectors from GitHub at test time) and `tests/operator-lifecycle-preprod.test.ts` (gated on `MIDGARD_RUN_PREPROD_OPERATOR_LIFECYCLE_TESTS=1`, requires a funded Preprod wallet). The Wycheproof file is the strongest Ed25519 oracle in the chunk and is worth vendoring so it can run offline and fail closed; the preprod lifecycle file would need real assertions before wiring it anywhere.
- Real production paths exercised: real Postgres (`tx-admissions-monotone-timestamps`); real Lucid emulator + real Aiken-compiled validators + local UPLC evaluation (`reserve-payout-builders`, `published-workflow-deployment`, `availability-challenge-responder-lifecycle`); real SQLite journal (`availability-challenge-responder-lifecycle`); real CML/Node Ed25519 (`ed25519-verifier`, `withdrawal-cli-utils`, `phase-a-cardano-signature-bridge`); real child processes (`phase3-architecture-g-soak`). The rest are pure functions with injected clocks/fetch, which is appropriate for their claims.
- Only one file in the chunk is a pure source-text oracle: `speculative-commit-safety-guard.test.ts` (215 lines, zero production execution). `provider-diagnostics.test.ts` L178-207 contains one such check embedded in an otherwise sound file; `sdk-abi-fixtures.test.ts` parses Aiken source constants by regex, which is defensible because the Aiken source is the other implementation of that contract.
- Golden/pin families: `transaction-root.test.ts` (fixture generated by `scripts/generate-transaction-root-v1-fixture.mjs`, which also emits `onchain/aiken/lib/midgard/transaction-root-v1-golden.test.ak` — genuinely cross-implementation, but its `fixtures:transaction-root-v1:check` script is not in any CI workflow) and `sdk-abi-fixtures.test.ts` (fixture regenerated by the test itself under an env var, consumed by nobody else — a change detector, not a contract). Recommend the second adopt the first's generator+`--check`+Aiken-consumer shape.
- Shared helpers this chunk depends on and did not audit in depth: `tests/helpers/published-workflow-deployment.ts`, `tests/helpers/availability-challenge-emulator.ts`, `tests/helpers/cardano-native-fixtures.ts`, `tests/midgard-output-helpers.ts`, `tests/utils.ts` (database layer provider). None of them hide the decisive condition in the files above — the deciding value is visible in each test — but the emulator fixtures do carry substantial setup semantics.
- `harmonic-uplc-contract-eval.test.ts` carries the chunk's only `.skip`, and it is a model of the required form: documented cause (an upstream `lessThanByteString` length-ordering bug in `@harmoniclabs/plutus-machine`), the replacement coverage that keeps the claim alive, and a one-line re-enable condition.
- Not determined: whether the `transition-trace-abi.json` and `transaction-root-v1.generated.json` fixtures currently on disk match what their generators would produce (checking would require running builds, which is out of scope for a read-only audit).
