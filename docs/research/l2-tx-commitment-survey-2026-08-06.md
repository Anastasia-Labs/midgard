# How production optimistic L2s structure transaction commitments for fraud proofs

Research survey, 2026-08-06. All "currently live" claims were checked against
primary sources or first-party announcements on this date; retrieval dates are
noted inline where status could change.

Research question: how do production optimistic L2s structure transaction
commitments for fraud-proof purposes, and does any of them use per-field
Merkle commitments *inside* individual transactions?

## TL;DR

| Protocol | Sequencer/operator commitment granularity | Dispute-time item access | Oversized-data mechanism | Per-field Merkle inside a tx? |
|---|---|---|---|---|
| Fuel v1 (live fraud proofs 2020–21; deprecated) | Per-root-batch: binary Merkle root over **whole serialized txs** + flat hash of the tx calldata list; txs bounded 44–896 bytes | **Full-tx reveal** in proof calldata, Merkle-proved against the root, then parsed field-by-field on-chain | None needed — root payload ≤ 32,000 bytes, tx ≤ 896 bytes, always fits in one L1 tx | **No** |
| Fuel v2 / Ignition (live L2, **no live fraud proofs**; zkVM one-round planned) | Tx ID = flat SHA-256 of serialized tx (witnesses excluded); block `txRoot` = binary Merkle root over whole serialized txs | N/A (no live dispute path); planned design proves off-chain in a RISC-V zkVM, single on-chain interaction | N/A | **No** (only `receiptsRoot` — over execution receipts, not tx fields) |
| Optimism / OP Stack (permissionless fault proofs live since 2024-06-10) | **None per tx** — raw compressed channel frames posted as calldata/blobs; proposer commits per-proposal output root = keccak256 of state commitments | Bisection to one MIPS instruction; VM **memory Merkle proofs** against disputant-generated state roots; L1 data via preimage oracle: **full keccak-preimage reveal** hashed on-chain, or KZG point evaluation for blobs | **Large Preimage Proposal**: streaming keccak absorption across many txs, 136-byte blocks, depth-16 Merkle tree over blocks, challenge period, then "squeeze" | **No** |
| Arbitrum Nitro / BoLD (permissionless BoLD live since 2025-02-12) | Per-batch **flat keccak256** dataHash chained into a hash-chain accumulator; no Merkle over txs | Bisection via disputant-generated **history commitments** (Merkle over machine-state hashes) to one WAVM instruction; inbox messages and keccak preimages **fully revealed** and hashed on-chain in the one-step proof; blobs via KZG point evaluation | Bounded by design: `maxDataSize` = 117,964 bytes (90% of geth's 128 KB tx limit, headroom left "for proving"); blob contents never fully revealed (32-byte KZG openings) | **No** |

Headline answer: **none of the surveyed protocols commits per-field Merkle
roots inside individual transactions.** Where fine-grained access exists, it
comes from (a) whole-object reveal of a *bounded* object plus on-chain
parsing, (b) dispute-VM memory/trace Merkleization generated by *disputants at
dispute time* (not by the sequencer at commitment time), or (c) KZG point
evaluation for blob data. The finest commitment-time granularity observed
anywhere is the *whole transaction* (Fuel's Merkle leaves).

---

## 1. Fuel

Fuel is the closest architectural cousin (UTXO-based). Two distinct systems
must be kept apart:

- **Fuel v1** — the original optimistic rollup on Ethereum mainnet (Yul+
  contracts, live ~2020–21) with a **live, permissionless fraud-proof path**.
  Now deprecated.
- **Fuel v2 / Ignition** — the current FuelVM-based L2, live on Ethereum
  mainnet since 2024-10-16, **without live fraud proofs** (checked
  2026-08-06).

### 1.1 Fuel v1: whole-tx Merkle leaves, full-tx reveal, on-chain parse

What the operator commits. Block producers commit "roots" via
`commitRoot(merkleTreeRoot, commitmentHash, length, token, fee)`
([Root.yulp](https://github.com/FuelLabs/fuel-v1-contracts/blob/master/src/Root.yulp)).
Each root carries **two** commitments over the same batch of transactions:

- `merkleTreeRoot` — a binary Merkle tree root whose **leaves are whole
  serialized transactions**;
- `commitmentHash` — a "simple hash of list of transactions", i.e. a flat
  hash over the batch calldata.

Transactions themselves travel as L1 calldata; the contract enforces a
maximum root payload of 32,000 bytes and up to 2,048 transactions per root
(Root.yulp comments: "Calldata max size enforcement (~2M gas / 16 gas per
byte/64kb payload target)").

Dispute-time item access. The fraud provers (`provers/InvalidTransaction.yulp`,
`provers/InvalidInput.yulp`, `provers/DoubleSpend.yulp`, etc.) consume a
`TransactionProof` struct
([Transaction.yulp](https://github.com/FuelLabs/fuel-v1-contracts/blob/master/src/Transaction.yulp))
that contains the block header, the root header, a Merkle proof, and —
critically — **the entire serialized transaction bytes**
(`transaction.length: uint16, transaction: [bytes1]`). The leaf hash is
recomputed on-chain over the revealed bytes (`computeLeafHash` with an RFC-6962
style `0x00` leaf prefix) and checked against `merkleTreeRoot`; field access is
then plain byte parsing of the revealed transaction (`selectInput`,
`selectOutput`). This is viable because transactions are hard-bounded:

```
TRANSACTION_SIZE_MIN := 44
TRANSACTION_SIZE_MAX := 896
```

(Transaction.yulp). A ≤896-byte object always fits in one Ethereum
transaction with room for the rest of the proof, so "reveal the whole thing
and walk it" was the entire design. The Fuel docs describe the transaction
fraud-proof style as UTXO pointer checking: fraud proofs "simply require each
spend of a UTXO to 'point' to the creation of the UTXO"
([fuelbook fraud proofs](http://fuelbook.fuel.network/master/technology/fraud_proofs.html)).

Per-field commitments: none. The transaction is committed only as an opaque
Merkle leaf (whole bytes) plus its membership in the flat `commitmentHash`.

### 1.2 Fuel v2 / Ignition: flat tx-ID hash, whole-tx Merkle leaves at block level

Transaction ID. `sha256(CHAIN_ID ++ serialized_tx)` over the canonical
serialization, **without witness data** and with certain fields zeroed for
signing ([fuel-specs identifiers/transaction-id.md](https://github.com/FuelLabs/fuel-specs/blob/master/src/identifiers/transaction-id.md)).
Flat hash; no Merkle structure at the transaction level.

Transaction format. `TransactionScript` is a flat canonical serialization of
fields (`scriptGasLimit`, `receiptsRoot`, lengths/counts, `script`,
`scriptData`, `policies`, `inputs`, `outputs`, `witnesses`)
([fuel-specs tx-format/transaction.md](https://github.com/FuelLabs/fuel-specs/blob/master/src/tx-format/transaction.md)).
The **only** Merkle root embedded inside a transaction is `receiptsRoot` —
"root of the binary Merkle tree of receipts", i.e. a commitment to *execution
outputs*, not to the transaction's own fields. It is not a per-field
commitment scheme.

Block-level roots. The block application header commits
(`[fuel-specs protocol/block-header.md](https://github.com/FuelLabs/fuel-specs/blob/master/src/protocol/block-header.md)`):

- `txRoot` — verbatim: "Merkle root of transactions in this block" (binary
  Merkle tree; leaves are the transactions, not tx IDs);
- `message_outbox_root` — "Merkle root of output messages `messageId` in this
  block" (leaves are message *IDs*);
- `event_inbox_root` — "Merkle root of all events imported from L1 in this
  block".

The binary Merkle tree is SHA-256 with RFC-6962-style domain separation
(`node.v = h(0x00, serialize(d))` for leaves, `h(0x01, l.v, r.v)` for internal
nodes) ([fuel-specs protocol/cryptographic-primitives.md](https://github.com/FuelLabs/fuel-specs/blob/master/src/protocol/cryptographic-primitives.md)).
So the finest granularity of commitment is again the whole serialized
transaction as one leaf.

Fraud-proof status (retrieved 2026-08-06). Ignition has **no live fraud
proofs**. L2BEAT (secondary tracker, cited for status only): "Currently the
system permits invalid state roots"
([l2beat.com/scaling/projects/fuel](https://l2beat.com/scaling/projects/fuel)).
First-party: the Fuel Book says "Hybrid proving is being developed, and
prototyping is done with RISC-V-based zkVMs like SP-1 and RISC-0" — i.e. the
*planned* design is a one-round zk fraud proof, explicitly "rather than
playing bisection games on-chain like other rollups"
([fuel-book fuel-and-ethereum.md](https://github.com/FuelLabs/fuel-book/blob/main/docs/src/the-architecture/fuel-and-ethereum.md)).
The older FuelVM docs describe an Interactive Verification Game (bisection)
design; the current first-party direction supersedes it. Both are *planned*,
not live.

**Per-field Merkle inside a tx: No** (v1 and v2 both).

## 2. Optimism / OP Stack

Status: permissionless fault proofs (Cannon + Fault Dispute Game) live on OP
Mainnet since **2024-06-10**, per the first-party announcement
([optimism.io blog](https://www.optimism.io/blog/permissionless-fault-proofs-and-stage-1-arrive-to-the-op-stack));
the Security Council retains a fallback to permissioned mode.

### 2.1 What the sequencer commits about transactions: nothing per-tx

The batcher posts **raw compressed data**, not commitments. Batcher
transactions are `version_byte ++ rollup_payload`, containing channel frames
(`channel_id ++ frame_number ++ frame_data_length ++ frame_data ++ is_last`);
channels are ZLIB-compressed concatenations of RLP-encoded batches whose
`transaction_list` is "an RLP-encoded list of EIP-2718 encoded transactions"
([specs.optimism.io/protocol/derivation.html](https://specs.optimism.io/protocol/derivation.html)).
There is **no Merkle or hash commitment over L2 transactions** posted by the
batcher at all — the L1 data itself (calldata or EIP-4844 blob) *is* the
commitment, anchored by L1 block hashes.

State commitments are made separately by proposers as **output roots**:

```
output_root = keccak256(version_byte || state_root || withdrawal_storage_root || latest_block_hash)
```

([specs.optimism.io/protocol/proposals.html](https://specs.optimism.io/protocol/proposals.html)).
Granularity: one 32-byte root per proposal. Nothing per-transaction, let
alone per-field.

### 2.2 Dispute-time item access: disputant-generated VM Merkleization + preimage oracle

The Fault Dispute Game bisects a game tree of claims: above `SPLIT_DEPTH`,
claims are output roots; below it, "a commitment to the last VM state in a
trace" ([specs.optimism.io/fault-proof/stage-one/fault-dispute-game.html](https://specs.optimism.io/fault-proof/stage-one/fault-dispute-game.html)).
These execution-trace claims are produced by the **disputants during the
game** (bonded moves), not by the sequencer in advance. At `MAX_GAME_DEPTH`
the base case is `step`, which runs one MIPS instruction on-chain.

The Cannon FPVM Merkleizes VM memory as a fixed-depth binary Merkle tree —
current MIPS64 spec: "The tree has a fixed-depth of 59 levels, with leaf
values of 32 bytes each", keccak256 throughout; the state witness is a
188-byte buffer whose keccak hash (status byte substituted) is the claim
([specs.optimism.io/fault-proof/cannon-fault-proof-vm.html](https://specs.optimism.io/fault-proof/cannon-fault-proof-vm.html)).
On-chain, `MIPS64.step(bytes _stateData, bytes _proof, bytes32 _localContext)`
takes the packed VM state plus Merkle branches for the memory the instruction
touches ([MIPS64.sol](https://github.com/ethereum-optimism/optimism/blob/develop/packages/contracts-bedrock/src/cannon/MIPS64.sol)).

Transaction bytes enter this world through the **preimage oracle**: the fault
proof program reads L1 batch data by hash. Key types include global keccak256
(type 2), sha256 (type 4), and EIP-4844 blob KZG (type 5, keyed
`5 ++ keccak256(commitment ++ z)[1:]`, authenticated by point-evaluation
proof) ([specs.optimism.io/fault-proof/index.html](https://specs.optimism.io/fault-proof/index.html)).
For a small keccak preimage the authentication is a **full-preimage reveal**:
`loadKeccak256PreimagePart(uint256 _partOffset, bytes calldata _preimage)`
hashes the entire supplied preimage on-chain and stores the requested 32-byte
part ([PreimageOracle.sol](https://github.com/ethereum-optimism/optimism/blob/develop/packages/contracts-bedrock/src/cannon/PreimageOracle.sol)).

### 2.3 Oversized data: the Large Preimage Proposal (LPP)

When a keccak preimage is too large to reveal-and-hash in one L1 transaction,
the OP Stack absorbs it **across multiple transactions** using keccak's sponge
structure ([PreimageOracle.sol](https://github.com/ethereum-optimism/optimism/blob/develop/packages/contracts-bedrock/src/cannon/PreimageOracle.sol)):

- `initLPP(uuid, partOffset, claimedSize)` — bonded (≥ 0.25 ether) proposal;
- `addLeavesLPP(uuid, inputStartBlock, input, stateCommitments, finalize)` —
  streams 136-byte keccak blocks; each block becomes a Merkle leaf
  `keccak256(input || index || stateCommitment)` where `stateCommitment` is a
  hash of the claimed 1600-bit keccak state matrix after absorbing that block;
  an incremental binary tree of depth `KECCAK_TREE_DEPTH = 16` (≤ 65,535
  leaves) is maintained on-chain;
- `challengeLPP(...)` / `challengeFirstLPP(...)` — during `CHALLENGE_PERIOD`,
  anyone can Merkle-prove adjacent pre/post leaves and re-execute one
  absorption step on-chain to show a state commitment is wrong, seizing the
  bond;
- `squeezeLPP(...)` — after the unchallenged period, the final digest is
  squeezed and the preimage part becomes authorized in the oracle.

This is the industry's canonical answer to "flat-hash preimage exceeds
single-transaction capacity": it *depends on* the hash being an incrementally
absorbable sponge whose midstate can be committed per block and re-checked
one permutation at a time.

**Per-field Merkle inside a tx: No.** No transaction-level commitment exists
at all; all fine-grained access is VM-memory Merkle proofs (disputant-built)
plus preimage reveals against flat hashes (or KZG openings for blobs).

## 3. Arbitrum Nitro / BoLD

Status: BoLD (permissionless validation/challenges) live on Arbitrum One and
Nova since **2025-02-12**, per first-party material
([blog.arbitrum.io](https://blog.arbitrum.io/bold-permissionless-validation-for-arbitrum-chains/),
[docs.arbitrum.io BoLD gentle introduction](https://docs.arbitrum.io/how-arbitrum-works/bold/gentle-introduction):
"BoLD enables anyone to participate in validating the chain state (including
challenges)").

### 3.1 What the sequencer commits: flat batch hash in a hash-chain accumulator

`SequencerInbox.sol` commits each batch as a **flat keccak256**
([SequencerInbox.sol](https://github.com/OffchainLabs/nitro-contracts/blob/main/src/bridge/SequencerInbox.sol)):

- calldata batches: `keccak256(bytes.concat(header, data))`;
- blob batches: `keccak256(bytes.concat(header, DATA_BLOB_HEADER_FLAG, abi.encodePacked(dataHashes)))`
  (the versioned blob hashes stand in for the data);
- the 40-byte header holds timestamps/block bounds/delayed-message count.

Each message hash is folded into a **hash chain**: the one-step prover
recomputes `acc = keccak256(abi.encodePacked(beforeAcc, messageHash, delayedAcc))`
and checks it against `bridge.sequencerInboxAccs(msgIndex)`
([OneStepProverHostIo.sol](https://github.com/OffchainLabs/nitro-contracts/blob/main/src/osp/OneStepProverHostIo.sol)).
No Merkle tree over transactions, no per-tx commitment — the granularity is
the batch, inside a linear accumulator.

### 3.2 Dispute-time item access: history commitments + full-reveal one-step proofs

BoLD disputes are structured around **history commitments** — "a Merkle tree
of asserted states from some start to endpoint" — produced by **validators at
dispute time** and bisected until one WAVM instruction is isolated; then "both
parties run that step to produce, and then submit, a one-step proof to the
OneStepProof smart contract"
([docs.arbitrum.io BoLD gentle introduction](https://docs.arbitrum.io/how-arbitrum-works/bold/gentle-introduction)).

Machine state itself is Merkleized by the prover: WAVM memory uses 32-byte
leaves hashed with a domain prefix —

```rust
pub const LEAF_SIZE: usize = 32;
fn hash_leaf(bytes: [u8; Memory::LEAF_SIZE]) -> Bytes32 {
    crypto::keccak_seq(&[b"Memory leaf:", &bytes])
}
```

with a 28-layer tree ([nitro crates/prover/src/memory.rs](https://github.com/OffchainLabs/nitro/blob/master/crates/prover/src/memory.rs)).

When the disputed instruction must *read transaction bytes*, the OSP
authenticates them by **full reveal against the flat commitment**
([OneStepProverHostIo.sol](https://github.com/OffchainLabs/nitro-contracts/blob/main/src/osp/OneStepProverHostIo.sol)):

- `executeReadInboxMessage`: the proof supplies the complete message bytes;
  the contract computes `keccak256(message)` and re-derives the accumulator
  link (formula above) against the on-chain accumulator.
- `executeReadPreImage` (keccak type): the proof supplies the complete
  preimage; `require(keccak256(preimage) == leafContents, "BAD_PREIMAGE")`;
  a 32-byte chunk at the requested offset is then extracted
  (`LEAF_SIZE = 32`).
- EIP-4844 blob preimages: authenticated via the KZG point-evaluation
  precompile (address 0x0A) at a bit-reversed root-of-unity evaluation point —
  a 32-byte field element is opened **without ever revealing the blob**.

### 3.3 Oversized data: bounded by construction

Arbitrum has no LPP-style multi-transaction absorption for keccak preimages.
Instead the objects that must be fully revealed are **bounded up front**:
`maxDataSize` (immutable in SequencerInbox) is set to **117,964 bytes** on L1,
documented as "90% of Geth's 128KB transaction size limit, leaving ~13KB for
proving" ([docs.arbitrum.io](https://docs.arbitrum.io/run-arbitrum-node/sequencer/run-sequencer-node);
the constant is enforced in
[SequencerInbox.sol](https://github.com/OffchainLabs/nitro-contracts/blob/main/src/bridge/SequencerInbox.sol)).
I.e., the batch bound is chosen *specifically so that the full batch plus
proof overhead fits in one L1 transaction*. Blob-carried data sidesteps
reveal entirely via KZG openings.

**Per-field Merkle inside a tx: No.** Flat batch hashes + hash-chain
accumulator at commitment time; Merkle granularity exists only in
disputant-generated machine-state/history commitments and 32-byte KZG
openings.

## 4. Implications for Midgard

Context (given, not researched): Midgard has **no dispute VM** — fraud proofs
are hand-written per-rule Plutus validators walking multi-transaction
computation threads on Cardano L1. L1 transactions are bounded at 16,384
bytes; Plutus exposes only whole-input hash builtins (no incremental
midstate across transactions); previously published UTxOs' inline datums can
be referenced without counting against the consuming transaction's 16,384-byte
size (publication carriage). Midgard L2 transactions are themselves ≤ 16,384
bytes, so every per-field preimage is ≤ ~16 KB. The decision under review:
keep per-field domain-tagged counted Merkle commitments (blake2b-256 leaves
binding count/index/length/content, O(log n) item openings) versus revert to
a flat blake2b-256 per field over raw canonical CBOR, with disputes doing
full-preimage reveal via carriage plus an on-chain boundary walk (or
init-step offset table) for item access.

### What the survey actually shows

1. **No precedent exists for per-field Merkle commitments inside
   transactions.** Zero of three protocols do it — including Fuel, the UTXO
   cousin, in both generations. The finest *commitment-time* granularity
   observed anywhere in the survey is the whole serialized transaction as a
   Merkle leaf (Fuel v1 root trees, Fuel v2 `txRoot`). Optimism commits
   nothing per-tx at all; Arbitrum commits a flat hash per ~118 KB batch.

2. **But the comparison is apples-to-oranges for the two live VM-based
   systems.** OP and Arbitrum get arbitrarily fine-grained access "for free"
   from dispute-VM memory/trace Merkleization that is generated by *bonded
   disputants at dispute time* and never committed by the sequencer. The
   sequencer's commitment can afford to be maximally flat precisely because a
   VM re-derives everything and the L1 only ever checks one instruction
   against disputant-built Merkle roots. Midgard has no such second layer:
   whatever structure fraud validators can open **must already be in the
   operator's commitment**. The industry's flat commitments are not evidence
   that flat is sufficient for a VM-less design; they are evidence that a
   dispute VM makes commitment structure irrelevant.

3. **The relevant precedent for a VM-less design is Fuel v1, and it matches
   the flat/reveal pattern.** Fuel v1 is the one surveyed system whose fraud
   proofs, like Midgard's, are hand-written per-rule provers with no VM — and
   its answer was: bound the object hard (≤ 896 bytes), commit it as one
   opaque Merkle leaf, reveal the *entire* object in the proof, and parse
   fields by walking revealed bytes on-chain. Arbitrum's OSP does the same at
   batch granularity (full reveal + flat-hash check + offset extraction),
   made safe by `maxDataSize` = 117,964 within a 128 KB L1 transaction — the
   bound is chosen so reveal-plus-proof fits with ~13 KB headroom. Midgard's
   proposed flat design (bound the field preimage at ≤ ~16 KB, flat-hash it,
   full reveal, boundary-walk for items) is structurally the same move.

4. **The one place the industry hit Midgard's exact problem — a flat hash
   whose preimage exceeds single-transaction capacity — the workaround was
   heavy, and it relies on a primitive Plutus lacks.** OP's Large Preimage
   Proposal exists because a keccak preimage larger than one L1 tx cannot be
   hashed in one go; the fix streams 136-byte sponge blocks across many
   transactions with per-block midstate commitments, an on-chain incremental
   Merkle tree, a bond, and its own challenge game. That entire mechanism is
   built on keccak's absorbable midstate — exactly what Plutus's whole-input
   hash builtins do not expose. Midgard avoids needing LPP-class machinery
   only because (a) preimages are bounded at ~16 KB and (b) publication
   carriage lets a single script execution see complete preimage bytes via
   reference datums without those bytes counting against the verifying
   transaction's size. Both legs matter. One caveat worth stating explicitly
   (inference, not a surveyed fact): unlike Arbitrum, where the reveal budget
   (128 KB) comfortably exceeds the object bound (118 KB) *within the same
   transaction*, Midgard's carriage budget per *publication* transaction is
   the same 16,384 bytes as the maximum field preimage, so near-bound
   preimages must be published across multiple carriage transactions and
   reconciled (concatenated) inside the verifying script before the single
   whole-input hash check. The flat design's dispute cost is therefore a
   multi-transaction publication walk in the worst case — closer in spirit to
   LPP's multi-tx absorption than to Arbitrum's one-shot reveal, though
   without LPP's extra challenge game since the final hash check is still a
   single whole-input verification.

5. **What the counted Merkle design buys is something no surveyed protocol
   needed: O(log n) item openings without full-field reveal, committed by the
   operator.** The survey cannot settle whether Midgard needs it — that turns
   on whether any fraud rule requires item access where full-field reveal via
   carriage is too expensive inside a bounded multi-transaction thread (e.g.
   worst-case thread length, min-fee economics of carriage transactions, and
   how often single-item access suffices). What the survey *can* say: the
   industry pattern for VM-less, bounded-object fraud proofs is flat
   commitment + full reveal + on-chain parse (Fuel v1); Merkle granularity
   below the whole-object level appears only where disputants build it
   ephemerally (Cannon memory, WAVM memory, BoLD history) or where the base
   layer provides algebraic openings (KZG blobs). A per-field counted Merkle
   commitment made by the operator would be *novel structure relative to
   every surveyed system* — justified, if at all, by Midgard's unique
   constraint that the operator's commitment is the only Merkleization that
   will ever exist, and by concrete thread-cost arithmetic, not by industry
   precedent.

6. **No contradiction found with the framing of this research request.** One
   nuance: "Fuel" as a live-fraud-proof precedent means Fuel **v1**
   specifically; the current Fuel product (Ignition) has no live fraud-proof
   path (as of 2026-08-06) and its announced direction is a one-round zkVM
   proof — i.e. Fuel's *future* answer to item access is "prove execution in
   a zkVM", which is a third pattern unavailable to Midgard's hand-written
   validator approach.
